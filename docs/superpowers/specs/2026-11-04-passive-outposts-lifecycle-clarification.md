# Passive outposts: clean lifecycle, retained authority и rollback epoch

Дата: 4 ноября 2026 года. Проектное уточнение: подтверждённая developer runtime модель `gpt-6-astra`.

**Статус:** main принял этот technical ruling как уточнение уже одобренного Task13 без нового игрового выбора. Здесь только документационный контракт для реализации основной Sol: не code review, не итоговое whole-branch review и не утверждение реализованности. Tests ниже **предложены, но не выполнены**. Единственное итоговое review остаётся после Task16; capability/feature остаётся OFF до Tasks13–15 и остальных approved readiness gates.

Основа: [approved design §8–9](<2026-11-03-passive-outposts-design.md#L246-L308>), [Task13](<../plans/2026-11-03-passive-outposts.md#task-13-archive-resetrecreate-и-узкий-rollback-conflict-barrier>), [ordinary-return clarification](<2026-11-04-passive-outposts-ordinary-return-clarification.md#L132-L143>) и [recovery0.8.1](<2026-11-03-recovery-correctness-design.md>). Исходная спецификация не переписывается. Ниже новые имена состояния/интерфейсов — требуемый контракт Task13, не существующие API.

## 1. Уже утверждённые ограничения

- Clean reset/recreate сохраняет прежнюю явно destructive семантику. **Не переносить имущество в новую generation**, не возвращать из retired world и не вводить новый игровой способ восстановления. Все outposts закрыты, имущество physically received в accepted home snapshots, unresolved transfer/Started без согласованного receipt отсутствуют. Archived owner прежде восстановлен. Closed/tombstone/handed-off история не исчезает.
- Recreate сначала проверяет полный affected-owner set, включая архивных и участников связанных cleanup effects; отказ последнего владельца означает ноль effects у всех. Lock order **A → sorted O → S → Live → T**; новые protected operations не вклиниваются между preflight и completion.
- Journal закрепляется до cancellation/refund/file/generation/IsCurrent effects. Незавершённая destructive процедура оставляет maintenance, не публикует промежуточный мир и не replay-ится автоматически. Одна DB-транзакция не делает несколько file moves/старых transactions атомарными.
- Immutable snapshot/proof сохраняет exact world/owner/generation/write-epoch/boundary/snapshot-id/raw SHA256. Accepted historical evidence не является текущим разрешением mutation. Permanent ordinary negative fences, original/derived request identity, source/parcel/return receipts и все нужные bytes сохраняются.
- Допустимый rollback проверяет exact target/local frontier до effects; более новые только stock/clock изменения сами по себе не конфликт. Старые unrelated0.8.1 rollback semantics не перепроектируются. Login epoch не разрешает старый pending.
- Внешний anchor и непрерывная цепь защищаются существующим Pending → main DB domain+transition+head → external completion → success/events. Lost anchor/history не разрешает Initialize. Принятый SQLite/OS durability contract не расширяется обещанием power-loss proof для произвольных файловых операций.

## 2. Почему нужен именно mechanical bridge

[RecreateWorld](<../../../src/Rimlink.Server/Application/Admin/AdminOperations.cs#L569-L595>) удаляет World; [WorldService.Create](<../../../src/Rimlink.Server/Application/World/WorldService.cs#L30-L46>) позднее создаёт новый InfluenceInstanceId. [Initialize](<../../../src/Rimlink.Server/Application/Outposts/OutpostAuthority.cs#L168-L181>) запрещён при history, а [Begin/Open](<../../../src/Rimlink.Server/Application/Outposts/OutpostAuthority.cs#L47-L55>) пока предполагают одну world-binding. Это не основание очищать историю или ослаблять равенство WorldId.

Сохранить одни outpost rows тоже недостаточно: [SaveStore.Archive](<../../../src/Rimlink.Server/Application/Saves/SaveStore.cs#L326-L357>) удаляет live SaveVersion, а [stored resolver](<../../../src/Rimlink.Server/Application/Outposts/OutpostSnapshotGuard.cs#L382-L407>) знает только live row или ArchivedColonies manifest. Кроме того, [CheckStartupAsync](<../../../src/Rimlink.Server/Application/Outposts/OutpostFeature.cs#L45-L70>) сейчас останавливает host при history и любом не-Ready состоянии. Task13 должен явно различить исторически исправную authority без активного мира и незавершённую maintenance.

## 3. Technical clarification: одна chain, отдельная active binding

### 3.1. Journal и сохранение evidence

Использовать существующую [OutpostLifecycleOperation](<../../../src/Rimlink.Server/Storage/Entities/OutpostRecords.cs#L201-L215>), уже включённую в [OutpostDomainDigest](<../../../src/Rimlink.Server/Application/Outposts/OutpostDomainDigest.cs#L21-L35>). Новая таблица сама по себе не нужна. Versioned typed Intent/Progress/Result содержат:

- operation/request identity, actor, kind; исходные installation/world/boundary/head; полный отсортированный owner set, expected поколения/epochs и exact целевые значения;
- immutable план стадий и доказательств: original scope/id/hash, версии и необходимые source/parcel/negative-fence зависимости, planned destination locators; для rollback — target/frontier и переход текущего epoch; для WorldBind — retirement reference и target binding/configuration;
- проверяемый progress каждого side effect, ожидаемые before/after projections и final result. Intent неизменен, terminal Result не переопределяется; каждое изменение Progress/Phase защищено отдельным transition/head. Неизвестный kind/version/phase и противоречие — отказ, не generic whitelist.

Для Reset/Recreate последовательность journal фаз: **Prepared → EvidenceRetained → Destructive → Completed**. Prepared долговечно фиксируется до первого эффекта; перед конкретным destructive шагом уже записан его intent, после него сверяется и фиксируется наблюдённый результат. Только текущий владелец barrier продолжает свой operation; после crash нужен explicit evidence-backed recovery, не replay cancellation по одному названию phase. Marker исчезает только после доказанной completion всех запланированных стадий.

Retained evidence map принадлежит lifecycle operation, но не новой игровой generation. Каждый locator однозначно связывает original world/owner/generation/epoch/boundary/snapshot-id/raw hash, metadata версии и безопасный confined path. Число save version само по себе не ключ; после reset оно может повториться. Map/manifest и его digest защищены journal; размеры/shape проверяются до effects, overflow не разрешает pruning. Физические формы разрешает только [SaveFiles.ReadEvidence](<../../../src/Rimlink.Server/Application/Saves/SaveFiles.cs#L116-L148>): retain full либо delta вместе со всеми нужными base; проверенная материализация full допустима только с теми же exact raw bytes/id/hash и сохранённой исторической metadata.

**Порядок file cut:** journal planned locators → сохранить и проверить destination → protected commit новых reachable locators → убрать старые source rows/files → завершить journal. До переключения resolver использует старый locator, после — проверенный новый. Crash не оставляет единственную недостижимую копию. Все retired worlds и исходные source/parcel/snapshot proofs продолжают проверяться; missing/corrupt/ambiguous evidence означает maintenance, не исключение этой истории из проверки. Обычный compaction/hygiene не удаляет такие ссылки и bytes. Это evidence archive, не selectable восстановленная колония и не имущество новой generation.

[SnapshotGuard](<../../../src/Rimlink.Server/Application/Outposts/OutpostSnapshotGuard.cs#L249-L251>) получает явный lifecycle codec вместо blanket отказа любой lifecycle row, но **не** начинает принимать ещё не реализованные Task14 restore-authorizations. DomainDigest не покрывает live World/Player/SaveVersion автоматически: validator сверяет их фактические значения с текущей доказанной lifecycle projection. Предыдущие terminal записи проверяются как история, а не ошибочно требуют вечного равенства текущему Player epoch/generation.

### 3.2. Reset, retirement и последующее создание мира

1. **Clean Reset:** world и restore boundary прежние; generation меняется по прежней reset-семантике. Old scopes и evidence неизменны, новая generation не наследует их custody/assets. Нет новой Genesis/Initialize.
2. **Clean Recreate:** после полного preflight и всех journalled стадий удалить active World и закрепить Completed retirement с result **NoActiveWorld**. Authority/anchor сохраняют installation, прежнюю world-binding как историческую и непрерывный head. Не оставлять успешный recreate бесконечно unfinished; не объявлять отсутствие World случайным первым запуском.
3. **Поздний Configure/Create:** существующий административный маршрут выполняет отдельный typed **WorldBind** transition, ссылающийся на latest exact completed retirement, ещё не consumed другим WorldBind. Под barrier выбирается ровно один новый WorldId; immutable intent связывает source installation/world/boundary/head, retirement ID/digest, target WorldId, exact создаваемую конфигурацию и ожидаемые owner projections. Одной main DB transaction записываются World, lifecycle binding result, current authority projection и next head. Concurrent/replayed Create не создаёт вторую world/chain; сохранить existing отказ «world already exists», не добавлять новый wire request-id только ради этого bridge.
4. InstallationId и chain сохраняются. Для **clean** recreate restore boundary остаётся прежней: world identity/generation уже разделяют namespaces. Task14 fresh-boundary restore/import — другая процедура; она здесь не реализуется. Старые snapshots/transitions не получают новую world/boundary. Active lookups/manifest/custody используют current world, не произвольную историческую Active/Home строку.
5. WorldBind проходит существующий Pending protocol. Target binding фиксируется в typed Intent, уже покрытом [transition digest](<../../../src/Rimlink.Server/Application/Outposts/OutpostTransitionDigest.cs#L54-L69>) и Pending.NextHead.Digest; расширение anchor wire format не требуется только ради хранения target WorldId. Обычная transition.WorldId обозначает source binding; только валидный WorldBind меняет binding следующих transitions.
6. **Reconciliation:** Pending+DB-old сохраняет old binding; Pending+DB-next принимает только exact authenticated WorldBind target после проверки chain/retirement/configuration/actual projections и всех retained bytes, затем закрепляет target binding в anchor. Любое другое сочетание — maintenance. Committed anchor/main authority/current World согласованы либо доказан exact Completed NoActiveWorld. Не снимать общий WorldId check, не допускать world-switch по одному незаверенному intent. Success/configure response/events — после external completion.

### 3.3. Startup readiness не равна gameplay readiness

Добавить в server-only startup contract состояние **NoActiveWorld**; это successful historical validation, не alias Ready/RequiresInitialization/Maintenance. Именованные predicates ниже — условия контракта, не клиентские полномочия:

| State / доказанное условие | CanStartHost | CanBindSuccessor | CanMutateGameplay |
|---|---|---|---|
| Ready: current active World совпадает с verified binding, все evidence проверены | Да | Нет | Только с остальными readiness/capability gates и exact current scope |
| NoActiveWorld: exact Completed retirement, нет active World, нет unresolved Pending или unfinished stages, вся retained history проверена | Да, startup/admin plane доступен | Да, только existing authorized admin Create и exact retirement под barrier | Нет; также запрещены обычные hosted/background protected mutations |
| RequiresInitialization: доказанно нет feature history | Прежний first-use режим | Нет: обычный первоначальный Create не successor bind | Прежние feature gates; Initialize только explicit и history-empty |
| Maintenance: unfinished destructive marker либо mismatch/missing evidence/anchor | Нет для обычного startup | Нет | Нет |

NoActiveWorld не включает capability и не разрешает произвольный BeginHeldAsync. Исключение имеет только typed lifecycle WorldBind entry с проверенным retirement; IsAvailable остаётся false до полного safety graph. Unfinished operation нельзя превратить в NoActiveWorld лишь потому, что World уже удалён. Explicit maintenance/recovery не становится автоматической веткой обычного startup. Initial no-history World.Create/Initialize сохраняют прежний контракт.

## 4. Technical clarification: rollback write-epoch bridge

- Под общим barrier сначала **read-only** проверить exact target original bytes/scope и local frontier против всей custody/receipt истории — до EnsureFull, IsCurrent, epoch и прежних возвратов. Канонический target определяется IsCurrent, не highest Number. Сами rollback selection и canonical-current lookup — разные запросы.
- Protected lifecycle evidence связывает target id/raw hash/original scope/frontier с expected **текущим Player epoch e → e+1**, не target.epoch+1. IsCurrent, epoch, связанные DB effects и lifecycle transition/head фиксируются согласованно. Replay/reconciliation этого operation не повышает epoch повторно. Если есть внешние шаги, к ним применяется journal-before-effects, не фиктивная атомарность файлов.
- Target XML, SaveVersion historical epoch, OutpostSnapshotLink и уже accepted proof/receipt bytes остаются неизменными. [OpenCurrent](<../../../src/Rimlink.Server/Application/Saves/SaveStore.cs#L219-L233>) отдаёт original bytes и текущий write epoch отдельно; controlled canonical download проверяет именно выбранный файл. Не переписывать queued pending/upload, request intent, local ID или historical proof новым login scope.
- Download header получает additive server-authored `OutpostRollbackBridge`: lifecycle operation/transition ID+digest, canonical target id/raw hash/original scope, current authorized scope и compatible local-frontier digest. Он строится только из committed lifecycle evidence; client-supplied echo не authority. На upload сервер снова проверяет stored bridge, текущий owner epoch/binding и exact metadata; последующие unrelated head/stock changes допустимы лишь при прежней доказанной совместимости. Это не новый игровой RPC и не reauthorization через login. Добавить typed message в [outposts.proto](<../../../src/Rimlink.Protocol/Protos/outposts.proto>) и optional `rollback_bridge` в уже импортирующий его [SaveHeader](<../../../src/Rimlink.Protocol/Protos/saves.proto#L28-L49>) и `OutpostSaveMetadata`; только новые tags, bounded shape, без изменения старых полей. Header/target/epoch/bridge выбираются одним canonical cut под тем же fence, не отдельным read после снятия lock. Echo в новом snapshot нужен для структурной связи historical captures, но сервер всегда сверяет его с journal. Parser проверяет shape и наличие соответствующего original accepted receipt; только server evidence устанавливает accepted authority. После первого accepted fresh snapshot bridge остаётся provenance rollover, не повторяемым разрешением менять live registry; последующие обычные transitions могут расширять frontier по прежним правилам.
- После проверки actual downloaded bytes против canonical target и server bridge клиент на **main thread** обновляет только mutable outer metadata scope и scope тех live own-game registry bindings, которые точно разрешены этим canonical frontier. UUID/assignment/reference/tombstone/custodian не меняются, чужие/исторические bindings не переводятся в current scope. Изменение всех затронутых bindings согласованное, при неоднозначности — block writes, не частичная пересадка. Старый файл, pending/outbox и original registry observations в historical snapshots не редактируются. Затем нужен **новый** actual captured snapshot с новым ID/raw hash/current outer epoch, accepted до использования как нового mutating proof. Bridge действует только внутри same-world/owner/generation/boundary, не через reset/recreate/restore.
- Уже accepted terminal receipts/frontier/captures остаются byte-exact original historical evidence. Validator проверяет их исходный accepted snapshot/transition/source и rollback связь; это **history/ACK-only**, не повторный spawn, credit, admission или отмена permanent negative fence. Completed ordinary captures не превращаются в новые active outgoing. Новые операции получают собственные fresh captures/proofs. [OutpostRecoveryData.Validate:67](<../../../src/Rimlink.Protocol/OutpostRecoveryData.cs#L64-L78>) сейчас требует capture.Scope == outer для OrdinaryOutgoing, но registry проверяет только valid scope. Добавить квалифицированную historical-accepted ветку для immutable captures, а не общее равенство scope всей registry и не blanket allowance любого старого capture.
- Нужны отдельные historical-accepted ветки в [OutpostAdmissionEvidence](<../../../src/Rimlink.Server/Application/Outposts/OutpostAdmissionEvidence.cs#L22-L35>) и [OrdinaryReturnAcceptance](<../../../src/Rimlink.Server/Application/Outposts/OrdinaryReturnAcceptance.cs#L28-L47>), не удаление scope equality повсеместно. Live operation scope/header/proof остаются exact; old Prepared/Ready/Started без accepted evidence не reauthorize. Старый outbox quarantined; existing strict [OutpostReconciliation](<../../../src/Rimlink.Client.Core/Outposts/OutpostReconciliation.cs#L16-L33>) не должен начать replay old scope.

### 4.1. LegacySnapshot и ProtectedSnapshot

**Принятое bounded ruling:** unrelated0.8.1 относится к затронутому namespace/истории, **не только** к history-empty installation. Игрок Б без релевантной protected истории сохраняет прежнюю допустимость rollback при истории А. Global HasHistory выбирает authority/journal route, но не создаёт Б обязанность иметь OutpostSnapshotLink. Это mechanical classifier/codec, не новый игровой способ восстановления.

- **Read-only target/classifier до effects:** под A→sorted O→S→Live→T для actually affected set выбрать конкретный persisted owner/version; проверить реальные full/delta bytes, original identity/hash/recovery по0.8.1 и доказанную server association с namespace (world, owner, generation, boundary). Target original epoch ≤ current e, не обязательно равен e; previous canonical current выбирается отдельно по IsCurrent. Если допустимый legacy format не хранит часть tuple, journal сохраняет фактическую legacy identity и явное отсутствие полей отдельно от доказанной namespace association; не фабрикует XML metadata/OutpostSnapshotLink и не ослабляет обязательные проверки0.8.1. Unknown/corrupt/неполная обязательная identity — refusal, не empty history.
- **LegacySnapshot:** доказанно нет relevant protected local frontier/custody/operation/receipt/ordinary negative-fence/dependencies в этом namespace **за все epochs**; target/current не требуют tagged evidence. Проверять incoming/outgoing/handed-off связи, не только PlayerId Б или активные outposts. Чужая и retired-world/generation история сама по себе не локальный конфликт, но все original scopes/links/real source/parcel/snapshot bytes продолжают проверяться. Чисто mechanical legacy-journal rows не являются игровой custody history.
- **ProtectedSnapshot:** feature-bearing metadata/required protected references требуют прежнего exact-link/frontier compatibility check и §4 bridge. Closed/tombstone/handoff/accepted history не исчезает; missing referenced link, malformed metadata или unsupported format не разрешают legacy fallback. Совместимый protected rollback остаётся допустимым по прежнему local-frontier контракту.
- **Typed journal:** proven history-empty installation может сохранить прежний execution path с recheck под fence. При global history даже LegacySnapshot проходит protected rollback journal variant, не owner-only return-null в незащищённый legacy executor. Intent связывает exact target/previous-current identity, raw hashes/locators, namespace association, before e→e+1 и affected projections. IsCurrent/epoch/DB effects/journal/head согласованы через Pending→main commit→external completion; reconciliation того же operation не повышает epoch повторно. Внешние effects — только journal-before-effects, без destructive autoreplay. Retain все referenced real bytes обоих variants, не подменять историю пустым synthetic link.
- **Cleanup owners:** новый journal обязательно включает Б как меняющий epoch owner и supersedes только его latest current projection. Старый immutable intent А, где Б был cleanup participant, не меняется; остальные epochs неизменны, если собственных effects нет. Все реально затронутые cleanup owners входят в locks/journal, не все historical owners установки автоматически. Нельзя отключать current epoch validator. Legacy projection должна принимать и следующий обычный fresh legacy save нового epoch по exact legacy identity, без навязанного OutpostSnapshotLink.
- **GetRollbackBridge:** epoch gap сам по себе не требует Outpost bridge. Для exact committed LegacySnapshot selection вернуть null **после** journal/namespace/bytes/current-projection validation (либо применить прежний no-history путь); header несёт обычный current0.8.1 epoch. Это не разрешение Outposts registry/capture rebase, переноса old proofs или replay pending/outbox. Для ProtectedSnapshot обязательны server bridge, fresh actual capture и historical-accepted-only/ACK; missing обязательная связь — refusal. Strict live scope и permanent ordinary negative fences сохраняются в обоих variants.

## 5. Узкие интерфейсы и integration seams Task13

Существующие planned lifecycle APIs и новые server-only seams фиксируются в Task13. New DTO `LifecycleStep` живёт рядом с lifecycle codec: operation ID/kind, immutable intent/digest, expected head/phase, next phase, expected before/after projections, typed retained-locator/rollback/WorldBind data. Это не произвольный bypass Ready; unknown/неподтверждённый step запрещён.

- `OutpostAuthority.BeginLifecycleHeldAsync(OutpostLease lease, TransitionIntent intent, LifecycleStep step, CancellationToken ct) → Task<OutpostAuthority.OutpostDomainTransaction>`: тот же scoped DB/единственная transaction и CompleteAsync protocol. Первый journal step разрешён после соответствующего preflight; продолжение — только exact owned operation/phase; WorldBind — только из NoActiveWorld. Никакого nested BeginTransaction или автоматического replay effects. Обычный BeginHeldAsync сохраняет gameplay-ready guard.
- [OutpostFeature](<../../../src/Rimlink.Server/Application/Outposts/OutpostFeature.cs>), [OutpostAuthority](<../../../src/Rimlink.Server/Application/Outposts/OutpostAuthority.cs>), [WorldService](<../../../src/Rimlink.Server/Application/World/WorldService.cs>) и [WorldGrpcService](<../../../src/Rimlink.Server/Grpc/WorldGrpcService.cs>): единые predicates §3.3, late Create под authority barrier, cancellation token до durable decision; существующие полномочия не расширяются.

Временно ещё не добавленная staged transition валидируется явно, не считается отсутствующей историей.
- [SaveStore](<../../../src/Rimlink.Server/Application/Saves/SaveStore.cs>), [SaveArchive](<../../../src/Rimlink.Server/Application/Saves/SaveArchive.cs>), [ColonyArchive](<../../../src/Rimlink.Server/Application/World/ColonyArchive.cs>), [ColonyHygiene](<../../../src/Rimlink.Server/Application/World/ColonyHygiene.cs>) и [AdminOperations](<../../../src/Rimlink.Server/Application/Admin/AdminOperations.cs>): preflight, retained map и journalled ordering; no archive GC of retained evidence.
