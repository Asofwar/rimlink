# Passive outposts — квалифицированная среда исполнения и сборки

**Статус:** узкое уточнение [Task 15 §10.9](2026-11-05-passive-outposts-admin-readiness-clarification.md#109-frozen-additive-executor-versus-historical-validation-2026-11-05-follow-up), без повторного итогового ревью. Реализация и проверки принадлежат Sol; приведённая ниже матрица ещё не выполнена этим документом. Product остаётся Pending/OFF; deploy не разрешён. Предыдущее [уточнение SQL bytes](2026-11-07-passive-outposts-migration-sql-bytes.md) сохраняется.

## Причина и выбранный маршрут

В текущем исходнике `ValidateArtifact` принимает Framework только `.NET 10.0.13`. Локальный `dotnet --info` подтвердил SDK `10.0.402` и установленные Microsoft.NETCore.App/Microsoft.AspNetCore.App `10.0.13`. Сообщённый CI запускает SDK `10.0.403` / runtime `10.0.14` и отказывает с `restore-schema-artifact-invalid` до main plan/DDL. Это согласуется с точной проверкой runtime; документ не утверждает самостоятельного повторения 48 CI failures или поломки SQL/версии `0.9.1`.

**Для следующего публичного выпуска выбрать отдельную квалификацию `.NET 10.0.14`, сохранив старую `.NET 10.0.13` запись для прежних свидетельств.** Microsoft выпустил `10.0.14` как внеплановое обновление безопасности; SDK `10.0.403` включает соответствующие .NET и ASP.NET runtimes. Применимость конкретных CVE к Rimlink здесь не установлена, поэтому нельзя ни утверждать уязвимость Rimlink, ни объявлять обязательное понижение runtime до `10.0.13` безопасным решением. [Официальные release notes](https://github.com/dotnet/core/blob/main/release-notes/10.0/10.0.14/10.0.14.md).

Изолированный SDK `10.0.402` / runtime `10.0.13` допустим как контрольная среда воспроизведения прежней квалификации. Зелёный прогон в ней сам по себе не закрывает выпуск с плавающими CI/Docker/runtime. Не удалять и не понижать системные SDK/runtimes пользователя, не менять глобальную сеть или настройки ОС.

## Закрытый контракт квалификации

- Сохранить исходный qualification ID/version, provider profile и provenance `rimlink-outposts-schema-20261105-0520` неизменными, включая его точное соответствие `.NET 10.0.13`. Старые plans/heads/cuts/receipts не переписываются и не переквалифицируются задним числом.
- После реальных проверок добавить одну отдельную code-owned запись квалификации для `.NET 10.0.14`: собственные неизменные QualificationId/ProviderProfile и evidence SDK/runtime/provider/backend. Старые шесть schema descriptors, ProfileId/ProfileDigest, четыре ребра и два SQL recipe digest сохраняются, если наблюдения подтверждают точное равенство. Отличие каталога/recipe требует отдельного решения; нормализация и замена ожидаемых bytes запрещены.
- Выбор новой операции связывает фактический Framework с его точной записью квалификации и существующими EF/SQLite/backend predicates. Recorded-step validation проверяет соответствие **qualification + provider profile + artifact.Framework**, а не независимое попадание каждого поля в общий список. Нельзя расширить старый профиль условием `>= 10.0.13`, префиксом `.NET 10.0`, сравнением только major/minor или разрешением любого patch. Непроверенный runtime остаётся Unsupported.
- Форматы Additive/v2 и ExecutorArtifact/v1 не требуют изменения только ради второй явно квалифицированной записи. Fresh selection и pre-DDL Resume сохраняют точное совпадение текущего artifact/MVID/hash/provider/recipe с уже frozen планом. На runtime `10.0.14` нельзя переисполнить незавершённое DDL плана с executor `10.0.13` либо заменить его witness. После доказанного post-schema состояния и при historical/nested validation применяются прежние no-DDL правила: старый корректный witness читается без требования старого runtime/DLL у читателя и без генерации SQL.

## Минимальная конкретная правка среды

1. **SDK/CI:** закрепить SDK `10.0.403` в `global.json` с `rollForward: disable`; убрать `10.0.x` из CI и закрепить Linux runner `ubuntu-24.04`. Использовать отдельный каталог toolchain, созданный для этого прогона, и официальный `dotnet-install` с exact `--version 10.0.403`; команды build/test должны использовать именно его `dotnet`. Зафиксировать путь, SDK и реальные runtime assemblies тестового процесса. `global.json` выбирает SDK независимо от runtime. [Microsoft: global.json](https://learn.microsoft.com/en-us/dotnet/core/tools/global-json), [dotnet-install](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-install-script).
2. **Не считать exact setup-dotnet достаточным:** используемый `actions/setup-dotnet@v4` сначала устанавливает runtime из канала LTS, затем запрошенный SDK. Даже отдельный `DOTNET_INSTALL_DIR` с exact SDK может содержать более новый runtime. Не маскировать это проверкой только `dotnet --version`; не требуется обновлять весь набор GitHub Actions ради этой задачи. [Исходник v4](https://raw.githubusercontent.com/actions/setup-dotnet/v4/src/installer.ts).
3. **Server/CLI:** у поставляемых `rimlink-server` и `rimlink-tools` явно задать runtime requirement `10.0.14` и `RollForward=Disable` для данной квалифицированной поставки; проверить сгенерированные runtimeconfig для обоих требуемых shared frameworks, без `10.0.0` и fallback на иной patch. Достаточно свойств существующих проектов, без нового launcher/framework и без глобального ограничения клиентской DLL/Discord. `RuntimeFrameworkVersion` один задаёт лишь минимум у framework-dependent приложения; строгий выбор требует отдельной политики. Это намеренное ограничение данного exact-executor контракта: автоматическое получение будущих security patches отключено, следующему patch нужна оперативная отдельная квалификация. Не рекомендовать такой pin как общий способ эксплуатации .NET. [Microsoft: runtime version / roll-forward](https://learn.microsoft.com/en-us/dotnet/core/project-sdk/msbuild-props#runtimeframeworkversion).
4. **Tests/dev host:** runtime серверного проекта не выбирает runtime чужого testhost. Запускать все содержащие сервер тестовые процессы и изолированный acceptance host из проверенного toolchain `10.0.14`; подтверждать действующий Framework внутри процесса. Не распространять pin на игровые mod/bridge runtime и не менять их загрузку. SDK/runtime `10.0.13` оставить только для отдельного legacy control, без смешивания output/cache и claims.
5. **Docker:** закрепить build image `mcr.microsoft.com/dotnet/sdk:10.0.403-noble` и server image `mcr.microsoft.com/dotnet/aspnet:10.0.14-noble`, зафиксировать реально разрешённые image digests в evidence. Fixed tag закрепляет .NET patch, но может получать обновлённые OS layers. Не менять qualified data/anchor storage и не выдавать overlayfs writable layer за проверенный ext4 backend. Общий Docker build SDK также нужно согласовать с `global.json` в `Dockerfile.discord`; это не расширяет квалификацию outposts на Discord. [Официальные SDK tags](https://github.com/dotnet/dotnet-docker/blob/main/README.sdk.md), [ASP.NET tags](https://github.com/dotnet/dotnet-docker/blob/main/README.aspnet.md), [политика tags](https://github.com/dotnet/dotnet-docker/blob/main/documentation/supported-tags.md).

Это воспроизводимость конкретного выпуска, не запрет пользователю устанавливать новые security runtimes параллельно. Не задавать глобальные `DOTNET_ROLL_FORWARD` или системный PATH; явные overrides runtime политики не являются поддержанным обходом квалификации. Переход на self-contained публикацию и новый установщик не нужны.

## Версия и полномочия

Реализация затрагивает production executor admission и runtime/deployment files; это новый исправляющий выпуск `0.9.2`, а не новая сборка под уже публичным `v0.9.1`. Сохранить `v0.9.0` и `v0.9.1` на прежних commit и не заменять связанные архивы другими исходниками. До прохождения gates новый release остаётся Draft. Такое решение следует выбранному пользователем сохранению опубликованной истории; техническое уточнение не выдаёт дополнительных полномочий на publish/deploy или включение Product.

**Ruling:** публичный путь — отдельная квалификация актуального security runtime `10.0.14` и согласованная воспроизводимая поставка; точная среда `10.0.13` остаётся инструментом legacy-проверки, а не способом скрыть несовпадение выпуска.

## Дополнение: main CI перед release tag и точное reuse

Сначала отправить candidate `0.9.2` в `main` **без тега**, дождаться полного Linux suite и Docker build/smoke именно его commit. До этого кандидат можно исправлять без перехода к `0.9.3`: публичного `v0.9.2` ещё нет. Затем создать `v0.9.2` на проверенном commit. Обычные branch/PR проверки сохраняются; активный main CI не отменяется ради запуска tag CI.

Повторное использование разрешено **только** внутри `build-test` для события `push` release tag. Checkout выполняется всегда; сравнивается полный commit SHA из `git rev-parse HEAD`, а не имя тега, tag-object SHA, текущая вершина `main`, ancestor или равный tree. В reuse входят только неизменённые SDK/build/test шаги; сам job остаётся выполняемым и должен успешно установить доказательство либо пройти обычную проверку.

Закрытые условия доказательства:

- GitHub REST возвращает source run workflow `.github/workflows/ci.yml` того же repository/workflow identity; `event=push`, `head_branch=main`, `head_sha` точно равен checkout commit, `status=completed`, `conclusion=success`, `id` отличается от текущего run. Repository и head_repository относятся к этому же репозиторию; PR, fork, tag, другой workflow, незавершённый/failed/skipped/cancelled run не подходят. Фильтры запроса не заменяют проверку полей ответа.
- Source run выполнил обязательный `build-test` и его Build/Test steps успешно, без `skipped` и `continue-on-error`; проверить jobs/steps именно выбранного `run_attempt`. Main-путь в данном commit никогда не использует reuse. Это запрещает цепочку «reuse результата другого reuse» и зелёный workflow без реально выполненного suite. Полный source workflow success также подтверждает обязательные main Docker jobs/smoke, предусмотренные этим commit.
- Build/test commands, runtime, sources и их настройки не имеют отдельного tag-поведения. Только Git ref и OCI labels не требуют повторения suite. Если tag меняет компиляцию, test selection, qualification input или runtime, данный reuse неприменим. Exact SHA не доказывает идентичность плавающей внешней среды; ранее заданные pins и собственный tag Docker smoke сохраняются.
- При отсутствии кандидата, неполном ответе, API/permission/JSON ошибке либо неподтверждённом jobs/steps результате выполнять обычные SDK/build/test шаги. Нельзя превращать ошибку поиска в `reused=true`, брать «последний зелёный» другого commit или подставлять ручной success. Достаточны job-scoped `contents: read` и `actions: read`; новые PAT/secrets и общая permission expansion не нужны.

Достаточно штатного REST поиска runs и проверки jobs; новый общий framework/cache/набор настроек не требуется. API поддерживает фильтры `branch`, `event`, `head_sha`, `status`; `exclude_pull_requests=true` лишь убирает массив PR из ответа и **не** доказывает event/fork exclusion. [GitHub: workflow runs](https://docs.github.com/en/rest/actions/workflow-runs#list-workflow-runs-for-a-workflow), [workflow jobs](https://docs.github.com/en/rest/actions/workflow-jobs#list-jobs-for-a-workflow-run).

В step summary записать `reused`, source run ID/attempt, URL и exact SHA; при fallback указать причину и фактический новый запуск. Не создавать фиктивный TRX, новый test count или утверждение «тесты повторно прошли»: ссылка ведёт к результатам source run. `docker` сохраняет `needs: build-test` и на теге самостоятельно выполняет build/cache, smoke и только после них разрешённую публикацию. Reuse unit-suite не заменяет проверку реально публикуемого образа и не меняет полномочия release/deploy.

Проверка самой новой orchestration логики узкая: exact successful main proof даёт reuse; иной SHA/repository/event/workflow, незавершённый run, skipped Test и API failure дают full run; branch/main всегда full. После одного успешного полного main CI tag run должен показать reuse того же SHA и собственный Docker результат. Не повторять неизменённые suites дополнительно «для уверенности» и не помечать эту спецификацию как уже выполненную проверку workflow.
