# Rimlink Wiki: полноценная двуязычная энциклопедия

Дата: 4 ноября 2026. Статус: направление одобрено пользователем («давай»); этот документ фиксирует границы следующей итерации. Реализация — основная сессия GPT-6.1 Sol; Astra — спецификация, план и один итоговый read-only review.

## Цель и исходное состояние

Пользователь считает [опубликованную wiki](https://asofwar.github.io/rimlink/ru/) пустой и маленькой. Нужен справочник, по которому можно самостоятельно играть, эксплуатировать сервер и участвовать в разработке, а не набор аннотаций и маркетинговая витрина.

На момент обследования HEAD 25b22d4: [главная](../../../wiki/ru/index.md) содержит 27 строк и три завершающие ссылки; [экономика](../../../wiki/ru/players/economy.md) — 29 строк; [backup/recovery](../../../wiki/en/admins/backup-recovery.md) — 26. Это симптомы, не метрика качества. [Manifest](../../../wiki/content-manifest.json) задаёт 45 пар с общим шаблоном usage/limits/related; [тема](../../../wiki/.vitepress/theme/style.css) меняет цвет и иллюстрации, но не рабочую ширину. Справочники уже объёмнее: их не следует раздувать ради одинаковой длины. Опубликованный RU HTML отвечает HTTP 200; текущая визуальная композиция в браузере в рамках проектирования не проверялась.

## Решение и альтернативы

**Рекомендуется:** сохранить VitePress 1.6.4, Vite 6.4.5, Node 24, локальный поиск, /rimlink/, /ru/ и /en/; развить содержимое, портал и DefaultTheme. Подтверждённый [механизм расширения темы](https://github.com/vuejs/vitepress/blob/v1.6.4/docs/en/guide/extending-default-theme.md) позволяет сохранить навигацию и чтение без нового приложения.

Только расширить CSS — дёшево, но не решает отсутствие инструкций. Переезд на новый движок — лишние риски URL, поиска и публикации без выигрыша в содержании. Оба варианта отклонены. Нет runtime backend, аккаунтов, интерактивного редактирования, внешнего поиска, аналитики и новых зависимостей без отдельного обоснования.

## Портал и чтение

- Режим **Read**, не landing page: короткое объяснение общей планеты и локальных колоний, применимость версии, видимый поиск, три маршрута «Играть / Запустить сервер / Разрабатывать» с конкретным результатом каждого.
- Следом — пошаговый быстрый старт с прямыми ссылками; каталог механик, сгруппированный по началу игры, миру/общению, обмену, взаимодействию колоний; эксплуатация и разработка; заметный блок «Что делать, если…». Каталог содержит все статьи, а не только три входные страницы.
- На 1440×900 первый экран показывает назначение, поиск, три маршрута и начало полезного каталога. Баннер не вытесняет их ниже первого экрана. Иллюстрация необязательна; она не считается содержанием инструкции.
- Общая оболочка использует доступную ширину до ориентировочно 1440 CSS px; читаемый текст 65–85 символов в строке, таблицы/схемы могут быть шире. На широком экране слева явно видны разделы, в статье справа оглавление; активная группа не спрятана. На мобильном — подписанное меню и локальное оглавление, без горизонтального скролла всей страницы.
- Светлая/тёмная темы, заметный focus, клавиатурный путь, skip link; обычный текст контраст ≥4,5:1. Таблицы и код прокручиваются в своих контейнерах. Основной текст и ссылки читаются без JS; поиск и интерактивное меню могут требовать JS.
- Портал строится из локализованных метаданных manifest, не из второй независимой копии каталога. Локализуются видимые подписи, accessible names, поиск, empty/error states, пояснения к схемам и alt, а не только заголовки.

Типы статей различаются: руководство имеет предусловия → действия → ожидаемый результат → ошибки/возврат; explanation — модель, границы и разбор примера; reference — поля, значения, доступ, побочные эффекты и ошибки; портал/FAQ/глоссарий — полноценные ответы и навигацию, не искусственные шаги. Word count и наличие трёх заголовков не принимаются за качество.

При независимом сценарии допустима новая пара feature articles. Старую страницу и все опубликованные anchors сохранять как полезный обзор со ссылкой на детали; не заменять одним redirect. Новые pageId/sections/navigation/search/sourcePaths добавляются одновременно в RU и EN.

## Источники, схемы и безопасность

Текущий код/валидаторы/контракты и версии важнее старых prose. [Игровое руководство](../../player-guide.md), [серверное](../../server-setup.md), [coop](../../shared-colony.md), [modpack delivery](../../modpack-delivery.md), документы конкретных механик — отправная точка, не источник универсальных гарантий. У delivery ещё написано upcoming 0.8.0; переносить эту устаревшую формулировку нельзя. Исторические verification остаются датированным свидетельством, не «работает всегда».

Не обещать passive outposts, захват территорий, автономный coop или абсолютное отсутствие потерь. Coop: один активный партнёр, хозяин онлайн, единственный автор канонического сейва. GOG runtime не верифицирован; подготовленный легально распространяемый modpack не содержит Core/DLC и требует разрешённого способа входа. Generation и save-write epoch различны. Никогда не советовать удалять recovery journals/outbox/lock, принимать изменившийся pin вслепую или обходить TLS в production. Примеры используют placeholders, не реальные токены/профили/сейвы.

Минимум четыре полезные двуязычные схемы: архитектура/владение состоянием, вход/modpack, передача через escrow/почту, save/recovery. Предпочтительны статические SVG/HTML с текстовым эквивалентом и понятным порядком чтения, без нового runtime diagram engine. Только реально доступные подтверждённые screenshots: источник/дата/версия/тип/редакция личных данных, RU/EN подписи. Иллюстрации явно обозначены; старый рисованный marketing gallery не считается игровым снимком. Отсутствие genuine screenshots не блокирует честную wiki и не оправдывает подделку; не запускать чужие игры ради кадров.

## Контроль полноты и приёмка

1. Для всех 45 исходных pageId плюс новых пар в manifest задаётся тип и компактный coverage: именованный вопрос/сценарий, собственный anchor и точный source path. Автомат проверяет существование/структуру/парность, редактор сверяет смысл RU/EN и факты; флажок coverage не является доказательством качества. Непокрытые сценарии — открытый дефект, не заполнитель текста.
2. Пользователь проходит из портала к любой статье не более чем за два перехода; installation, backup, wallet и coop доступны напрямую. Browser assertions подтверждают видимость быстрых маршрутов и каталога, активное меню и работающие ссылки, а не один h1. Для шести ключевых путей (первый вход, trade, live/coop, modpack recovery, backup restore, build) обе версии отвечают на каждый шаг и безопасный отказ без чтения исходников.
3. Ноль пропавших legacy URLs/anchors, внутренних deadlinks, непарных страниц/revisions, отсутствующих reference записей и непокрытого source drift относительно явной базы. Существующие checks не ослабляются ради нового контента. Semantic review отдельно от структурных PASS.
4. Обе локали: 360/768/1440 CSS px, light/dark; портал, глубокое руководство и широкий reference. Клавиатура, focus, no-JS reading, deep-link reload и same-page language switch с hash; поиск ≥10 предметных запросов на язык, top-5 целевой результат, отсутствие смешанных языков, ё/е, пустая выдача. Нет runtime errors, утечки секретов и неожиданных внешних запросов.
5. Один итоговый whole-change review и один fix pass Sol; отчёт с матрицей coverage, фактическими командами/результатами, визуальными evidence и честными ограничениями. Docs-тесты не доказывают игровой runtime, GOG или восстановимость production.

## Публикация и границы

По сообщению основной сессии, GitHub Pages уже работает через legacy gh-pages, пользователь разрешил обновить wiki. Это не разрешение сменить Pages source. [Текущий deploy workflow](../../../.github/workflows/wiki-deploy.yml) рассчитан на Actions, а [maintenance README](../../../wiki/README.md) ещё описывает unpublished/Actions; основная сессия подтвердила замену этого manual-only workflow на сборку и выдачу проверенного artifact без deploy-pages и write-прав. Исполнитель сверяет фактическую конфигурацию и приводит инструкции к реальному ручному пути; публикация dist в gh-pages остаётся отдельной операцией. Публикуется только проверенный build выбранного commit, с сохранением старого артефакта/commit для возврата и smoke RU/EN после deploy. Автодеплой по push не добавлять.

Astra создаёт только этот документ и план. Маркетинг, чужой AGENTS diff, passive-outposts и modpack verification не изменяются. Следующие расширения (новые page IDs, наличие genuine кадров) решает Sol по выявленному содержанию и фиксирует; смена движка, платные услуги, новые игровые возможности и смена hosting route — вне этой итерации.
