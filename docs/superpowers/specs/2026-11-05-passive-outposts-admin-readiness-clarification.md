# Passive outposts: admin controls and acceptance readiness clarification

**Status:** bounded mechanical clarification of approved Task 15; not an implementation, code review, final branch review or acceptance receipt. All tests below are proposed and **NOT RUN** in this documentation task. Gameplay, prices, limits, custody ownership and restore policy are unchanged.

**Authority:** [original specification §§5.2–5.3,7,9–11](<2026-11-03-passive-outposts-design.md>), [Task 15 and Task 16 / G1–G7](<../plans/2026-11-03-passive-outposts.md#L378>), [ordinary return clarification](<2026-11-04-passive-outposts-ordinary-return-clarification.md>), [lifecycle clarification](<2026-11-04-passive-outposts-lifecycle-clarification.md>) and [bulk restore clarification](<2026-11-04-passive-outposts-bulk-restore-clarification.md>). ## 1. Already approved constraints

- Admin UI, REST and CLI expose the same manifest confirmation, recovery status and archive/reset/backup preflights. Manual resolution selects existing proved transitions with actor/reason and append-only evidence; it is never an instruction to issue another copy or edit immutable snapshots/blobs/receipts.
- No-removal requires the continuous cancellation-fenced branch and its exact accepted NoRemoval snapshot with original live pawns. An old pre-save, absent Removed flag, operator assertion, timeout or cold reload is not that proof. Accepted removal can select the existing one-batch return. Committed wins over cancellation; existing terminal outcomes remain terminal.
- Ordinary positive business receipts, original request/local IDs, derived live→raid route and permanent negative-return fences survive cleanup, accepted return, closure, archive, rollback and restore. Unknown is not a negative proof; historical result inspection is not a new replay/spawn authorization.
- Locks remain A→sorted O→S→Live→T. Protected mutations use external Pending→main DB domain/transition/head→external completion, then publish. All retired-world real source/parcel/snapshot bytes and original world/owner/generation/epoch/boundary/id/hash remain required evidence.
- Physical provisioning is an explicit qualified maintenance operation. Logical initialization requires positively empty feature history and an already qualified NULL anchor. Missing/corrupt anchor with history, FreshFence, BackedOutEmpty, unfinished lifecycle or restore cannot be repaired by Initialize. Bulk restore/Resume/Backout remain explicit stopped-server procedures, not web actions.
- Config, admin role, completed schema migration or successful unit/RPC/private builds do not establish readiness. Product capability stays OFF until the complete integration graph **and Task 16 acceptance**. G1–G7 must exercise actual isolated clients; an unavailable case is NOT RUN/blocked acceptance, never an implicit waiver.

## 3. Bounded DTOs, observation and exact intent

**Types live with the planned admin contracts/codec files listed in Task 15; the following is a data contract, not source code.** IDs keep their existing exact spelling; no trim/case-fold/rebinding of historical identifiers. Request IDs are UUID D; SHA-256 values are exactly 32 bytes (REST representation: 64 lowercase hexadecimal characters). The actor comes from the authenticated transport, never from body fields.

| DTO | Required meaning |
|---|---|
| OutpostAdminQuery | Optional owner/operation filter, page size 1..100 (default 50), opaque bounded continuation. No filesystem path or arbitrary SQL selector. |
| OutpostAuthorityObservation | Tagged Committed(installation,world,boundary,head ID+digest, chain-proved domain format, separately verified actual schema profile), Uninitialized(world,binding/qualification digest), or Unavailable(reason,known partial facts). No fabricated empty/Genesis committed head. Pending/FreshFence/maintenance facts are diagnostic and not a Committed mutation precondition. |
| OutpostAdminView | Observation and observation digest; startup/history state; readiness decision and blocker codes; bounded operation/custody/parcel/manifest summaries; exact evidence references and Missing/Corrupt/Unsupported/Verified states; safe available-action descriptors. Stable continuation is bound to the observation; a changed cut restarts the page instead of silently merging cuts. No pawn blobs, save XML, auth data, arbitrary paths or full private file contents. |
| OutpostAdminIntentDraft | Tagged Initialize / ActivateDomainFormat / ConfirmManifest / Resolve, request ID, nonblank audit reason, exact selected IDs and original proof references. Resolve also names operation family, original request kind+ID, original intent digest and scope; ordinary captures additionally retain local ID and any derived route. |
| OutpostAdminPreview | Exact typed action, authenticated actor identity, expected authority observation, selected evidence inventory/digest, expected operation revision/state, bounded effect summary, canonical intent bytes digest, eligibility and typed blockers. Preview is advisory, not a reusable authority grant. |
| OutpostAdminCommand | The same frozen draft, expected authority observation and exact preview intent digest; explicit confirmation. No force, guessed absence, new payload, destination-owner edit, replacement scope, balance input, arbitrary transition kind or code. |
| RecoveryResolutionResult | Discriminated OutpostOutcome / OrdinaryOutcome / CanonicalDownloadRequired / RecoveryRequired, with command receipt ID, original operation/result references and resulting authority head where applicable. OrdinaryOperationReply is never disguised as OutpostOperationReply; historical outcomes explicitly carry NoReplayAuthorization. |

Technical limits for this new admin control plane: reason 1..1024 UTF-8 bytes (nonblank, no NUL/control characters); at most 64 selected evidence references; canonical command at most 64 KiB; at most 100 rows and 1 MiB serialized per inspection page. Larger proof graphs are resolved server-side using existing evidence budgets, not embedded in requests or truncated into an absence claim. Existing 24 MiB manifest / 256 KiB chunk limits and existing metadata/graph limits are unchanged. Limit/malformed errors are typed and produce no partial action.

Canonical digest encoding is a versioned domain-separated, length-prefixed UTF-8/binary format with fixed field order and explicit union tags, not host-default JSON or concatenated strings. It covers authenticated actor identity, request ID, action, exact reason, expected observation/head, original scope/kind/intent, all selected ID/hash/transition-digest references, revision, proposed effect kind and manifest ID/revision/digest when relevant. Sort only declared set-valued collections; preserve order where it has meaning. Freeze all caller buffers before awaiting. Missing optional facts are tagged missing, never empty hashes.

Inspect and Preview acquire a consistent read fence and perform **no domain, anchor, file, checkpoint or audit mutation**. Do not use a reconciliation-writing Open as a supposedly read-only GET. If normal qualified observation cannot safely open a hot/missing/corrupt store without mutation, report unavailable/maintenance; do not auto-recover/provision. A stopped server is unreachable, not RequiresInitialization: CLI directs the operator to the approved offline inspection/recovery procedure rather than starting a permissive web host. Readiness and candidate discovery do not run production settle.

## 4. Commit, audit and the closed resolution catalogue

Mutation authorization is Admin scope plus the existing service-level Admin role. Under the complete discovered/rechecked owner set and A→O→S→Live→T, re-read authority, operation, immutable proofs and current canonical IsCurrent snapshot. Recompute the command/evidence digest; compare expected head ID **and** digest, exact original scope, operation kind/intent/revision and current preconditions before any side effects. A stale command has no effects and requires a new preview; the UI/CLI cannot auto-confirm a refreshed digest. Client cancellation after durable Pending never causes compensation or a final rejection that permits a local return.

Use one protected append-only admin command receipt for successful Initialize/ActivateDomainFormat/ConfirmManifest/Resolve. The planned OutpostAdminCommandRecord stores the versioned immutable command+digest, authenticated actor/reason, original result/evidence references, operation transition ID and bounded durable result. Protect this table through the explicitly activated v2 domain format and stored-evidence validation in §10; add the normal additive EF migration/schema test. NEVER append it to the frozen v1 table array or infer the format from whether the table is empty. Stage its row and AdminAudit row in the **same** main DB transaction as the selected existing effect (or an audit-only protected resolution recording an already terminal result); do not modify an original gameplay request/intent to smuggle in admin fields. The audit row is an index, not an independent custody authority. Allocate receipt/transition/next-head IDs before staging; the protected receipt stores semantic outcome and references, not its own resulting transition/head digest (which would create a hash cycle). Derive that digest for the response from the immutable committed transition. Initialization stages the receipt after empty-history checks but before computing the initial protected effects digest; it never pre-creates history as a preview.

Idempotency key is authenticated actor identity + admin action kind + request ID. After current authorization/scope checks, exact recorded intent replay returns the prior administrative result without another effect, receipt, head or audit entry; different bytes under the key are IntentMismatch. The request retains its original expected-head/digest on replay: match the stored complete command, not a newly recomputed preview. If today's scope/boundary no longer permits its execution, only read-only historical inspection is allowed. Unfinished external completion does not become a successful response by reading a DB-only receipt. Failed/stale attempts may be diagnostic logs, never a successful resolution receipt or authority proof.

| Resolve choice | Required proof and allowed effect |
|---|---|
| ExistingTerminal | Exact persisted committed/cancelled/accepted outcome and transition/source linkage. Record selected evidence and return that outcome; do not recall, reissue, refund or clear fences implicitly. |
| AbortNoRemoval | Operation already has its protected CancelFence and the matching accepted NoRemoval attestation from the original continuously fenced branch, exact current canonical proof/live pawn registry and all existing cancellation checks. Only then execute the same AbortNoRemoval effect. Admin cannot manufacture the continuous branch, create a fence on behalf of an unknown cold game, or infer proof from a pre-save. Otherwise RecoveryRequired with artifacts/reservations retained. |
| AbortWithReturn | Exact accepted post-removal receipt, matching original operation/custody and existing cancellation guards. Execute the existing one-batch return and reserve release once; committed/terminal outcome wins a race. No separate local refund/clone. |
| OrdinaryReturn | Re-run the existing positive-source resolver including derived routes, both exact removal/canonical proofs, current IsCurrent branch, tombstone/custody checks and original payload digest. Applied returns its known outcome; only proved negative eligibility can execute the existing OrdinaryReturnStarted authorization and permanent request/derived-route fence. Never convert Unknown/status-read into a grant or delete a fence after Accepted. |
| CanonicalDownload | Select only the exact already authorized current canonical snapshot and its existing rollback/restore provenance from Tasks 13–14. Administrative result is a download/reconciliation requirement, not a payload/spawn grant. The normal authenticated owner download verifies bytes and existing bridge, then requires a fresh accepted capture before new mutations. No new epoch/boundary, bridge policy or historical snapshot rewrite. |

No other choice is admitted. Ambiguous source/branch, missing evidence, unsupported graph, Prepared/Started without proved outcome, old session or foreign scope stays RecoveryRequired. A property-moving resolution requires the complete recovery integration graph and the qualified product or isolated-acceptance composition (§7); Enabled=false is not permission to weaken retained-history fences. Safe inspection and empty-history initialization do not imply that recovery/gameplay is available. No new generic admin 'resume production', 'clear SafetyHold', 'force delivery' or destructive journal replay is introduced.

## 5. Initialization and manifest flow

Initialization uses a tagged **Uninitialized observation**, not expectedHead=null interpreted as a wildcard. Bind the current world/configuration digest, positive empty-history result and observed qualified physically provisioned NULL store into the preview. Recheck under A/S immediately before the existing initialize transaction. Any history, non-NULL/FreshFence/BackedOutEmpty envelope, changed world/qualification, missing store or unsupported backend refuses; only the approved stopped provisioning/recovery path can address storage problems. New generated installation/boundary/head and the admin receipt are persisted together and returned after external completion. Caller-supplied Actor is not trusted. New initialization explicitly binds domain format v2 under §10; legacy Initialize records remain byte-exact v1. Logical initialization does not set acceptance/readiness/capability.

Manifest export remains a main-thread export from the administrator's actual correct game world. Upload uses the existing bounded authenticated chunk assembly, binding and digest validation; it stages an immutable document under authority, it is **not** a read-only preview endpoint. Inspection of a staged document exposes world/params/surface/tile coverage, game/defs/server catalog/modpack/DLC fingerprints, valuation/revision/digest, affected preparations/outposts and predicted compatibility/SafetyHold reasons. No server-side terrain generator or trusted client claims are added.

Confirm preview and commit bind the staged ID+revision+digest, world binding, expected authority head, affected-state/evidence digest and audit reason. All affected owners are rediscovered/rechecked under the existing barrier. Call the same manifest validation/settle/hold rules as the game-admin path; preserve Q/F, original inputs/provenance and checkpoint where the existing maintenance rule requires a hold. Unknown biome/def/surface, wrong world, incomplete/duplicate/conflicting coverage or stale preview fails closed. Confirm never resumes a hold by guessing elapsed time and never enables capability. Existing game-admin manifest confirmation must use the same command validation/audit path (additive protocol fields if needed); REST/CLI are not a weaker parallel route. Initial empty-history catalog setup can precede product acceptance; changing a catalog affecting custody requires the complete qualified recovery graph.

## 7. Noncyclic readiness and isolated acceptance composition

### 7.1 Product gate

OutpostReadiness.Evaluate(OutpostReadinessInputs inputs) → OutpostReadinessDecision is pure and returns Mode, ConfiguredEnabled, IntegrationStates, BuildQualification, StartupState, DomainFormat, CurrentSchemaVerified, AdvertiseCapability, CanResolveCustody, HistoryProtectionRequired and stable blocker codes. Integration states are Implemented/Unavailable/Unknown for the fixed safety graph: qualified authority/domain/files, exact metadata/registry/receipts, admission/cancel, typed delivery/wealth, ordinary source/return/negative fences, live/raid/coop ownership, archive/reset/rollback, coherent backup/bulk restore/nested provenance, compatible game/core callbacks and admin audited parity. DI registration or schema presence alone cannot set Implemented; supported contract revisions are a code-owned inventory qualified by the corresponding tests/evidence. Unknown fails closed.

Build qualification is a read-only code/build-owned artifact: Pending until Task 16's required automated, platform, real G1–G7 and whole-branch acceptance/fix verification are evidenced. It binds the supported safety-contract/source build identity and evidence references. No endpoint, options binder, environment variable, data directory file, imported backup, admin receipt or UI checkbox can write it. Task 15 ships Pending. The qualification schema, evaluator, build-only sealing step and candidate evidence record are included in the single whole-branch review. Only after Task 16's actual acceptance, that review/fix pass and required re-verification may the build step seal Qualified for the verified safety-source content identity; ordinary builds or incomplete records remain Pending. The seal is an embedded build artifact, not a new runtime setting or an unreviewed change of gate logic, and is excluded from its own source-identity digest to avoid a self-hash cycle. The isolated stand uses the pending artifact until then. No automatic publication/deploy follows; the build receipt is release qualification evidence, never custody authority. Pending/failed/unknown mandatory case keeps product OFF; changing relevant safety implementation invalidates qualification until its required evidence is re-established.

Product AdvertiseCapability requires ConfiguredEnabled AND complete integrations AND qualified build AND startup Ready AND chain-proved domain v2/current-schema verification (§10). Manifest eligibility remains an operation-specific guard, not a reason to conceal the initial export workflow. CanResolveCustody requires complete qualified recovery integrations, Ready and the same v2/current-schema verification even when new gameplay is configured off; it never bypasses current scope/evidence. Read-safe inspection and explicit empty-history setup are separate abilities, not capability. NoActiveWorld remains host/admin-only, Maintenance/unfinished restore/lifecycle blocks ordinary startup/hosted writers as before. Retained history is protected regardless of Enabled/qualification; incompatible/legacy clients cannot erase metadata or receive unsupported payload, while proved unrelated legacy colonies retain 0.8.1 behavior. Login advertisement, every game mutation/delivery admission and startup/hosted-writer admission consume this same decision at their appropriate boundary, not cached user-controlled flags. Do not relax exact proof checks to make a disabled build appear usable.

### 7.2 G1–G7 without enabling product

Create a separate **dev-only** tools/Rimlink.OutpostAcceptanceHost project/composition, excluded from ordinary server/CLI published artifacts, Docker/release packaging and automatic startup. It runs the **same** server application services/routes, storage/backend qualification, options validation, authorization, schema and game protocol, but supplies a nonserialized IsolatedAcceptance build-qualification provider through an internal test/composition seam. The normal Program path supplies only Product/Pending-or-qualified and never resolves that provider from configuration, assembly scanning, environment, HTTP, database or plugin input. Do not add an ordinary --allow-unaccepted, Development-mode or Enabled override, reflection write to IsAvailable, alternate safety implementation or fake authority. A narrow extraction of shared host composition is allowed; duplicating the production host is not.

The dev provider waives **only the circular requirement that the Task 16 product acceptance/review seal already exist for this owned run**: G1–G7 supply evidence for that seal, and the final review follows them. All implementation and available automated prerequisite gates still apply; neither G acceptance nor final review is waived for the eventual product. It never waives a missing integration, runtime authority/readiness, backend profile, client version, exact evidence, actor, manifest, lock, restore fence or ordinary-return check. Its state remains IsolatedAcceptance/NOT product accepted. On this endpoint the normal protocol capability can be advertised to exercise actual game clients; the simultaneously ordinary product composition remains OFF. The dev executable/UI/log/verification record must identify this distinction. No dev qualification is persisted in the DB, anchor, backup, bridge or user config, and copying its data to an ordinary build cannot open that build's gate.

Before starting (Task 16 only, after separate execution permission), require an explicit owned stand descriptor: canonical separate DataDir, anchor outside replacement trees, backup/archive roots, loopback-only bound endpoint/unique port, two owned game IDs, distinct -savedatafolder roots and local compiled mod/companion paths. Verify no overlaps/reparse aliases with each other or production/shared directories, qualified filesystem profile, locks/ownership and no ambiguous existing foreign state. New standalone data or an explicitly inspected copy prepared for this isolated stand is permitted; do not silently import a production install/anchor or copy auth settings. Listener/config changes and launch/restart revalidate isolation; failed/unknown isolation refuses before hosting, not falls back to Product or weaker fencing. No shared games, broad listening socket, MCP configuration mutation or automatic process termination is authorized by this design.

Use that composition throughout G1–G7, including normal restart and explicit stopped restore/Resume/Backout of the owned host; it still exercises the real filesystem and original fault boundaries. Record dev composition identity, server/core/game/bridge build identities, runtime storage profile, exact game counts/UUIDs/snapshots/heads/parcel IDs and each required fault-point result. No missing G-case is auto-filled. Task 16 includes the qualification candidate and sealing logic/evidence in the one final branch review/fix/handoff; only after that acceptance is complete may it seal the ordinary product artifact for the same verified safety implementation and verify product-gate/packaging behavior. No extra runtime API or post-review gate-code edit is required. This is not authorization to turn on any real deployment or publish a release.

## 10. Domain-digest compatibility and explicit activation

### 10.1 Existing seam and selected ruling

The [v1 digest](<../../../src/Rimlink.Server/Application/Outposts/OutpostDomainDigest.cs#L22-L68>) commits a **fixed ordered 12-table inventory**, the DomainDigest/v1 tag, table count, exact SQLite table SQL, column descriptors and ordered typed rows; [definition reads](<../../../src/Rimlink.Server/Application/Outposts/OutpostDomainDigest.cs#L118-L147>) reject missing definitions. Adding even an empty table changes the hash. [Chain validation](<../../../src/Rimlink.Server/Application/Outposts/OutpostAuthority.cs#L350-L404>) currently compares the tip's raw Effects with this hash. [Historical-cut validation](<../../../src/Rimlink.Server/Backup/OutpostRestoreProcedure.cs#L273-L294>) shares the same computation. §§4–5 alone did not define the upgrade: this is a real **format seam**, not evidence that a legitimate old head is corrupt.

**Selected minimal ruling:** freeze v1; introduce v2 and one explicit authenticated **DomainFormatActivated(1→2)** transition. Derive the effective domain format by folding the validated immutable chain, never by scanning for receipt rows. A new typed Initialize binds v2 directly. A newly created restore from a v1 cut binds C/v1→R/v2 in its versioned restore intent, without inserting a fake predecessor. This changes encoding/schema admission only, not ownership, clocks, replay, authority source or recovery policy. Automatic migration alone never activates it; this is not Initialize, repair, a force option or a new Resolve outcome.

### 10.2 Two formats, two schema contexts

- **Domain v1** is exactly the current 12-table list, order, tag, writer and byte semantics. Keep its vectors, legacy Initialize/transition/manifest codecs and Genesis unchanged. New code must not edit old Effects/Digest/Intent, normalize old SQL, backfill receipt rows or add format columns to the 12 protected tables. Authority/anchor envelope FormatVersion and RLOTRANS version are different protocols; do not reinterpret either as DomainFormat.
- **Domain v2** uses the same bounded typed writer with tag Rimlink.Outposts.DomainDigest/v2 and a fixed count of 13: the exact v1 inventory followed by outpost_admin_commands ordered by Id. Include its actual table definition, all column descriptors and every row even when zero rows exist. The normal Task15 migration creates only the additive command schema/required indexes and migration bookkeeping; it leaves all original protected definitions/data untouched. A migration needing to rebuild/alter one of those 12 definitions needs another explicit versioned plan, not a v1 normalization exception.
- Use the finite code-owned exact schema-profile catalogue in §10.7: complete supported migration lineage plus the corresponding full actual catalog, including every table definition/constraint/index/trigger, with an immutable profile identity/digest. CRLF and LF are distinct observations, never interchangeable spellings of one profile. Actual catalog checks and migration lineage must agree; an EF history entry alone is not proof that a table exists or has the correct shape. A profile is not caller-authored SQL and cannot be selected by environment/config/row count. Current schema admission also rejects views/shadow tables or unapproved triggers in place of the required table. Table SQL committed by v1/v2 remains byte-exact, not replaced by the profile hash.
- **CurrentRuntime** always requires the actual supported migrated schema, including the new table, before ordinary startup or admin activation. A persisted applied migration with a dropped table, missing mandatory migration, partial/wrong schema or unknown future schema is SchemaUnavailable/Unsupported and stops; never silently create an empty table to cure it. Normal pending additive EF migration remains the approved startup DDL operation, not an authority repair. It changes no head or domain-v1 digest. A healthy already-migrated v1 head is reported as FormatActivationRequired, **not corrupt**: allow only bounded admin inspection/preview and explicit activation, with ordinary hosted domain writers, save/admission/delivery and gameplay closed. Preserve NoActiveWorld as a separate existing restriction; activation does not create a world.
- **HistoricalCut** is a separate, query-only context for an exact manifest/file-digest-identified source/cut. A proved legacy v1 chain plus a recognized pre-admin schema profile may genuinely lack outpost_admin_commands. A recognized post-migration but pre-activation v1 cut must instead contain its correct **empty** table. Both use the frozen v1 computation. In either case, validate the entire selected prefix, original v1 domain equality, proof inventory/file closure and schema lineage; unknown/missing base tables are not an empty old database. No EF migration, table creation, WAL/journal repair, schema normalization, hidden temporary replacement or synthetic v2 manifest is allowed in read-only inspection. New-table readers are dispatched only after this admission, not called and swallowed on SQL failure.

The pre-activation empty-table check is a **consequence** of a fully authenticated v1-only prefix and supported schema profile, not how the format is chosen. Any admin command row under a v1 prefix is inconsistent and refuses. Once the selected prefix proves v2, an absent/empty/altered table never selects v1. Old bytes can be inspected as old evidence, but that historical context cannot be passed to a live writer or used as a fallback after a current-schema failure.

### 10.3 Immutable format binding and activation transaction

Chain validation first authenticates predecessor/digest links and typed identity/lifecycle/restore binding, then carries a DomainFormat state. The only format-increasing edges in this release are the exact DomainFormatActivated payload and the explicit versioned restore binding below. Reject 2→1, repeated 1→2 while already v2, unknown versions, unsupported profile, claimed activation on an ordinary kind, or an inconsistent embedded format. Every new command receipt must have a typed successful command/transition backlink and protected audit projection; every such transition requires its receipt. This closure, including the activation receipt, is verified even if a malicious edit empties the whole table. Mutable authority-row flags, local options, table presence, a DB-only audit entry or a backup label are never format authority. Rewinding/deleting the activation chain to an old valid head still mismatches the real external committed head; the supported threat model does not claim resistance to forging both independent stores.

Do not settle as a side effect. Missing/corrupt/foreign authority is not an upgrade candidate. Config Enabled and the isolated acceptance provider cannot skip this gate.

Under A→sortedO→S→Live→T, recheck all evidence and the exact expected head ID+digest. Compute the old v1 digest before staging the receipt and require equality with the existing tip. The next head is new; old head/Genesis/prefix bytes are not rewritten. No own next-head/Effects digest goes inside its protected receipt, so there is no hash cycle.

Crash before DB commit leaves the old valid v1 head and empty new table; Pending+old DB follows the existing verified no-commit reconciliation, not blind re-execution. Crash after DB commit validates the new v2 tip, receipt/schema/proof closure and exact Pending tuple before completing the external write. Inspect/Preview never clear Pending or activate. Reaching v2 makes only this blocker disappear; Task16 qualification and all other readiness gates remain mandatory.

No synthetic v1 initialization followed by automatic upgrade, and no lost-anchor bootstrap. Preserve the original Genesis constant; changing the first **new** Initialize bytes does not change any **old** Initialize.
