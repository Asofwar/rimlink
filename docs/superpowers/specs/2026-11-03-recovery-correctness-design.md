База: `404a67edd62e4114046500f3e0eab7ff4e306abb` (main/v0.8.0).

## Область дополнения

Это узкое уточнение существующих `2026-10-28-rimlink-core-design.md`, `2026-10-28-rimlink-economy-design.md`, `2026-10-29-rimlink-live-design.md`, `2026-10-29-rimlink-safe-trades-design.md` и `2026-11-02-save-generation-design.md` в этом каталоге. Оно заменяет их решения о достаточности игрового тика для восстановления, моменте журналирования/возврата и порядке выдачи modpack diff. Новых продуктовых возможностей нет.

Нумерация аудита: #1 повторная доставка после восстановления local save; #2 окна outbox/возвратов; #3 атомарный возврат live escrow; #4 отмена rollback клиентом; #5 потерянный pending; #6 перестановка uploads; #7 одинаковый тик доставки и сейва; #8 глобальные request IDs; #9 настройки до server password; #10 восстановление, зависящее от Wallet.

## Инварианты

- Удаление имущества из колонии, его прием сервером и возврат различаются долговечными доказательствами. Отсутствие ответа не означает отказ.
- Игровой тик — время симуляции, не идентичность сейва и не доказательство наличия предмета.
- Новый snapshot ID относится к одним неизменяемым байтам XML. Его metadata, receipts и hash читаются из этих же байтов, включая pending/direct upload.
- Старый upload не отменяет административный rollback. Старый локальный файл не получает новую идентичность колонии или разрешение записи из login.
- Неудача Wallet не останавливает mailbox, raids, incidents, social и live recovery.
- Исторические данные без доказательств не объявляются доказанными. При неоднозначности сохраняются файл и journal; автоматические повторное списание/возврат запрещены.

## Совместимые расширения протокола

Номера проверены по protobuf базы выше; перечисленные поля свободны. Перед реализацией сверить текущие изменения Sol. Только добавления; `ProtocolVersion.Current` не менять.

| Сообщение | Добавления |
|---|---|
| `SaveHeader` в `saves.proto` | `string snapshot_id = 10`; `int64 save_write_epoch = 11`; `uint32 recovery_version = 12` |
| `SaveInfo` | `string snapshot_id = 6`; `int64 save_write_epoch = 7`; `uint32 recovery_version = 8` |
| `SaveRolledBack` | `int64 save_write_epoch = 2`; существующий event body 42 не менять |
| `DeliverRequest` в `economy.proto` | `string snapshot_id = 3`; `int64 save_generation = 4`; `int64 save_write_epoch = 5` |
| `LoginRequest` в `auth.proto` | `uint32 recovery_version = 7` |
| `RegisterRequest` в `auth.proto` | `uint32 recovery_version = 6`; `string server_password = 7` |
| `LoginReply` | `int64 save_write_epoch = 13`; `uint32 recovery_version = 14` (поддерживаемый сервером контракт) |
| `ErrorCode` в `common.proto` | 67 `SAVE_WRITE_EPOCH_MISMATCH`; 68 `RECOVERY_CLIENT_REQUIRED`; 69 `REQUEST_INTENT_MISMATCH`; 70 `RECOVERY_REQUIRED` |

`recovery_version=0` означает legacy, 1 — этот контракт, в том числе пустой набор receipts. Неизвестный формат не считать legacy. Snapshot ID — GUID в формате N; числовые идентификаторы положительны, коллекции без дублей. Ошибки содержат локализуемые EN/RU ключи. `RECOVERY_REQUIRED` не является основанием очистить outbox или вернуть имущество. Для legacy-клиента неоднозначный replay отвечать временным gRPC `Unavailable` без нового definitive detail: старый `IsDefinitive` считает почти любой ErrorCode окончательным.

Новые mutation-поля для всех видов передачи не требуются: доказательства списания привязываются к существующему outbox ID в XML и проверяются клиентским coordinator перед отправкой. Аутентификация и серверная идемпотентность остаются обязательными; это восстановление штатного клиента, не защита от владельца модифицированной игры.

## Снимок, pending и rollback (#4–6)

Существующий `RimlinkGameComponent` сохраняет вместе с колонией: формат восстановления, snapshot ID, `SaveGeneration`, `SaveWriteEpoch`, набор полученных parcel ID и отметки исходящих операций `Removed/Returned` по стабильному outbox ID. Отметки сохраняются вместе с соответствующими изменениями игрового состояния. Чужая карта visit/mirror не пишет историю собственной колонии.

`SaveGeneration` сохраняет контракт reset: reset/новый мир отделяет новую колонию. Rollback не меняет ее generation и согласие guild influence. Новый `Player.SaveWriteEpoch` (начально 0) монотонно увеличивается при успешном rollback под `SaveFiles.PerStoreLock`, в транзакции выбора текущей версии. Обычный reconnect и архивирование/восстановление той же колонии epoch не увеличивают. Reset продолжает отказывать по generation; epoch никогда не уменьшать при restore архива.

Перед записью собственного сейва атомарно сохранить намерение pending с новым snapshot ID и generation/epoch; оно покрывает падение между записью .rws и postfix. После успешной записи захватить неизменяемую локальную копию, прочитать metadata из нее, вычислить hash и атомарно связать pending с копией. Если игра проглотила ошибку SaveGame, старый файл с другим snapshot ID не признавать новым. После падения в промежутке копия восстанавливается из основного .rws только при совпадении ожидаемого ID. Использовать существующие приемы temp + flush + rename; не удалять прежний пригодный pending до закрепления нового.

Один активный uploader на сессию. Он получает конкретный snapshot и возвращает результат именно этого snapshot, а не общий `LastError/LastVersion` последнего задания. Очередь сохраняет порядок; снимки, обеспечивающие переход outbox, нельзя пропустить при объединении обычных автосейвов. Успех A не очищает pending B. Поздний callback завершенной/замененной сессии не меняет новую сессию и ее marker. Обычный network failure сохраняет pending; rollback/replaced переводит старые артефакты в сохраненное, но не отправляемое состояние.

Сервер после приема потока и под store lock повторно читает generation/epoch, проверяет сессию и соответствие header данным XML, затем фиксирует версию. Проверка recovery metadata должна дочитывать ограниченный XML до конца: текущий `SaveValidator` возвращает успех уже на player faction. Извлекать только собственный компонент по структуре XML, не одноименные узлы других модов. Соблюдать существующий предел распакованного сейва, запрет DTD и fail-closed для поврежденной metadata.

В `SaveVersion` сохранять snapshot ID, формат, исходные generation/epoch, raw XML hash и извлеченные receipt/operation metadata. Повтор тех же байтов под тем же ID возвращает прежнее подтверждение без новой версии и без изменения текущей версии; тот же ID с другими байтами отклоняется. Raw hash не зависит от повторного zstd-сжатия при compaction. Идемпотентный upload не проходит через более новый write epoch.

Доверенный `Download` возвращает выбранные байты с проверяемым size/hash и текущим разрешенным epoch в header; это единственное исключение из равенства epoch header/XML старого выбранного сейва. Клиент применяет этот epoch к загружаемой собственной игре через результат конкретного проверенного download, связанный с hash/ID файла. Он не переписывает старые pending-файлы и не берет epoch из общего login. Следующий сохраненный снимок уже содержит новый epoch. `DownloadOf` не дает право записи собственной колонии.

Уведомление rollback немедленно блокирует исходящие изменения старой игры. Выход не сохраняет ее; pending и старые журналы сохраняются отдельно для диагностики, без replay в новой ветви. Если уведомление пропущено, серверный epoch все равно отвергает старый upload. Проверять обе очередности гонки: upload до rollback допустим, но затем выбранная версия становится текущей; upload после rollback отклоняется.

## Долговечный outbox (#2)

Расширить существующие `OutboxEntry/TransferOutbox`, без отдельного transaction framework. Новая запись хранит payload, kind, собственный ID, generation/epoch, фазу и идентичность подтверждающего snapshot. Денежные операции только с wallet, не меняющие карту, могут сразу быть Ready.

| Фаза | Разрешенное поведение при восстановлении |
|---|---|
| `Prepared` | Payload сохранен до необратимого снятия вещей/пешек. RPC запрещен. `Removed(id)` в выбранном долговечном сейве означает, что нужно обеспечить upload именно этого состояния; подтверждение переводит в Ready. Если в выбранном холодном снимке нет отметки, исход неоднозначен: перевести запись в RecoveryRequired и сохранить payload для ручной сверки; не удалять запись и не создавать возврат по предположению. |
| `Ready` | Списание доказано принятым snapshot; повторять неизменный запрос с прежним client_request_id. Успех позволяет очистить entry, окончательный отказ с имуществом атомарно переводит в Returning. Временный отказ сохраняет Ready. |
| `Returning` | Сохранить этот статус до возврата. Если выбранный сейв уже содержит `Returned(id)`, второй возврат запрещен. Иначе вернуть имущество один раз на главном потоке и сохранить отметку с ним. Entry удалять лишь после подтверждения снимка с Returned; если upload не удался, local pending + Returning остаются. |

Одна и та же сверка используется обычным исполнением, входом и reconnect. Решение принимает выбранный snapshot, не только последняя запись файла journal. В частности, падение после server commit, но до записи Ready восстанавливается повторным upload того же snapshot, затем replay того же запроса. Падение после сохранения Returned, но до удаления entry не создает второй pod.

Все destructive entry points `Outgoing` (карта, caravan, pods, real raid/live proposal, deposit, trade, auction, procurement) должны сохранять Prepared до снятия, а не внутри нынешнего Run после Take. Подготовка blobs сохраняет исходные объекты до успешной записи journal; частичная ошибка сериализации/записи ничего не уничтожает. Проверить `RaidResolver` (сейчас Add до save) и shop removal acknowledgements: нельзя сделать старый Add безусловно Ready и оставить эти пути вне барьера. Отметки Removed/Returned не удалять по таймеру; GC только после доказанного завершения и с учетом сохраненных pending-снимков. В 0.8.1 допустимо не вводить GC, оставаясь в существующем пределе размера сейва.

При reset/rollback чужие generation/epoch не перепривязывать. Груз неизвестного исхода сохраняется в journal для сверки, не отправляется и не возвращается автоматически в другую ветвь. Поврежденный journal нельзя молча заменить пустым списком.

## Parcel receipts и порядок входа (#1/#7/#10)

Для новой доставки записать подготовленную запись Deliver, затем на главном потоке создать pod и добавить parcel ID в receipt set. Сейв должен содержать и pod, и receipt либо не содержать обоих. RPC Deliver отправлять только после приема сервером конкретного snapshot с этим ID. Повтор при потерянном ответе сохраняет прежний ID посылки; деньги и storage fee применяются только при первом Deliver.

Сервер проверяет владельца parcel, generation/epoch и присутствие receipt в принятом snapshot. Более новый текущий снимок той же ветви должен сохранять это receipt; выбранный rollback отделяется epoch. Если упомянутый snapshot уже удален retention, допускается доказательство через текущий snapshot той же ветви с тем же parcel ID; смену ссылки выполнять явно, не подменять содержимое старого снимка.

В `Parcel` хранить признак новой receipt-доставки и generation ее колонии; reset не оживляет доставленные вещи прежней колонии. Для таких доставок `Pending` сопоставляет parcel ID с metadata текущего snapshot, а не `DeliveredTick`. Отсутствие receipt в корректном новом формате означает необходимость восстановления; наличие означает отсутствие повторного spawn. DeliveredAt=null и наличие receipt означают повтор подтверждения, а не повтор pod. Receipt хранится и после успешного ack: иначе следующий сейв снова сделает посылку недоставленной. Тик остается для истории/legacy, не для доказательства нового формата.

Порядок входа:
1. Authenticate/modpack/delivery readiness; получить generation/epoch/capability. Создать состояние сессии, но запретить доставку и destructive recovery до выбора сейва.
2. Прочитать pending и outbox, выбрать восстановление local или authoritative download. До upload проверить, что снимок согласуется с Removed/Returned незавершенных операций; не отправлять сырые pending RPC раньше этой сверки.
3. Восстановить/upload неизменяемый local snapshot либо проверить server download. При постоянном отказе сохранить локальный файл отдельно; при временном сохранить pending для повтора.
4. Согласовать фазы outbox с выбранным файлом. Повторить только доказанные Ready и подтверждения существующих receipts. Возврат/spawn, требующий Verse, выполняется после загрузки на главном потоке.
5. Перечитать mailbox относительно окончательного серверного состояния. После загрузки дополнительно сверить receipts реально загруженного файла; устаревший список никогда сам по себе не разрешает повторный spawn.

Replay отделить от загрузки UI-состояний. Wallet/rules/lots, mailbox, raids/flags, incidents, social, live/current/pending ends загружать независимо. Failed Wallet не пропускает последующие блоки. Для transient failures хранить незавершенные части и повторять существующим game update/coordinator с ограниченной задержкой, без бесконечного tight loop и перекрывающихся replay. Отмена на конец/смену сессии; проверка идентичности сессии до применения; `SharedState` менять через MainThread. Пропущенные live ends после загрузки карты должны реально вызывать settle/report, а не только попадать в список.

## Атомарное завершение live (#3)

Для визита Cancel, Fallback, CloseEnding и ReportVisit фиксируют окончательное состояние, создание возвратной посылки и очистку Pawns в одной serializable транзакции под LiveStateLock. Исключение оставляет восстановимое прежнее состояние. Announce, event bus, feed и метрики результата — после commit. Не делать вложенную SQLite-транзакцию поверх существующей транзакции raid Cancel; сохранить работоспособность raid/coop веток. Повтор завершения не создает вторую посылку.

## Scope ключей и миграция истории (#8)

Логическая идентичность: `(actorPlayerId, operationKind, client_request_id)`. Проверять повтор до изменяемых business guards, но после установления владельца и вида операции. Не принимать глобальное совпадение за успех. Новые операции сохраняют hash неизменного намерения; повтор с измененным payload получает REQUEST_INTENT_MISMATCH без side effects. Идемпотентность не зависит от текущей цены, доступа в visit, смены модпака, закрытия trade или freeze после уже принятой операции.

| Хранилище | Владелец/вид и преобразование старых записей |
|---|---|
| `parcels` | Gift + From: transfer.send; Withdraw + To: wallet.withdraw; Purchase с request ID + To: shop.buy. Добавить явные RequestActorId/RequestKind и composite unique index вместо глобального; ID не менять. Остальные исторические комбинации не угадывать. |
| `lots` | SellerPlayerId + market.post + request ID; вид не требует отдельной колонки в таблице одного вида операции. |
| `trades` | InitiatorPlayerId + trade.open + request ID. |
| `transfers` | FromPlayerId + Kind + request ID; deposit и trade-side различны. Для новых trade-side сохранять структурированную ссылку TradeId/намерение. |

Старый hash намерения неизвестен: не вычислять его из измененного trade или текущего запроса. Legacy-повтор известного actor/kind возвращает прежний результат без повторной мутации; если связь с результатом не доказана, сохранить запись и отклонить временно с объяснением. Для старого trade-side исходный TradeId восстанавливать только из однозначно проверенного формата исторической записи либо оставить нерешенным; чужой/подмененный TradeId не использовать как прежний результат. Нераспознанные legacy IDs сохраняются как блокирующие повторную мутацию в их историческом домене, а не исчезают при снятии индекса.

Полностью проверить Transfer.Send, Wallet.Deposit/Withdraw, Market.Post, Trades.Open/SetSide и Shop.Buy. Уже scoped receipts у auctions/procurement/community/influence и raids/live не переводить на другую систему; проверить, что различие видов не позволяет применить другой payload под старым ключом.

## Пароль и совместимость (#9)

После проверки учетных данных порядок gate: Ban → ServerPassword → Modpack → остальные проверки допуска. Содержимое общих settings не выдавать до знания пароля сервера. AdminBypass пропускает только сравнение модпака; правило не удалять. Не включать password auth автоматически. При Register пароль из login-запроса переносится в RegisterRequest.server_password=7 и далее в LoginContext.ServerPassword; проверка пароля предшествует settings-bearing diff и при регистрации.

Обновление с 0.8.0 добавляет nullable/default metadata, epoch=0, recovery format=0; не переписывает старые .rws, balances, payloads, IDs и request IDs. Архивный ManifestVersion дополняется optional metadata; старые manifest читаются с legacy defaults. При восстановлении нельзя потерять metadata нового снимка или уменьшить текущий epoch. Backup, deltas и retention сохраняют смысл snapshot/receipts независимо от формы файла.

Первые формат-1 снимки включают только реально доказанные receipts. Legacy DeliveredTick сохраняется для исторических записей, а не преобразуется в доказательство по равенству тиков. Уже случившуюся потерю или дубль 0.8.0 автоматически восстановить из отсутствующих данных невозможно. Legacy outbox без новой фазы не считать Prepared с гарантированно не снятым грузом: сохранять прежнюю идентичность, сверять доступные доказательства; неразрешимый случай сохранять для ручной сверки без destructive replay.

Старый клиент допускается для legacy-состояния generation/epoch по прежним правилам; после перехода колонии на новый recovery format или после rollback с epoch>0 нужен поддерживающий клиент. Сервер отказывает до загрузки карты и не допускает downgrade upload в format 0. Новый клиент перед новыми destructive операциями требует advertised recovery_version=1; старый сервер не должен молча игнорировать доказательства. Это fail-closed совместимость wire, а не обещание исправить неизмененный 0.8.0 клиент. ProtocolVersion остается прежним.

Версия исправлений 0.8.1: `Directory.Build.props`, `src/Rimlink.Client.Core/ClientInfo.cs`, `mod/About/About.xml`. Merge/push/tag/release/deploy не входят в разрешение.

## Согласованное дополнение после итогового ревью

Это документальная фиксация решений по [единственному итоговому отчету](../../verification/2026-11-03-recovery-correctness.md#итоговое-ревью-и-исправления), без нового ревью. Выполнение исправлений и результаты проверок описаны в [отчете реализации](../../verification/2026-11-03-recovery-correctness.md).

- Регистрация: настоящий прогон обнаружил отсутствие поля пароля сервера. Добавлено только `RegisterRequest.server_password=7`; клиент переносит пароль login-запроса в регистрацию, сервер передает его в `LoginContext.ServerPassword` и проверяет до выдачи settings. AdminBypass сравнения модпака сохраняется.
- **Ruling для selected snapshot:** отсутствие `Removed(id)` у Prepared не доказывает наличие имущества в выбранной колонии: более новый local save мог быть отклонен, а в старом fallback имущества еще не было. Запись переводится в `RecoveryRequired`, payload сохраняется для ручной сверки; автоматические discard, return и replay запрещены. Завершение upload A без отметки будущей Prepared B не меняет B.
- Download: выбор текущего сейва, открытие его потока и чтение generation/epoch выполняются согласованно под `PerStoreLock`; сеть передает уже выбранную пару после освобождения lock. Старые байты не получают authority новой ветви.
- Rollback: tracked Player перечитывается внутри транзакции под store lock до увеличения epoch. Два последовательных rollback после перекрывающихся чтений обязаны дать E+1 и E+2.
- Изменения имущества: проверка актуальной сессии/epoch охватывает все соответствующие transaction paths, включая raids, live и shop ack. Callbacks и replay привязаны к авторизации, generation/epoch и игровому контексту доказательства; одного равенства объекта connection недостаточно. Запоздавший shop-ответ не применяется к другой колонии.
- Очистка файлов: queued/in-flight snapshots защищаются до завершения использующих их задач, наряду с pending и quarantined journal. Успех A не разрешает удалить еще ожидающий B, даже если Current уже указывает C.
