# Rimlink после 0.8.1: пассивные аванпосты

Дата проектирования: 3 ноября 2026 года. База: main `e666570f809f86ece3b51b5c5f52935c1079cb4f`, tag `v0.8.1`.

**Статус:** пользователь утвердил спецификацию, план и исполнение; реализация основной сессией `gpt-6.1-sol` начата. Для Task 2 пользователь отдельно выбрал «SQLite/NTFS контракт»: документированные SQLite/OS guarantees на ограниченном поддерживаемом deployment принимаются как предпосылка долговечности (§9.1.1), а не как независимо полученное доказательство directory-entry power-loss persistence. Спецификации/планы/ревью выполняет реальная `gpt-6-astra`. Это контракт, не заявление о готовности всей реализации или выполненных проверках; merge/push/release/deploy требуют отдельной команды.

## 1. Цель, область и существующая основа

Дать колонии один небольшой личный источник ресурсов: реальные колонисты покидают игровую симуляцию и работают в серверном аванпосте без карты. Сервер аналитически считает выработку за реальное время, включая обычный offline и простой сервера, но останавливает её при полном складе. Это **явное исключение только для аванпоста** из заморозки офлайн-колонии, а не второй автор колониального сейва.

Сохраняется контракт [восстановления 0.8.1](<2026-11-03-recovery-correctness-design.md>): exact snapshots, неизменяемые uploads, receipts, generation, write epochs, actor/kind/request-id и ручное восстановление неопределённых исходов. Его [протокол проверок](<../../verification/2026-11-03-recovery-correctness.md>) доказывает прежние сценарии, **не** готовность аванпостов. [Предыдущая спецификация возможностей](<2026-11-01-rimlink-next-features-design.md>) не включала аванпосты; её остальные возможности здесь не перепроектируются.

### Рассмотренные подходы

1. **Выбран: серверное хранение пешек + аналитическое производство.** Один authoritative ledger, точные переходы владения, нет второй симуляции. Требует явных escrow/snapshot границ и расширения восстановления.
2. Клиент хранит работающих пешек, сервер считает ресурсы по их декларации. Проще отправка, но откат клиента возвращает работника в активную колонию при продолжающейся серверной добыче; владение становится двусмысленным. Не выбран.
3. Отдельная карта/автономная игровая симуляция. Богаче поведение, но противоречит утверждённому отсутствию карты и существенно расширяет scope. Не выбран.

Для географии выбран экспорт администратора с явным подтверждением серверу. Сведения каждого игрока без общего каталога и генерация сервером мира только из seed не являются выбранной архитектурой.

## 2. Игровой контракт

| Параметр | Утверждённое значение |
|---|---|
| Владение | Личное: world instance + player + colony generation |
| Количество | Один аванпост на колонию; подготовка основания резервирует этот слот |
| Работники | От 1 до 4; выбранные реальные пешки прибывшего каравана |
| Профиль | Один одновременно: дерево или сталь |
| Склад | 1000 единиц ресурса, не 1000 стаков |
| Основание | 500 серебра из серверного кошелька, один раз |
| Содержание | Нет регулярной платы, еды или иных расходников |
| Получение | Ручной claim в собственную почту; бесплатно, без storage fee |
| Возврат пешек | По запросу в собственную почту, бесплатно |
| Скорость доставки | Серверная почта доступна сразу после commit, без времени пути; физическая выдача после безопасной загрузки домашней колонии |
| Закрытие | Возврат всех пешек и целого склада; цена основания не возвращается |
| Гильдии | Нет владения, общего управления, влияния или дополнительных прав гильдии |

Технически неуспешное основание не оставляет окончательного списания 500. Резерв до решения допустим, расход — только при commit. Нельзя менять эти значения произвольными настройками реализации; изменение баланса — отдельное продуктовое решение. Ограничения размера запросов, журналов и каталогов не являются настройками баланса.

### 2.1. Место и создание

Основание и пополнение происходят с караваном, **реально находящимся** на нужном тайле. Нельзя дистанционно выбрать пешку домашней карты или прислать её копию. Тайл — доступная суша основной поверхности планеты, описанной утверждённым manifest. В первой версии нет основания на орбитальных/вложенных/неизвестных поверхностях.

Нельзя занять тайл player settlement, NPC settlement или другого аванпоста/подготовленного основания. Резервация блокирует несовместимые новые серверные поселения на этом тайле в обе стороны, включая restore поселения из архива. Соседние тайлы не резервируются; радиуса влияния, контроля маршрутов и запрета прохода нет. Локальные квестовые/модовые объекты, не известные серверу, дополнительно проверяются клиентом перед отправкой. Их отсутствие сервер независимо не доказывает.

Для дерева биом должен предусматривать естественные деревья по загруженным defs; не требуется существующая игровая карта и подсчёт деревьев на ней. Для стали достаточно доступной суши, без месторождения на карте. Создание не порождает игровую карту.

### 2.2. Пригодность пешек

Допускаются свои взрослые свободные колонисты обычной человеческой расы, включая обычные гены/DLC. Взрослость определяется стадией жизни, не фиксированными 18 годами. Не допускаются чужие/гостевые пешки, пленники, рабы, животные, механоиды, произвольные модовые расы, downed, mental state, неспособность к выбранной работе, H=0 и неизвестные критичные данные.

На момент назначения фиксируются оба навыка — Plants и Mining, способность к обеим работам и H. «Не способен к Mining» не мешает назначить на дерево, но запрещает переключить аванпост на сталь, пока этот работник остаётся. Повреждённая/неподдерживаемая сериализация — отказ до удаления, не выдача упрощённой копии.

В серверном custody пешка заморожена: не голодает, не стареет, не болеет, не лечится, не получает опыт и не меняет потребности. Сохраняются здоровье, гены, одежда, оружие, личный инвентарь и поддерживаемые связи. Содержимое личного инвентаря не переводится в производственный склад. При возврате обычная игровая симуляция возобновляется; недопустим искусственный catch-up голода/возраста за хранение. Уже существующие правила безопасной десериализации и RelationLedger применяются, а не заменяются очисткой данных.

После выбора работников в караване остаётся способный продолжить путь свободный колонист. Исключение: после изъятия не остаётся **ни других пешек, ни груза**, тогда пустой караван удаляется безопасно. В остальных случаях операция отвергается до изъятия; нельзя автоматически выбрасывать вещи или уничтожать остаток каравана. Проверяется полное владение вложенными предметами, а не только верхний список.

## 3. Производство и время

На одного работника за один реальный час:

- Дерево: `20 × S(Plants) × H`.
- Сталь: `10 × S(Mining) × H`.
- `S(k) = 0,5 + 0,05 × clamp(k, 0, 20) = (10 + clamp(k, 0, 20)) / 20`.
- `H = clamp(min(Consciousness, Manipulation, Moving), 0, 1)`.

Значения берутся при назначении; NaN/Infinity и некорректные навыки не нормализуются молча. Нормальный конечный вход вне диапазона clamp обрабатывается согласно формуле. H=0 непригоден. Для четырёх работников с навыком 10 и H=1: 80 дерева/час либо 40 стали/час; пустой склад заполняется за 12,5 либо 25 часов. Максимум при skill20,H1: 120 дерева/час или 60 стали/час.

### 3.1. Детерминированный расчёт

Хранятся целый склад Q, дробь F, checkpoint T, roster/profile revision и зафиксированные worker inputs. `0 ≤ Q ≤ 1000`, `0 ≤ F < 1`; при Q=1000 всегда F=0. Скорость R — сумма скоростей текущих работников. Для активного аванпоста на момент t:

1. Определить неотрицательный прошедший интервал Δ в реальных часах по серверному времени ниже.
2. Вычислить `A = Q + F + R × Δ`.
3. Если A ≥ 1000, записать Q=1000,F=0; иначе Q=floor(A),F=A−Q.
4. В обоих случаях продвинуть checkpoint до t.

Это одна атомарная settle-операция, не цикл по игровым тикам. Расчёт не зависит от числа опросов UI/рестартов. Сначала settle, затем в той же транзакции claim, смена профиля/состава, archive или close. Время после насыщения склада отброшено: claim полного склада не превращает месяцы простоя в новый полный склад. Не хранить очередь «непроизведённых» ресурсов.

Техническая числовая политика: конечные binary32 inputs H фиксируются в точном исходном представлении; вычисление использует их точные рациональные значения, целочисленные уровни навыков и целочисленную длительность. Дробь не округляется при каждом settle. Допустимо эквивалентное точное bounded представление, но не float-накопление и не «почти единица значит предмет». Размер чисел ограничен форматом inputs, диапазоном времени и Q≤1000; большой Δ сначала сравнивается с временем насыщения, без переполнения. Не добавлять случайный yield.

### 3.2. Источник времени

Внутри процесса прошедшее время измеряется монотонным таймером. При обычном старте интервалы от долговечных checkpoints до UTC старта дают offline/downtime; затем используется единая связка UTC старта + monotonic elapsed. Wall-clock step работающего процесса не выдаёт/не отнимает ресурсы. Повторный settle одного момента даёт нулевой Δ.

Сервер доверяет корректно настроенным часам хоста для межпроцессных интервалов: без внешнего доверенного времени невозможно доказать фактическую длительность остановки. Отрицательный интервал не уменьшает запас и не создаёт yield; аномалия фиксируется, спорный downtime не угадывается. Уже учтённое время не учитывается снова. Это не обещание anti-cheat против администратора часов.

Обычный offline и обычный restart **не** равны archive или bulk restore. Archive сохраняет Q,F, но не накапливает время. Bulk restore начинает новую временную границу согласно §9 и не начисляет время с backup до восстановления. Trading freeze/debt не останавливают производство.

### 3.3. Claim, switch, recall, close

- Claim «забрать добычу» после settle переносит все доступные **целые** единицы в собственную почту. Дробь остаётся. При Q=0 нет пустой посылки; результат операции всё равно идемпотентен.
- Switch сначала settle старый профиль и затем требует Q=0, подходящий тайл и пригодность всех оставшихся работников к новому профилю. F может быть ненулевой: она уничтожается только при подтверждённом предупреждении. Новые R и T действуют с commit; старый интервал не пересчитывается по новому профилю.
- Partial recall сначала settle; выбранные работники переходят в почту, F и склад остаются, R уменьшается с commit.
- Last-worker recall эквивалентен close: settle, все работники и Q в почту, F отбрасывается с предупреждением, slot/tile освобождаются после долговечного создания результатов.
- Close не удаляет custody/operation/receipt историю. Сбой создания любой результирующей посылки откатывает весь переход, а не оставляет закрытый аванпост без имущества.

## 4. Идентичность, custody и доказательства

### 4.1. Идентификаторы

- `WorldInstanceId`, `OwnerPlayerId`, `SaveGeneration` определяют область колонии; auth отдельно доказывает действующего владельца.
- `SaveWriteEpoch` отделяет разрешённую ветвь после rollback; это не идентичность пешки и не substitute restore-boundary.
- `OutpostRestoreBoundary` отделяет историю после bulk restore; авторитет хранится вне восстанавливаемой DB (§9). Process instance id недостаточен.
- `PawnCustodyId` — постоянный случайный UUID реальной пешки в outpost lineage, сохраняемый при возврате и новом назначении. UUID не генерируется заново из-за смены ThingId.
- `AssignmentId` — новый UUID каждого размещения этой пешки. `OutpostId` никогда не переиспользуется после закрытия.
- `OperationId/client_request_id` стабилен для одного намерения. SnapshotId относится к одним immutable bytes, hash — к raw XML, не к сжатому файлу.

Ограничение уникальности: в пределах world не может быть двух одновременно авторитетных мест custody одного PawnCustodyId. Scope generation проверяется отдельно; несовместимая generation не исправляется выдачей нового UUID. Имя, игровой ID, положение в списке и hash blob — вспомогательные данные, не источник идентичности.

### 4.2. Bootstrap и неизменяемая lineage

Первое присвоение PawnCustodyId выполняется в game recovery registry на main thread до удаления; запись связывает UUID с конкретной сериализуемой пешкой и сохраняется в exact pre-removal snapshot. Сервер подтверждает новую registration только для принятого snapshot допустимой ветви, отсутствующего ранее UUID и непротиворечивой связи с выбранной пешкой. Это attestation штатного клиента, не идентификация изменённого клиента по внешнему паспорту.

Перед bootstrap/assign/load проверяется уникальность UUID и однозначность ссылки на игровую пешку в полном доступном own-game состоянии, включая караваны, карты, world pawns и вложенные контейнеры. Две записи с одним UUID, несколько объектов на одну ссылку, потерянная registry-запись для уже известной lineage, повторно используемый игровой ID или конфликт с активным server custody => RecoveryRequired. Нельзя «исправить» дубль перенумерацией или считать неизвестную пешку совершенно новой. Без однозначной связи bootstrap отказывает.

Для возврата parcel несёт прежний UUID и AssignmentId; новый игровой ThingId при необходимости не меняет UUID. Связи восстанавливаются штатным RelationLedger, не identity matching по имени. История append-only содержит registration, source snapshot/hash, подготовку, removal proof, assignment commit, recall/close, parcel batch, delivery receipt и следующий assignment. Изменяемая текущая проекция не заменяет историю. Corrections — отдельные проверяемые решения администратора, не редактирование старого доказательства.

После доказанного возвращения Home пешка снова участвует в обычной игре, а не остаётся навсегда зарезервированной аванпостом. Registry сохраняет tombstone/history при смерти, уходе или последующей обычной передаче; отсутствие живой ссылки при доказанном таком событии не равно пропаже UUID. При повторном появлении той же пешки UUID восстанавливается только по сохранённой связи. Обход нескольких контейнеров с одной и той же объектной ссылкой не считается двумя пешками.

Для уже помеченных пешек существующие blob-transfer/escrow/return пути обязаны сохранять registry envelope. Доказанный обычный переход владения связывает прежний UUID с новым owner/generation через существующие transfer/removal/delivery receipts; он не является автоматическим переносом имущества при reset. Приглашённые/зеркальные копии не получают нового authoritative custody. Клиент, который не способен сохранить envelope, не получает такую пешку через неподдерживаемую выдачу. Нельзя закрытием аванпоста и перепродажей стереть lineage, а затем зарегистрировать тот же объект как неизвестный. Это targeted интеграция помеченных пешек, не изменение цен/согласий/обычных правил передач и не восстановление всей legacy истории. Неоднозначный переход остаётся ручным recovery.

Переходы авторитетного места:

| Состояние | Что разрешено | Следующее состояние |
|---|---|---|
| `Home` | Пешка существует в колонии/караване и не занята другим transfer | `Prepared` после закрепления исходного snapshot/intent |
| `Prepared` | Резерв на эту пешку/операцию; в игре заблокированы конкурирующие передачи | `RemovedAwaitingCommit`, доказанная отмена либо `RecoveryRequired` |
| `RemovedAwaitingCommit` | Пешка отсутствует в принятом post-removal snapshot; immutable blob сохранён | `Assigned` или `ReturnPending` по единственному durable решению сервера |
| `Assigned` | Blob только у сервера; работник участвует в R | `ReturnPending` по recall/close |
| `ReturnPending` | Blob авторитетно принадлежит одной собственной mailbox batch; R больше не включает работника | `Home` после accepted exact delivery snapshot и завершения receipt-перехода |
| `RecoveryRequired` | Доказательств недостаточно/конфликтуют; никакого guessed replay/return/yield этого назначения | Только проверенный ручной переход с сохранёнными артефактами |

Почта и outpost ledger могут ссылаться на одни immutable bytes, но только одно место вправе выдать их. Завершённая доставка не позволяет повторный spawn; следующий assignment требует доказанную предыдущую delivery.

### 4.3. Outpost frontier

Снимок содержит versioned bounded outpost section: scope/boundary, UUID registry, immutable transition receipts и frontier принятой истории. Сервер хранит исходные извлечённые metadata и hash именно этого XML. Повтор snapshot-id с другими bytes запрещён; неизвестный формат не считается пустой историей.

Frontier — не один gameTick и не только «число работников». Он покрывает все переходы, меняющие локальное владение: removal, доказанный возврат, выдачу ресурсов/пешек, повторное назначение, bootstrap. Проверка учитывает causal predecessor и факт наличия соответствующих durable receipts в выбранной ветви. Серверные claim/recall, ещё не материализованные дома, могут оставаться ожидающими: согласованный snapshot не обязан содержать receipt ещё не выданной посылки. Но нельзя принять snapshot, стирающий уже подтверждённую доставку или вновь включающий server-held пешку.

История не удаляется по timer/закрытию аванпоста. Retention сохраняет необходимые immutable snapshots/blobs и компактные доказательства всех поддерживаемых rollback-переходов. GC допустим только с доказанным отсутствием ссылок из активного custody, pending/outbox, mailbox, archive и доступных rollback-версий. Первая версия может не выполнять такой GC; переполнение лимита останавливает новую операцию до удаления имущества, а не стирает доказательства.

## 5. Протокол операций и атомарность

### 5.1. Подготовка основания/назначения

1. На main thread проверить действующую own-game session, отсутствие несовместимого live/visit/mirror transfer, настоящий caravan tile, состав, пригодность, остаток каравана и данные manifest. Собрать все blobs без изменения живых объектов. Любая ошибка оставляет их нетронутыми.
2. Долговечно создать local Prepared intent с request-id, UUIDs, immutable blobs/hashes и scope. Зарегистрировать и принять exact pre-removal snapshot, содержащий согласованный registry и caravan attestation. До принятия этого снимка никаких удалений.
3. Серверное Prepare в одной транзакции проверяет guards, слот/тайл/места, уникальность custody, manifest и pre-snapshot. Для основания резервирует 500 серебра, tile и slot; для пополнения — worker slots. Сервер сохраняет immutable intent/blobs и резерв. Он не запускает производство и не расходует серебро окончательно.
4. После подтверждённого Prepare клиент повторно проверяет live caravan/пешек и session scope. До удаления запрещены конкурирующие операции над выбранными пешками и движение подготовленного каравана. Снять ровно подготовленный набор, записать removal receipt в той же собственной игре, сохранить/upload exact post-removal snapshot. Изменились пешка/багаж/tile — не переписать payload под прежним id, а отменить по правилам ниже.
5. Commit допускается только с принятым post-removal proof именно этого intent, current scope/boundary/epoch и совместимым текущим snapshot. Он атомарно переводит резерв в assigned custody, списывает зарезервированные 500, создаёт/обновляет outpost roster и checkpoint и записывает result. Производство начинается с server commit, а не клиентского времени прибытия/удаления.

Business guards и цена проверяются при Prepare; Commit исполняет уже зарезервированное обязательство, не создаёт новую торговую операцию. Последующий trading freeze/debt сам по себе не превращает его в потерю снятых пешек. Текущие scope, manifest validity, lifecycle и proof checks остаются обязательными. Если safety проверка запрещает commit, разрешено только доказанное AbortWithReturn либо RecoveryRequired, не произвольный definitive error с локальным возвратом.

Все первые 1–4 работника основания переходят одним решением: нет частично созданного outpost после отказа одного blob. Serialized blobs после Prepare неизменяемы. Вся операция укладывается в лимиты до изъятия; несколько частей upload имеют общий digest/manifest и не считаются принятыми по отдельности.

### 5.2. Отмена и неопределённость

Отмена — отдельный идемпотентный server transition, сериализованный с commit. Неясный RPC status не отменяет Prepare и не разрешает локальное восстановление из blob. Автоматический таймер не освобождает потенциально удалённых пешек.

- Пока текущая запущенная игра **доказанно не приступала к удалению**, coordinator сначала долговечно фиксирует cancellation intent и запрещает removal callbacks этой операции, затем принимает exact snapshot с NoRemoval/cancel attestation и исходными живыми пешками. Только эта непрерывная проверенная ветвь позволяет durable `AbortNoRemoval`: пешки остаются, резерв платы/тайла освобождается. Одного старого pre-snapshot недостаточно. Поздний Prepare response не снимает cancellation fence. После холодного запуска без такого доказательства действует RecoveryRequired.
- Если accepted post-removal proof существует, отмена получает `AbortWithReturn`: сервер атомарно переводит те же blobs в одну собственную mailbox batch и освобождает резервы; клиент не создаёт параллельный local return. Плата основания возвращается из резерва, финального расхода нет.
- Холодный запуск, Prepared без доказанного исхода, конфликт snapshot или отсутствие связи с фактически загруженной игрой => RecoveryRequired. Отсутствие Removed в старом файле **не** доказывает, что изъятия никогда не было. Payload, snapshots и резерв сохраняются для ручной сверки.
- Commit победил гонку с cancel — возвращается committed outcome, а не отказ, дающий право создать копию. Последующий recall — новая операция. Abort победил — поздний commit отвергается терминальным решением.

Сервер не ждёт сеть внутри транзакции. На reconnect coordinator сначала выбирает/проверяет снимок, потом согласует journal и server status, затем только повторяет доказанные действия. Ошибка Wallet не блокирует этот recovery или чтение mailbox. Callback старой session/game/boundary не изменяет новую игру.

### 5.3. Idempotency и guards

Порядок: auth/owner/kind + допустимые world/generation/epoch/restore-boundary → поиск неизменного request-id/intent → возврат прежнего terminal result → только для новой операции business guards. На неправильной boundary нельзя вернуть старый success как разрешение выполнять локальные действия. Read-only просмотр старого результата не является разрешением replay/spawn.

Ключ scoped actor + operation kind + request-id; intent фиксирует outpost/assignment/pawn IDs, профиль, набор, hashes, manifest, predecessor proofs и исходный scope. Другой payload под тем же ключом — typed intent mismatch без эффектов. Response/events не являются единственным хранилищем результата; уведомления публикуются после commit.

| Действие | Экономические ограничения | Неотменяемые safety проверки |
|---|---|---|
| Новое основание | Freeze/debt/modpack; достаточно 500; wallet threat guard | Auth, own-game, exact snapshots, current scope, caravan, manifest, custody |
| Пополнение караваном без wallet outflow | Freeze/debt/modpack; **нет дополнительного home-threat запрета** | Те же safety проверки и max4 |
| Claim/recall/close | Собственное имущество возвращается при freeze/debt/threat | Auth, boundary/epoch/generation, recovery, совместимость выдачи |
| Switch | Не вводить debt/threat запрет и не трактовать как торговый вывод | Settle, Q=0, manifest, новая работа доступна всем, current scope |
| Production | Не торговля; freeze/debt не останавливают | Active lifecycle, валидный custody/checkpoint, cap |
| Deliver/ack | Нет outpost storage fee; freeze не блокирует возврат | Own safe home game, exact snapshot + parcel receipt, current scope |

Существующее caravan-исключение подтверждено [TransferService:19–34](<../../../src/Rimlink.Server/Application/Economy/TransferService.cs#L19-L34>); delivery исключено из trading freeze в [EconomyGate:8–28](<../../../src/Rimlink.Server/Application/Economy/EconomyGate.cs#L8-L28>) и [PlayerFreeze:9–12](<../../../src/Rimlink.Server/Application/Economy/PlayerFreeze.cs#L9-L12>). Здесь нет разрешения обходить auth/recovery под видом «возврата».

### 5.4. Concurrency и состояния аванпоста

Outpost lifecycle: `Preparing → Active ↔ Archived → Closed`, с отдельной блокировкой `RecoveryRequired` для нарушенной доказательной цепочки. `Preparing` не производит. `Closed` терминален; новый outpost получает новый ID. Archive не является close.

Все расчёты и мутации конкретного outpost читают строки заново внутри единой транзакционной границы. Revision/CAS и unique constraints защищают слот owner+generation, tile+surface и активное custody. Roster до settle — старый, после commit — новый; нельзя применить новый roster к старому времени. Операции claim/recall/switch/close/Prepare/commit не могут проходить по разным несогласованным блокировкам.

Serialization охватывает также settlement occupy/abandon/restore, receipt acceptance, save selection, archive/reset и backup cut. Используется общий storage barrier с существующим SaveFiles.PerStoreLock; внутри него — операции фичи/DB, без сетевых ожиданий и повторного взятия уже удерживаемого lock. Интеграция должна соблюдать существующий порядок live/archive locks; несовместимый порядок устраняется до включения фичи, не обходится снятием safety barrier. Межпроцессный CLI следует тому же storage lock. Смена authority frontier и связанное изменение имущества фиксируются одной DB-транзакцией; внешняя recovery anchor (§9) ограждает эту транзакцию.

Close, last-worker recall и switch не проходят, пока существует незавершённое подготовленное пополнение этого outpost: сначала его доказанное завершение/отмена. Это исключает освобождение тайла/смену профиля под уже снятыми, но ещё не committed работниками. Partial recall и claim сериализуются обычным способом и не присваивают чужой reserve.

Уникальные constraints — последний рубеж, не замена domain result. Проигравшая конкуренция получает typed conflict; нет частичного списания или orphan parcel. Capacity claims и worker batches не суммируются сверх лимита при concurrent Prepare.

## 6. Почта, materialization, integrity и богатство

Outpost parcels — **собственные возвраты/добыча**, не gifts: не требуют accept gifts, не направляются другому владельцу, не исчезают по сроку хранения, не облагаются storage fee и не превращаются в trade. При отсутствии безопасной домашней карты остаются на сервере. Caravan/visit/mirror не являются местом физической выдачи.

Каждая claim/recall/close/abort-with-return создаёт immutable batch: один operation id, полный список parcels и payload digests, bound owner/world/generation/boundary. Если лимиты требуют несколько parcels, весь batch создаётся транзакционно; размер и схема проверяются до ухода из source custody. Повтор не создаёт новую batch. Расход склада и создание почты — один commit.

Производственные предметы передаются новым типом payload: только разрешённый profile/defName, целое положительное количество, manifest/valuation version, источник outpost/operation и server-side import value. Для первой версии это обычные WoodLog/Steel без quality/stuff/произвольного класса/XML. Клиент проверяет полный payload и совпадение defs до изменений, затем создаёт обычные стаки в пределах stackLimit на main thread. Отсутствующий def, несовместимые свойства или неподдерживаемый payload оставляют посылку недоставленной; нельзя заменить ресурс серебром/другим def или потерять часть batch.

Для пешек возвращаются исходные immutable blobs с registry envelope. Десериализация учитывает ResetMapIndex, необходимость новых игровых IDs, faction/ideo references, RelationLedger и очистку UI caches согласно существующим правилам. Нельзя Destroy десериализованный дубликат для «уборки»: он может сравниваться с живой пешкой по игровому ID.

Выдача: durable Deliver preparation → main-thread materialization вместе с parcel receipt/UUID registry → exact save/upload → server receipt acceptance/ack. До успешного локального перехода stage не становится видимым игровому тиканью; partial failure либо отменяет только созданные этим stage объекты безопасным способом, либо блокирует сохранение/дальнейшую выдачу и требует recovery. Нельзя сохранить половину batch с полным receipt. После crash выбор snapshot и receipt определяет повтор ack, не ответ Pending сам по себе.

**Count once:** в wealth входят server-held worker + личные вещи, целый stock и ожидающие parcels. Одна и та же стоимость не учитывается одновременно в outpost и почте; после accepted snapshot с delivery receipt — в локальном wealth, но не ещё раз в server-held, даже если транспортный ack потерян. Резерв основания относится к wallet-held один раз; consumed500 после commit больше не имущество. Дробь F не является готовым предметом и в wealth не входит. Применяется существующий коэффициент server-held wealth, а не новый.

В export администратора включаются versioned нормативные значения обычной единицы WoodLog/Steel для данного набора defs, снятые из игры; сервер проверяет конечность/неотрицательность и закрепляет их с manifest. Они используются для stock, parcel и import credit; клиентская команда claim не может задавать цену. Работники/вещи используют зафиксированную существующим механизмом оценку blob без повторного сложения инвентаря. Несовместимая оценка/defs не разрешается угадыванием.

Integrity credit возникает по доказанной физической выдаче, один раз на parcel/receipt, в той же принятой save-истории: легальная добыча не выглядит как необъяснимый локальный рост wealth. Server production не начисляет кредит заранее. Перед wealth snapshot выполняется существующий ForceRecount. Wealth и публичные проекции не раскрывают приватные blobs, registry и health детали.

## 7. Географический manifest и доверие

Источник — **новый экспорт из активного правильного World администратора**, не генератор в сервере. Новые миры расширяют существующий admin generation hook; существующие получают отдельное явное действие export/confirm. Подтверждение показывает world, параметры, поверхность, охват тайлов, fingerprint defs/modpack/DLC и digest. До него нет Prepare основания.

Manifest содержит schema/version, WorldInstanceId, полный digest параметров генерации, compatibility fingerprint, основную поверхность, перечисление tile IDs с biome/land/passability/natural-tree flags, ресурсные defs/valuation и revision/digest. Проверяются конечные размеры, отсутствие дублей/дыр в заявленном охвате, допустимые числовые диапазоны, отсутствие альтернативных conflicting records и соответствие миру. Сбор game objects — main thread. Неизвестный biome/поверхность/def не превращается в разрешение.

Каталог не является статическим списком всей будущей занятости: действующие server settlements, archived reservations и outpost reservations проверяются в транзакции отдельно. Клиент также проверяет фактический мир и свои локальные препятствия.

Manifest immutable после подтверждения. Новая revision — maintenance-переход с validation всех затронутых outposts/preparations и сохранением старой provenance. Нельзя сменой каталога молча ускорить старые worker inputs, переместить аванпост или удалить склад. Неразрешённая несовместимость ставит затронутый объект на safety hold, сохраняя имущество и checkpoint; время hold не угадывается при возобновлении. Это не обычный trading freeze.

Caravan attestation связывает actual tile/surface, local caravan identity, выбранные UUID и roster, eligibility/skill/H inputs, остаток каравана, manifest digest и exact pre/post snapshots с operation id. Сервер проверяет scope, hashes, receipts и внутреннюю согласованность с ledger.

**Граница доверия:** хеш snapshot доказывает привязку и неизменность байтов после фиксации, но не честность их автора. Admin export — доверие администратору и его игровому миру. Нельзя называть attestation независимым доказательством честного пути или защищённой симуляцией. Полный anti-cheat против модифицированного клиента/администратора не входит; при этом штатные disconnect/replay/rollback не должны создавать потери/дубли.

## 8. Archive, reset и rollback

### 8.1. Archive / restore той же колонии

Archive берёт lifecycle barrier, запрещает новые Prepare/commit и проверяет операции **до** существующих cancellation side effects. Неопределённая передача или начатая, но несогласованная физическая выдача не заметается архивированием: сначала доказанное завершение/отмена либо отказ archive с RecoveryRequired. Нельзя автоматически признать Prepared «не происходившим». Полностью committed mailbox batch, физическая выдача которой ещё не началась, не является неопределённой передачей: она сохраняется с архивом и может ждать restore; archive не обязан заставлять игрока сначала забрать всякую доказанно ожидающую почту.

Победивший archive рассчитывает production до одной server-time границы и сохраняет `Archived`, Q,F, работников, scope, slot/tile и checkpoint с архивной записью согласованно. Конкурирующий commit либо завершился прежде archive и вошёл в архив, либо видит архивный lifecycle и не проходит. Старый callback не запускает производство после паузы.

Restore той же колонии проверяет archive manifest, outpost lineage, generation, epoch и занятие тайлов до публикации. Возобновляет Active с текущего checkpoint без времени архива; Q,F и inputs сохраняются. Сбой restore не создаёт нового владельца и не возобновляет одну половину состояния. Возвраты/claim из архивной колонии выполняются после её успешного restore, не пересаживаются в новую generation.

### 8.2. Reset / recreate world

Перед любым изменением saves/economy/guild/archives/reset-generation выполняется outpost preflight. Он отказывает при Active/Archived/Preparing, неразрешённых local/server transfer proofs, ReturnPending, недоказанной выдаче либо иной открытой outpost custody. Закрытие объекта само по себе недостаточно: всё имущество должно быть физически получено в accepted home snapshot, receipts согласованы. Архивированную колонию сначала восстановить.

Recreate-world сначала под общей эксклюзивной lifecycle границей проверяет **всех** затронутых владельцев, включая архивных, а не сбрасывает первых и затем обнаруживает запрет у последнего. Запрет новых операций сохраняется до завершения destructive-процедуры. Ошибка preflight даёт ноль side effects; crash уже разрешённого reset сохраняет maintenance/recovery marker и не публикует промежуточный мир. Это targeted защита outpost интеграции, не заявление, что все прежние admin операции уже атомарны. После чистого preflight действует прежняя явно разрушительная семантика reset; перенос имущества в новую generation не добавляется.

### 8.3. Rollback конфликтов outpost

До изменения current save, epoch и запуска прежних возвратов проверяется выбранный exact snapshot против outpost frontier/lineage. Отказывают snapshot, который:

- возвращает server-held/return-pending пешку в локальную колонию;
- стирает подтверждённую delivery ресурсов или работника;
- возвращает старое назначение после возврата/повторного назначения;
- теряет UUID registry/proofs, известные серверу, либо имеет другую generation/boundary без разрешённой процедуры;
- не позволяет доказать совместимость из-за legacy/повреждённых/удалённых данных.

Нельзя опираться только на текущий список работников: закрытый outpost и уже доставленные parcels тоже оставляют барьер. Допускается snapshot с тем же доказанным локальным frontier; обычные серверные stock/clock изменения не требуют запрещать любой старший игровой тик. До завершения Prepared/ReturnPending rollback не маскирует неопределённость.

При разрешённом rollback применяется прежний write-epoch fencing 0.8.1, без переписывания исходных immutable snapshots и без использования login epoch как разрешения старому pending. Outpost barrier не меняет правила rollback unrelated market/raid/других функций и не пытается исправить их старую историю универсальным reconcile.

## 9. Backup, внешняя authority и bulk restore

### 9.1. Почему одного UUID вне DB недостаточно

Обычный backup той же работающей timeline содержит ту же boundary. Если просто хранить UUID отдельно, ручная замена DB старой копией с таким же UUID останется незамеченной. Поэтому вне восстанавливаемого набора нужен не только boundary, но и **durable authority head** защищённой outpost истории. Этот раздел — bounded техническое уточнение safety-контракта, не новый игровой выбор.

Recovery anchor находится в отдельной явно настроенной директории, **не внутри DataDir, backup/staging/extraction tree и не в наборе заменяемых restore файлов**. Canonical paths проверяются на пересечение. Anchor принадлежит этой установке/world, содержит boundary, committed head, phase и при необходимости одно pending решение. Его нельзя восстановить копией старого backup. В SQLite хранится matching head/boundary. Нельзя автоматически создать пустой anchor при наличии outpost history или объявить отсутствие файла первым запуском. Первое включение фичи требует явной административной инициализации и доказанного отсутствия прежней outpost history; потеря anchor после включения требует восстановления с новым fence, не silent bootstrap.

### 9.1.1. Принятый SQLite/OS deployment contract

Пользователь явно выбрал этот bounded контракт вместо Linux-only support или остановки из-за отсутствия независимого Win32 directory-entry proof. Он допускает продолжение Task 2 при соблюдении перечисленных ограничений; **не** объявляет backend реализованным/проверенным и не снимает остальные readiness gates.

- **Поддерживаемый stack:** Windows со стандартным SQLite `win32` VFS на локальном NTFS; Linux со стандартным `unix` VFS на явно квалифицированной локальной FS с корректными locks, file/directory sync и SQLite recovery semantics. ОС, драйверы, контроллер и носитель должны честно исполнять flush/barrier/order guarantees. Сетевые/синхронизируемые каталоги, custom/nolock VFS, непроверенные FUSE/overlay и временный container writable layer не входят в профиль. Docker сам по себе не гарантия: и основная DB, и anchor находятся на явно проверенном постоянном backing storage; anchor по-прежнему вне заменяемого набора.
- **Backend:** отдельная небольшая SQLite authority DB, а не таблица основной DB; bounded logical head/Pending/RestoreInProgress. Для authority connections обязательны effective `journal_mode=PERSIST`, `synchronous=EXTRA (3)`, `Pooling=False`, штатный `Mode=ReadWrite` без auto-create DB. Проверяются реальные ответы PRAGMA каждого connection, native library version/source-id, VFS и build/provider configuration, отсутствие отключённых sync/locking. Запрошенная строка подключения не считается проверкой. OFF/MEMORY/NORMAL, неподтверждённый VFS или config mismatch не являются fallback: Maintenance.
- **Идентичность зависимости:** matching-upstream research зафиксировал в используемых native artifacts SQLite `3.53.3`, source-id `2026-06-26 20:14:12 d4c0e51e4aeb96955b99185ab9cde75c339e2c29c3f3f12428d364a10d782c62`, пакет `SQLitePCLRaw.lib.e_sqlite3 2.1.13`. Это результат статического исследования артефактов, **не** выполненный runtime attestation backend. Task 2 должен проверить фактически загруженную библиотеку/VFS/config на обоих целевых профилях; обновление/другая сборка требует повторной квалификации, а не молчаливого принятия по названию пакета.
- **Provisioning и logical initialization раздельны:** физический каталог, authority DB и её journal подготавливаются явной административной maintenance-процедурой на выбранном stack до первого защищённого domain mutation. Обычный startup/logical initialize проверяет подготовленное хранилище, а не создаёт отсутствующее. Первое logical initialize разрешено только при доказанно пустой outpost history. Наличие файлов или operator flag не объявляется независимым доказательством их переживания power loss: долговечность provisioning здесь входит в **принятую предпосылку SQLite/OS contract**. Если история уже есть, пропавшее/повреждённое хранилище не инициализируется заново.
- **Жизненный цикл journal:** PERSIST сохраняет journal при обычном commit, но не обещает его вечной неизменности. `Mode=ReadWrite` основной authority DB не запрещает SQLite создавать rollback journal. DB и возможный hot journal рассматриваются вместе; нельзя удалять, переносить или «очищать» journal вручную, подменять DB файлом или откатывать anchor старым backup. Проверенная SQLite hot-journal recovery выполняется под exclusive authority/storage fence ДО обслуживания. Затем проверяются DB integrity/schema, installation/world/boundary, record checksum/digest/head, main-DB head и immutable file evidence; выполняется reconciliation §9.2.
- Если штатная recovery изменяет/удаляет/recreates journal, этот этап остаётся внутри **явной fenced provisioning/recovery procedure**, с проверкой effective settings и сохранением прежней logical identity/history. До восстановления пригодного journal/DB состояния protected mutations запрещены. Неожиданное отсутствие/corruption до обычного открытия — Maintenance, не молчаливое создание journal с предположением «он был холодным». Штатный zeroed header/cold journal по SQLite semantics не считается corruption; пригодность определяется с учётом этих состояний, а не требованием всегда иметь hot header. При неоднозначности hot-journal loss/прерванного recovery требуется ручное восстановление; чистый integrity_check сам по себе не доказывает, что последний head не потерян. Если процедура прервана, следующий startup либо доказанно завершает ту же recovery, либо остаётся Maintenance. Recreate journal никогда не означает новый installation/head или bootstrap истории.
- **Долговечность всей цепочки:** основной SQLite domain+head commit также обязан быть durable в его фактическом journal/synchronous режиме; настройка только authority DB недостаточна. Нельзя принять main `NORMAL` как power-loss durability. Immutable snapshot/blob bytes и необходимые directory/file операции до подтверждения сохраняются по их собственному durable контракту; выбранная SQLite предпосылка не доказывает автоматически любые внешние rename/copy. Существующий bounded safety graph, exact receipts, replay fences и §9.2 order не ослабляются.

Основание предпосылки: [SQLite synchronous](<https://www.sqlite.org/pragma.html#pragma_synchronous>), [atomic commit / PERSIST и OS assumptions](<https://www.sqlite.org/atomiccommit.html>), [hot-journal recovery](<https://www.sqlite.org/lockingv3.html#dealing_with_hot_journals>) и [VFS](<https://www.sqlite.org/vfs.html>). EXTRA не является самостоятельно доказанным Win32 directory flush: отдельное доказательство persistence новых Windows directory entries по-прежнему **не получено**. Эта граница явно принята пользователем, не скрыта за словом preprovisioned. Crash/process-kill tests проверяют state machine и recovery на наблюдённом stack; они **не** являются power-loss proof или гарантией честности произвольного железа. Выход за принятый профиль/невозможность проверить условия => Maintenance/STOP, не weaker backend.

### 9.2. Ограждение защищённых транзакций

Под общим storage/lifecycle barrier защищённый переход получает уникальный next-head и неизменный digest. К защищённым относятся custody/parcel/receipt/frontier, stock/checkpoint, manifest, archive/reset/rollback и принятие snapshot, меняющее authority outpost данных.

1. Атомарно и долговечно записать в anchor `Pending(old-head, next-head, transition-digest)` до DB commit.
2. Одной SQLite-транзакцией записать domain changes, transition record и next-head.
3. После успешного commit закрепить committed next-head в anchor. Только после этого публиковать успешный mutating result/уведомление и разрешать следующий переход.

При нормальном crash: Pending + DB old-head доказывает, что эта DB-транзакция не совершилась; Pending + DB next-head с тем же transition digest доказывает её commit и позволяет завершить запись anchor. Любое другое сочетание — stop/recovery. Не повторять domain action вслепую. Ошибка записи anchor не выдаёт final business rejection, который позволил бы local return.

Committed external head + более старый DB head обнаруживает подмену старым backup даже при совпадении boundary. Anchor protocol защищает от штатных сбоев/неправильной поддерживаемой restore-процедуры, не от администратора, одновременно вручную подделавшего обе копии. Потеря всей установки/anchor неразрешима автоматическим угадыванием: новый host стартует в explicit recovery/import mode с новой boundary, без обслуживания старых mutations. Это узкий fence фичи, не универсальный WAL всех подсистем.

### 9.3. Создание backup

Под существующим shared storage lock и outpost lifecycle barrier выбрать единый cut time, settle активные outposts до него и закрепить head. DB snapshot, save files и необходимые archived saves снимаются из этого же согласованного среза. Manifest содержит world/boundary/head, cut/checkpoint times, hashes/размеры всех файлов, exact snapshot IDs, archive manifests, ссылки custody/receipts и географический manifest.

Нельзя добавлять archive файлы позже без того же среза или считать архив сохранённым только потому, что в DB есть его строка. Ссылки, файлы и hashes проверяются до объявления backup пригодным. SaveFiles определяет full/delta/base; backup не предполагает, что любая историческая версия имеет full-файл. Сам anchor **не** входит в восстанавливаемый payload; его observed identity в manifest — доказательство среза, а не инструкция заменить внешний authority.

### 9.4. Restore на остановленном сервере

1. Захватить межпроцессный storage/external-anchor lock. До любых замен долговечно поставить внешний `RestoreInProgress` с новым случайным boundary и идентичностью выбранного backup. На startup этот marker запрещает обслуживание, включая save upload/delivery/replay затронутых колоний.
2. Проверить manifest и распаковать в staging с защитой путей/лимитов. Проверить DB-связи, blobs, snapshots, receipts и archive files целиком. При неполноте не публиковать набор и не отпускать fence. Старый пригодный набор не удаляется до проверки нового.
3. Восстановимо переключить набор файлов/DB. Не обещать атомарность нескольких filesystem rename: progress marker различает стадии; после crash остаётся maintenance до однозначного завершения/отката процедуры. Нельзя запускать сервер между заменой DB и saves.
4. Зафиксировать новую boundary/authority head, ссылку на backup cut и restore completion. Перенести восстановленные записи как исторические доказательства, **не** переписать старые bytes snapshots новой identity. Активным outposts установить новый accepted resume checkpoint; archive остаётся paused. Интервал backup→restore не даёт выработки.
5. Только после проверки согласованности файлов/DB/external authority разрешить штатное чтение и controlled download/reconciliation. Незавершённый restore/fence mismatch никогда не исправляется обычным login или process restart.

Новый клиент, который жил после backup, не может «догнать» сервер старым outbox или повторным spawn. Его артефакты сохраняются quarantined. Доверенный download выбранного canonical snapshot с hash/ID и новой boundary разрешает загрузку именно этой восстановленной ветви; следующее собственное сохранение фиксирует новое разрешение. Старые pending файлы не переписываются и не переносятся через границу. Для доказанных ожидающих parcels восстановленного среза создаётся явная новая authorization-связь `(new boundary, original parcel id, immutable payload digest, canonical snapshot proof)`; исходный provenance не переписывается, новая копия parcel не создаётся. Это разрешение выдачи восстановленной истории, не автоматический replay старого client request. Уже содержащий receipt canonical snapshot разрешает лишь ack, не spawn. Открытые операции из backup разрешаются только доказанными сохранёнными transitions; неоднозначные переходы требуют ручного решения.

Bulk restore восстанавливает **весь** согласованный срез, а не объединяет его с более новыми клиентскими колониями. Гарантия не распространяется на бездоказательное сохранение новых добычи/пешек вне восстановленной timeline. Нужные данные отсутствуют — pause, не создание компенсационных копий.

## 10. Совместимость, интерфейсы и ограничения

Протокол только additive: новые сообщения/поля/oneof bodies/ошибки со свободными номерами после проверки актуального дерева. Старые номера и meanings не переиспользуются, ProtocolVersion не повышается ради совместимых добавлений. Feature proto не импортирует events.proto.

Отдельная advertised outpost capability покрывает prepare/commit/cancel, exact metadata/registry, typed resource payload и restore fencing. Клиент проверяет capability до удаления. Сервер запрещает неподдерживающему клиенту загрузить/записать затронутую колонию, если тот может потерять registry/receipts; отсутствие capability не означает пустой outpost. Колонии без outpost history продолжают совместимость 0.8.1. Закрытие объекта не разрешает downgrade с потерей его истории.

Неизвестная typed ошибка не должна заставлять старый outbox выполнить возврат; fail-closed capability применяется раньше mutating вызова. Operation status отличает retryable transport, durable rejection/abort и RecoveryRequired. Лимиты и malformed inputs возвращают типизированный локализуемый результат, не crash/частичное действие.

Хранилище расширяется EF migrations со schema/upgrade tests, без переписывания старых blobs, save IDs или legacy receipts. На старом сервере первоначально нет outposts/manifest/anchor: фича не создаёт фиктивных workers и не начинает производить ресурсы до явной инициализации/подтверждения.

UI показывает профиль, 1–4 работников, замороженные входы формулы, скорость, целый склад/дробный прогресс, состояние full/archived/recovery и понятную причину запрета. Действия: основать у каравана, добавить работников на месте, получить добычу, вернуть выбранных, сменить профиль, закрыть. Отдельные подтверждения — цена основания, удаление из каравана, потеря дроби, закрытие. Network pending не показывается как гарантированный отказ.

Admin UI/REST/CLI получают согласованные manifest confirm, статусы recovery и безопасные archive/reset/backup preflight результаты. Ручное восстановление не является кнопкой «выдать ещё раз»: оно требует выбранных доказательств, actor/reason и append-only resolution; исходные артефакты сохраняются.

Game objects доступны только main thread; client core не получает Verse/RimWorld references. UI state обновляется существующим безопасным путём. Пользовательские тексты — keyed EN/RU. Dev companion/debug actions и документация входят в будущую реализацию; сейчас они не созданы.

Timing regression — также доступный slow-CPU/Linux прогон по правилам проекта. Нельзя объявлять игру проверенной по одним unit tests.

## 12. Non-goals и следующий этап

Не входят игровые карты аванпостов, удалённая RimWorld-симуляция, голод/возраст/лечение/опыт/содержание, другие ресурсы/апгрейды, auto-delivery, рейды на аванпосты, гильдейское владение/влияние, геополитика, маршрутизация караванов сервером, произвольные модовые расы, другие будущие фичи, универсальный автоматический reconciliation и anti-cheat против модифицированного клиента/администратора. Не обещаются атомарность старой restore-реализации или сохранение данных, отсутствующих в выбранном backup.

Плану остаются конкретные имена новых типов/файлов, свободные protobuf номера, EF schema, числовые resource limits, UI layout и последовательность RED→GREEN работ. Он **не** вправе заново выбирать ownership, time/cap/fraction, момент commit, replay/rollback authority или ослаблять внешний restore fence. Если существующий код делает требование недостижимым в этом scope, план обязан остановиться и вынести конкретное изменение контракта на согласование, не скрыть его в implementation detail.

Спецификация и план уже утверждены, согласованное исполнение основной Sol начато. Уточнение §9.1.1 фиксирует отдельно принятую deployment-предпосылку, не меняет игровой контракт и не является review реализации. Один итоговый обзор полной реализации на Astra, честный отчёт проверок и отдельные разрешения на merge/push/release/deploy сохраняются.
