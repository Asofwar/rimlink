# Rimlink — проектирование ядра

Дата: 2026-10-28. Статус: на вычитке.

## 1. Цель и границы

Rimlink — мультиплеер для RimWorld 1.7 для постоянного сервера сообщества
модпака: десятки игроков заходят когда хотят, мир живёт круглосуточно. Каждый
игрок ведёт свою колонию в общем мире. Колония симулируется на клиенте и
заморожена, пока игрок офлайн. Сервер хранит и координирует всё общее.

Проект делится на три подпроекта, каждый со своей спецификацией и планом:

1. **Ядро** (этот документ): сервер, аккаунты, общий мир, поселения, чат,
   сейвы, модпак, админ-API.
2. **Экономика**: передача вещей и пешек, торговля, рынок, караваны.
3. **Синхронизация в реальном времени**: визиты и рейды.

После ядра отдельными подпроектами идут веб-панель администратора и
Discord-бот; оба работают через REST-API ядра.

Это чистая разработка: собственный протокол, сервер и клиент. Код, ассеты,
структуры данных и название других мультиплеер-модов не используются.
Совместимость с ними не планируется.

Ограничения:
- Только RimWorld 1.7 (движок на .NET 10, Unity заменён `UnityStubs`).
- Сервер запускается в Docker на Linux и напрямую на Windows.
- Лицензия MIT, репозиторий публичный: `github.com/Asofwar/rimlink`.
- Название `Rimlink`, packageId мода `asofwar.rimlink`.

Критерии успеха ядра:
- Игрок с нуля (подписка на модпак, вход, высадка, игра, выход, повторный
  вход) проходит весь путь без помощи админа.
- Сервер с 50 одновременными игроками не теряет сейвы и не падает от ошибок
  одного клиента.
- Любое общее состояние меняется только через проверенные сервером запросы.

## 2. Компоненты и репозиторий

Монорепо, одно решение `Rimlink.sln`:

| Проект | Назначение | Ключевые зависимости |
|---|---|---|
| `src/Rimlink.Protocol` | `.proto`-контракты, сгенерированные классы, общие константы (версия протокола, лимиты) | Google.Protobuf, Grpc.Tools |
| `src/Rimlink.Server` | ASP.NET Core: gRPC-сервисы игры, REST-админка, SQLite, хранилище блобов, проверка Steam-билетов | Grpc.AspNetCore, EF Core Sqlite, Serilog |
| `src/Rimlink.Client` | Мод RimWorld 1.7: сетевой слой, локальное состояние, применение к игре, UI | Grpc.Net.Client, Lib.Harmony (только компиляция, рантайм из мода Harmony) |
| `src/Rimlink.Tools` | CLI администратора: миграции, бэкап и восстановление, импорт модпака, управление через REST | System.CommandLine |
| `tests/Rimlink.Server.Tests` | Юнит- и интеграционные тесты сервера | xUnit, gRPC in-memory `TestServer` |
| `tests/Rimlink.Client.Tests` | Тесты слоёв `Net` и `State` клиента без RimWorld | xUnit |

Дополнительно: `mod/` (About.xml, Defs, Languages `en`/`ru`, Textures —
всё своё), `deploy/` (Dockerfile, docker-compose.yml, `appsettings.example.json`),
`docs/`, `scripts/` (сборка мода).

Границы ответственности:
- Сервер — единственный источник правды для всего общего: аккаунты, мир,
  объекты на карте мира, чат, модпак. Клиент ничего общего не меняет напрямую,
  только отправляет запросы.
- Клиент владеет только своей колонией: симулирует её, сохраняет локально и
  отправляет сейв на сервер.
- Каждый вызов сервер проверяет по сессии: кто вызывает, есть ли право,
  не превышен ли лимит частоты.

## 3. Сеть и аутентификация

### Транспорт

Один TCP-порт (по умолчанию 25560), HTTP/2 поверх TLS, gRPC. Без TLS сервер
не стартует. Сертификат:
- либо свой (например Let's Encrypt для домена), пути в конфиге;
- либо самоподписанный, который сервер генерирует при первом запуске.
  Клиент при первом подключении показывает отпечаток, после подтверждения
  запоминает его для этого сервера (pinning). Смена отпечатка — явное
  предупреждение, а не тихий отказ.

Запросы — унарные вызовы с ответом. События сервера — один серверный стрим
`Events.Subscribe`, открываемый после входа; по нему идёт всё, что меняется:
чат, список онлайн, объекты мира, уведомления. Keep-alive обеспечивает
HTTP/2 (`KeepAlivePingDelay` 30 с, таймаут 10 с), своих пакетов нет.

Все сообщения — protobuf. Версия протокола — целое число в рукопожатии;
новые сервисы добавляются новыми `.proto`-файлами, существующие поля не
меняют смысла. События типизированы через `oneof`, неизвестный тип клиент
пропускает.

### Вход

1. `Auth.Login` с одним из:
   - билетом Steamworks (`GetAuthSessionTicket`). Сервер проверяет его через
     Steam Web API `ISteamUserAuth/AuthenticateUserTicket` (ключ Web API в
     конфиге) и получает SteamID. Аккаунт создаётся при первом входе;
   - логином и паролем, если в конфиге включён `Auth:AllowPassword`.
     Пароль идёт в чистом виде внутри TLS, на сервере хранится Argon2id с
     солью. Регистрация — отдельный вызов, включается тем же флагом.
2. Проверки по порядку: версия протокола; бан аккаунта, SteamID или IP;
   модпак (раздел 6); лимит игроков (считаются только вошедшие); пароль
   сервера, если задан. Каждая отказывает кодом gRPC с машиночитаемой
   причиной и текстом.
3. Сервер выдаёт токен сессии (случайные 32 байта), живущий до отключения.
   Все остальные вызовы несут его в метаданных `authorization`.
4. Один аккаунт — одна активная сессия: новый вход вытесняет старую с
   событием «вход с другого места».

### Защита

- Лимиты размера сообщений: сейв до 64 МБ (передаётся кусками по 1 МБ),
  остальные вызовы до 1 МБ.
- Лимит частоты на метод и аккаунт (token bucket), например чат 5 за 5 с,
  сейв 3 за 30 с (передача, доставка и выход могут сохранять подряд). Превышение — `RESOURCE_EXHAUSTED`, не разрыв.
- Не более 5 неавторизованных соединений с одного IP, таймаут на вход 30 с.
- Любая ошибка обработчика логируется с идентификатором запроса и отвечает
  `INTERNAL` без деталей; соединение других игроков не затрагивается.
- Имена (игрок, фракция, поселение) проверяются на сервере: Unicode-буквы,
  цифры, пробел, `_-.'`, длина 2–32, без управляющих символов. Имена никогда
  не становятся путями: файлы и каталоги именуются по числовым ID.

## 4. Мир и поселения

### Мир

Первый админ создаёт планету в своём клиенте (сид, размер, покрытие,
сложность, сценарий, рассказчик). Клиент отправляет `World.Create` только с
параметрами генерации и списком тайлов, занятых НПС-поселениями. Все клиенты
генерируют планету из того же сида, поэтому рельеф, НПС-фракции и их
поселения совпадают. Сервер хранит поверх этого свой слой: объекты игроков.

Пока мира нет, входить может только админ; остальные получают код
`WORLD_NOT_CREATED`. Пересоздание мира — админ-операция с подтверждением,
она архивирует все сейвы и объекты.

### Объекты мира

Таблица `world_objects` общая для всех типов: `id`, `type` (в ядре только
`settlement`), `owner_player_id`, `tile`, `name`, `created_at`, `payload`
(protobuf-байты, зависящие от типа). Караваны и участки добавятся новыми
типами без изменения схемы.

### Поселение

`World.Settle(tile, name)`: сервер проверяет, что тайл свободен (ни НПС,
ни игрок), у игрока меньше `MaxSettlementsPerPlayer` (по умолчанию 1),
имя допустимо. Записывает объект и рассылает событие `WorldObjectAdded`.
`World.Abandon(objectId)` — только владелец или админ, событие
`WorldObjectRemoved`. Чужие клиенты ставят на карту объект «поселение
игрока» с фракцией этого игрока (имя, цвет из профиля); взаимодействия с
ним появятся в подпроекте 2.

Игрок без поселения при входе попадает в обычный выбор места высадки с
подсветкой занятых тайлов.

## 5. Сейвы

- Клиент сохраняет игру как обычно в `Saves/Rimlink/<server-id>/`, затем
  отправляет файл на сервер: сжатие zstd, поток кусками по 1 МБ, вызов
  `Saves.Upload`. Отправка идёт после записи файла в фоновом потоке и не
  блокирует игру дольше обычного сохранения.
- Триггеры отправки: автосохранение, ручное сохранение, выход в меню,
  основание и покидание поселения.
- Сервер хранит версии: последние 10 и по одной в день за 7 дней. Метаданные
  в `save_versions` (игрок, номер, время, размер, хеш, игровой тик), блоб в
  `data/saves/<player_id>/<version>.rws.zst`. Запись атомарная: во временный
  файл, затем переименование.
- При входе сервер отдаёт последнюю версию (`Saves.Download`), клиент
  загружает её. Копия сервера главная; локальный файл — кэш. Если у клиента
  есть локальный сейв новее серверного (сервер его не видел из-за обрыва),
  клиент предлагает отправить его.
- Откат: админ выбирает версию, сервер помечает её текущей; игрок получит
  её при следующем входе, а если он онлайн — уведомление с просьбой
  перезайти.
- Проверки сервера над сейвом: после распаковки zstd это XML-файл `.rws`
  RimWorld (сама игра сейвы не сжимает), сид мира совпадает,
  имя фракции игрока совпадает с профилем, размер в лимите. Полный разбор
  сейва сервер не делает; всё общее защищено тем, что живёт на сервере.

## 6. Модпак

Сервер хранит упорядоченный список `modpack_entries`: `position`,
`package_id`, `version` (из `About.xml`), `workshop_id` (если есть), `url`
(если не из Steam), `kind` (`required`/`allowed`). Задаётся админом из
клиента («Сделать мой набор модпаком»), через CLI или REST.

При входе клиент отправляет свой список `package_id`+`version`. Сравнение
только по ним: ни по именам папок, ни по `ModsConfig.xml`, ни по хешам
настроек, ни по источнику (Steam или локальная папка). Порядок не
сравнивается на входе, но входит в список сервера. При несовпадении ответ
содержит дифф: недостающие, лишние, с другой версией. Клиент показывает окно
с действиями:
- «Подписаться в Steam» — на все недостающие с `workshop_id` разом через
  Steamworks `SubscribeItem`;
- «Открыть ссылку» для записей с `url`;
- «Выставить порядок как на сервере» — переписывает `ModsConfig.xml` с
  резервной копией `ModsConfig.rimlink-backup.xml`;
- «Перезапустить».

Настройки модов сервер не сверяет. Админ может приложить к модпаку
рекомендуемые файлы настроек (`Mod_*.xml`); клиент предлагает применить их с
резервной копией, но вход от этого не зависит.

## 7. Чат

Один общий канал и личные сообщения. Сервер хранит последние 500 сообщений
(`chat_messages`), отдаёт 50 при входе. Ограничения: длина 500 символов,
5 сообщений за 5 с, мут от модератора. Rich-text-теги экранируются на
клиенте при отображении. Системные события (вошёл, вышел, основал
поселение, объявление сервера) идут тем же стримом отдельными типами;
клиент решает, что показывать.

## 8. Администрирование и наблюдаемость

Роли: `player`, `moderator` (кик, мут, модерация чата), `admin` (всё).
Первый админ назначается в конфиге по SteamID или логину.

REST на том же порту под `/api/admin/*`, авторизация токеном из конфига
(`Admin:ApiToken`), для веб-панели и Discord-бота в будущем — тот же API.
Команды в игровом чате через `/` транслируются в те же операции с ролью
отправителя. Операции ядра: игроки онлайн, кик, бан и разбан (аккаунт,
SteamID, IP; причина и срок), мут, откат сейва, сброс игрока (архивирует
его данные), модпак, объявление, сохранить всё, выключение с
предупреждением за N минут. Все действия пишутся в журнал `admin_actions`
(кто, когда, что, над кем).

Логи структурные (Serilog) в консоль и файл с ротацией. `/health` для
Docker и мониторинга. Метрики Prometheus на `/metrics`: игроков онлайн,
вызовы и ошибки по методу, время ответа, размер и количество сейвов.

Хранилище: SQLite через EF Core, миграции применяются при старте.
Таблицы: `accounts`, `sessions`, `bans`, `players`, `world`,
`world_objects`, `chat_messages`, `modpack_entries`, `save_versions`,
`admin_actions`. Бэкап: `rimlink-tools backup` делает снимок базы
(`VACUUM INTO`) и блобов одним архивом; расписание в конфиге; восстановление
`rimlink-tools restore`.

## 9. Клиент

Четыре слоя с чёткими границами:
- `Net` — обёртка над gRPC: подключение, вход, стрим событий, переподключение
  с повтором. Ничего из Verse не знает, тестируется отдельно.
- `State` — локальная копия общего состояния (игроки онлайн, объекты мира,
  чат) и очередь входящих событий. Меняется только сетевым потоком.
- `Game` — всё, что трогает RimWorld: применение состояния к миру, объекты
  чужих поселений, сейв. Работает только на главном потоке: события из
  `State` забираются раз в кадр из `GameComponent.GameComponentUpdate`.
  Обращения к `Find.*`, `Current.Game`, окнам из сетевых потоков запрещены.
- `UI` — окна: подключение, список серверов (из локального конфига), чат,
  игроки, модпак, админ-команды. Все строки через `Translate()`, переводы
  `en` и `ru`.

Harmony-патчи только там, где без них нельзя, каждый — postfix или prefix с
условием, без безусловного `return false`: после записи сейва (отправка),
основание и покидание поселения, кнопка «Мультиплеер» в главном меню.
Одиночные сейвы и настройки игрока мод не трогает.

Поток входа: главное меню → «Мультиплеер» → выбор сервера → подключение и
вход → при несовпадении модпака окно с диффом → загрузка сейва с сервера
или выбор места высадки → игра. Любая ошибка — окно с текстом и кнопкой
«Повторить»; окно ожидания всегда отменяемо.

Переподключение: при обрыве игра ставится на паузу, показывается баннер,
попытки с нарастающей задержкой (1, 2, 4 … до 60 с) в течение 2 минут,
затем предложение выйти в меню с локальным сохранением. Неотправленный
сейв уходит при следующем входе.

Сборка: компиляция против `Assembly-CSharp` и `UnityStubs` установленного
RimWorld 1.7 (`-p:RimWorldDir=...`), скрипт собирает папку мода; DLL gRPC и
protobuf кладутся рядом с `Rimlink.Client.dll`.

## 10. Обработка ошибок

- Сервер: ошибки валидации — `INVALID_ARGUMENT`, прав — `PERMISSION_DENIED`,
  состояния (тайл занят, мира нет) — `FAILED_PRECONDITION` с кодом причины
  в деталях; неожиданные — `INTERNAL` с идентификатором в логе.
- Клиент: показывает причину человеку, по коду выбирает действие
  (повторить, открыть модпак, выйти в меню). Ошибка применения события к
  игре логируется и не останавливает обработку следующих событий.
- Сейв с ошибкой проверки отклоняется с причиной; предыдущая версия
  остаётся текущей.

## 11. Тестирование

- Сервер: юнит-тесты правил (вход, модпак-дифф, лимиты, права, валидация
  имён); интеграционные через gRPC in-memory на сценарии: регистрация и
  вход, создание мира, поселение, сейв с откатом, чат с лимитами, бан.
- Клиент: `Net` и `State` тестируются без RimWorld; слой `Game` и UI —
  ручной чек-лист в игре (`docs/manual-checklist.md`).
- CI (GitHub Actions): сборка `Protocol`, `Server`, `Tools` и тесты на
  каждый push; Docker-образ в GHCR по тегу. Клиент в CI не собирается
  (нужна игра).

## 12. Спайк и порядок работ

Первая задача плана — спайк: минимальный мод с `Grpc.Net.Client`, который
из главного меню RimWorld 1.7 вызывает тестовый gRPC-сервер по TLS и
получает ответ. Если HTTP/2 внутри игры не работает, запасной вариант —
собственный протокол поверх `SslStream` с MessagePack; он меняет только
слой `Net` и транспорт сервера, остальной дизайн сохраняется.

Порядок: спайк → каркас репо и CI → протокол и сервер (аккаунты, вход,
баны) → мир и поселения → сейвы → чат → модпак → админ-REST и CLI → клиент
по слоям → Docker и документация.

## 13. Вне рамок ядра

Передачи и торговля, караваны, рынок, визиты и рейды, веб-панель,
Discord-бот, симуляция колоний на сервере, поддержка RimWorld 1.6.
