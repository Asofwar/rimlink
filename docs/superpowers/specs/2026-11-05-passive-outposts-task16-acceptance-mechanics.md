# Passive outposts: механика изолированной Task16 acceptance

**Статус:** механическое уточнение утверждённых G1–G7; не реализация, не code review, не итоговый review и не свидетельство прохождения acceptance. Все проверки ниже — требования, **NOT RUN в этой документационной задаче**. Реализацию выполняет основная Sol; Astra уточняет контракт. Runtime Astra подтверждён собственным `turn_context`.

**Основание:** [основная спецификация §§3.2,5,9,11](2026-11-03-passive-outposts-design.md), [admin readiness §§7.1–7.2](2026-11-05-passive-outposts-admin-readiness-clarification.md), [Task16 и G1–G7](../plans/2026-11-03-passive-outposts.md). Пользователь разрешил завершение задачи и реальный отдельный стенд G1–G7; выбрана версия **0.9.0**. Browser-check — **SKIPPED BY USER**, не PASS и не исключение для остальных проверок. Product остаётся OFF; merge/push/tag/release/deploy не разрешены. Единственный итоговый review всей ветки выполняется после G1–G7; эти seams и их проверки входят в его пакет.

## 1. Граница механического изменения

Разрешены только недостающие способы воспроизводимо наблюдать уже утверждённое поведение: отдельный вызов настоящего physical provisioning, управляемое время private composition и ожидание на точных существующих границах операций, включая offline restore hooks для G6. Они не меняют gameplay, цены, лимиты, production arithmetic, custody, snapshots, recovery, authority, grants или readiness. Неизвестный результат остаётся неизвестным. Никаких прямых записей Q/F, работников, receipts, rows, checkpoints или успешных ответов ради сценария.

Стенд сохраняет контракт §7.2: принадлежащие этому запуску канонические непересекающиеся пути, отдельные DataDir/anchor/backup/game/savedata, собственные процессы и loopback endpoint, реальные backend/qualification/metadata/lock проверки. Отсутствие GABS в сессии само по себе не отменяет сценарий: допустим проверенный semantic protocol уже установленного RimBridgeServer к своим экземплярам, без изменения общей MCP-конфигурации. Запуск/закрытие/аварийное завершение своих игровых процессов — только разрешённым CUA Driver с повторной проверкой принадлежности PID и экземпляра. Недоступная граница отмечается NOT RUN, а не имитируется записью в БД.

## 2. Отдельный offline physical provision

**Интерфейс:** отдельная явно вызываемая команда dev acceptance executable `provision <stand.json>`; не часть `prepare`, `run`, startup, GET/preview или normal CLI. Её единственный storage effect — вызов существующего `OutpostAnchorStore.Provision()` с реальными options/backend/path checks. Она не вызывает Initialize, не создаёт logical authority/head/world, не ставит Ready и не присваивает qualification.

До вызова: проверить owned stand descriptor и изоляцию; получить существующие cross-process ownership/storage fences без изменения их порядка; подтвердить остановленный сервер и положительно пустую новую область состояния. Допускаются только известные файлы подготовки стенда, не прежняя игровая/authority история. Нельзя принимать отсутствие одного anchor-файла за доказательство пустоты. Наличие любого старого/частичного authority store, protected history, restore marker, неизвестных state files или занятого fence — отказ до provisioning. Процедура не обслуживает восстановление потерянного anchor и не удаляет остатки неудачи.

После успешного настоящего Provision проверить его штатным read-only способом: qualified physical store с singleton Record=NULL, без logical authority. Повторный вызов не перезаписывает store: штатная CreateNew-семантика сохраняется. Failure сохраняет файлы для диагностики, не делает cleanup/retry-overwrite. Последующий запуск и явная logical initialization проходят обычные проверки.

**Почему/цена ошибки:** без явного входа стенд нельзя штатно подготовить; автоматический fallback превратил бы потерю anchor в ложный первый запуск. Поэтому разрешён только новый положительно пустой owned stand.

## 3. Время только private composition

**Интерфейс:** узкое internal свойство/factory `OutpostTimeProvider` существующего `IOutpostAcceptanceComposition`, потребляемое при создании только существующего `OutpostClock` в isolated host. Это fixture источника времени outpost, не глобальная замена зарегистрированного TimeProvider: auth/trade/live/hygiene, транспортные deadlines и остальные службы сохраняют свои обычные System часы. Системное время ОС не изменяется. Нормальная composition безусловно создаёт OutpostClock с `TimeProvider.System`. Dev-owned controller предоставляет bounded `Observe` и `Advance(positive duration, step identity)`; названия здесь описывают контракт, не готовые исходники. Управление — только private локальным каналом owned harness, не новой normal REST/gRPC API, env/config опцией, reflection override или provider из data/backup.

Provider имеет постоянную положительную TimestampFrequency, монотонный GetTimestamp, согласованные атомарные readings и проверку переполнения. Для ускорения работающего процесса положительный шаг двигает simulated monotonic elapsed и согласованный UTC на одинаковую длительность: один UTC jump не производит ресурс, поскольку настоящий OutpostClock использует UTC старта + monotonic elapsed. Обычный ход времени между шагами сохраняется. Не заменять OutpostClock или production/settle алгоритм; не делать ускорение таймеров неявным побочным эффектом. Поведение timers явно определить и проверить, включая cancellation; timeout ожиданий harness измерять реальными монотонными часами.

Каждый шаг фиксирует stand/run/process identity, последовательный step ID, причину, duration, simulated UTC/timestamp/frequency до и после, отдельно реальные UTC harness и наблюдённый результат. Повтор step ID не добавляет время второй раз. Нулевые/отрицательные, overflow, чужие либо закрытые run/owner, неизвестная qualification или утрата isolation — отказ без шага. Исходный UTC anchor fixture (UTC старта + начальный monotonic timestamp/frequency) записывается до запуска OutpostClock и сверяется с первым Sample; после Advance сверяются оба readings и фактический Sample. Здесь clock anchor — временная опорная точка fixture, не внешний OutpostAnchorStore: последний никогда не редактируется ради времени. При restart новый provider получает явно записанное UTC начала не раньше последнего simulated UTC плюс отдельно объявленный downtime (он может быть нулевым); monotonic origin нового процесса независим. Проверяются непрерывность run log и отсутствие отрицательного межпроцессного интервала относительно настоящих outpost checkpoints; несовпадение остаётся диагностикой/отказом, не исправляется правкой checkpoint. Контрольная запись стенда не является domain/anchor/backup authority и не импортируется в product.

**G3:** реальная колония создаёт outpost обычным путём; реальные checkpoints, offline/restart и положительные интервалы дают cap1000 обычным settle. Затем дополнительный интервал при полном складе, настоящий claim и settle того же/следующего известного момента доказывают отсутствие backlog. Сохранить Q/F, rates, моменты и реальные parcel/item counts. Сверить повтор settle без шага; отдельно сохранить обычный restart и ограничения archive/bulk-restore gap. Быстрые часы не заменяют реальные reconnect/cancellation проверки и не снимают двухклиентную проверку.

**Почему/цена ошибки:** вместо многочасового ожидания меняется только источник времени. Несогласованные UTC/monotonic или незаписанный restart дали бы ложное доказательство cap/downtime; поэтому обе шкалы и каждое продвижение наблюдаемы.

## 4. Pause seams и точные fault boundaries

**Интерфейс:** internal по умолчанию no-op асинхронный checkpoint `Reach(boundary, immutable run/operation context, cancellation)`; dev companion может только `Arm`, `Observe`, `Release`, `Disarm` конкретный one-shot checkpoint. Контекст связывает stand/run, PID/экземпляр, game identity, connection/login/session, owner/scope и исходный operation/request ID. Никаких произвольных delegates, изменения request/result или generic memory setters. Normal artifact не подключает controller и не приобретает authority через клиентский флаг.

Армирование требует проверенного актуального IsolatedAcceptance host/stand и собственного game/session; одного dev mode, loopback адреса или самозаявленного bool недостаточно. Привязка действует только на эту сессию и endpoint, не расширяет login capability и не является serialized qualification. При отсутствии достоверной привязки instrumentation закрыта. Release/последующее действие повторно проверяют game/session/owner; cancellation, menu/load/visit, disconnect/relogin, смена endpoint либо disposal инвалидируют pending arm. Старый callback не продолжает removal/commit в новой игре и не выполняет компенсацию. Ожидание не блокирует main thread, bridge dispatcher или сетевой event loop; не добавляет await внутрь атомарного main-thread удаления партии. Ошибка/отмена идёт через существующий recovery/outbox путь.

Минимальные различимые точки G2 (при необходимости один checkpoint покрывает соседние границы, но evidence отмечает фактически достигнутое):

1. Перед exact pre-save; после durable local capture/outbox и до подтверждённого server acceptance; после принятого exact pre-save, до Prepare send.
2. Prepare отправлен, ответ неизвестен; отдельно доказанный durable Prepared на сервере до получения ответа; после проверенного Prepared, до повторной проверки каравана и removal.
3. После всей существующей атомарной main-thread removal/receipt фазы, до post-save. Не добавлять yield между пешками и не принимать partial removal за NoRemoval. Изменение caravan/skill/status проверять перед этой фазой через обычную revalidation.
4. Post-save локально durable, ещё не подтверждён сервером; после принятого exact post-save и до Commit send.
5. Commit отправлен, ответ неизвестен; отдельно durable Committed до получения ответа; после проверенного Committed до локального outbox cleanup, затем после cleanup как контроль.

Для каждого applicable fault записать фактические local/save/outbox/server/anchor состояния и точные IDs/hashes, затем выполнить cold restart либо scoped net drop/reconnect с query/replay **того же** operation. Не объявлять клиентский pause после завершившегося RPC доказательством потерянного ответа. Lost-reply случаи требуют наблюдаемого настоящего durable server completion и удержанного/потерянного transport response; использовать узкий private transport/companion hook существующего вызова, без подделки статуса или повторного business execution. Если имеющаяся instrumentation не может доказать эту грань, сценарий остаётся NOT RUN. Так же точные save sub-boundaries требуют настоящего SaveSync/upload наблюдения, а не предположения по имени caller checkpoint.

Для G3 receipt-before-ack разрешён такой же узкий pause в существующем delivery flow после реального durable receipt save, до ack: reconnect должен выполнять ack-only. Смена game/menu/visit при ожидающем callback и частичная/неподдержанная выдача проверяются реальным обычным путём; никаких fabricated receipt/acceptance или очистки fencing. Этот seam не добавляет новую delivery policy.

**Выбор реализации:** предпочтительны минимальные явные no-op seams на уже существующих async границах. Только dev Harmony hooks допустимы вместо них, если точно наблюдают те же points на конкретном build, не зависят от хрупкого случайного timing и не меняют порядок, atomicity, exceptions/cancellation. Если это нельзя доказать, не подменять точку «примерно соседней» ради меньшего diff.

**Почему/цена ошибки:** pauses делают crash/drop воспроизводимыми; неправильное место или новый межпешечный yield меняют саму тестируемую операцию. Evidence обязана отделять send, server durable completion, received reply, local durable save и accepted save.

### 4.1. G2: received-before-service отдельно от lost reply

Допустимы ровно два дополнительных private server-entry pause для настоящих Prepare и Commit: request уже принят и прошёл обычную authentication/authorization, но соответствующий business service ещё не продолжен. Они связываются с точными run/session/owner/request ID и intent digest, не принимают решение об eligibility и не заменяют service guards. До них не создаётся business effect этого вызова. Ожидание асинхронное, до service locks/transaction, без изменения auth и сетевого диспетчера; normal composition оставляет no-op. После release действуют исходный cancellation и все штатные проверки актуальности сессии и evidence.

Observe подтверждает именно reached-entry, не durable Prepared/Committed и не глобальное отсутствие результата: другой replay того же request мог уже завершиться. Запись включает попытку вызова и наблюдаемый original operation; не дедуцировать negative custody из «ещё не вызван service». Net drop/cancel здесь проверяет in-flight RPC без durable completion этой попытки, а отдельный after-durable-before-transport seam проверяет lost reply. При последующем query/replay решение всегда принимает настоящий service по оригинальным ID. Обязательные cases: entry pause→drop, entry pause→release, cancel/session change→stale release refused, concurrent exact replay/known terminal outcome и after-durable lost reply как отдельная строка evidence. Никаких fabricated replies или перевода terminal обратно в Prepared/Unknown.

### 4.2. G3: реальная частичная выдача и unsupported defs

Это уточнение границы теста, не review реализации. Существующие `receipt-local-durable` и `receipt-accepted-before-ack` стоят после materialization и пригодны для ack-only, но не доказывают partial spawn. В текущем пути `OutpostIncoming.Materialize` сначала создаёт объекты всей партии, затем одним штатным `DropPodUtility.DropThingsNear` передаёт их в игру; исключение после завершения этого вызова означало бы полную выдачу без receipt, а не частичную. Созданные в памяти, но ещё не размещённые объекты также не считаются физически выданными.

**Реальная fixture:** получить обычным claim настоящий resource parcel с несколькими stackLimit-стеками (например, утверждённый cap1000), либо обычным recall несколько workers; исходные IDs, payload digest, quantities и expected stack partition записать до выдачи. Server BeginDelivery, durable client SpawnStarted и permit остаются настоящими. Предпочесть воспроизводимый штатный placement failure при наличии доказанного способа. Если его нет, разрешён ровно один dev-only fault `delivery-placement-fail-after-prefix`: синхронно наблюдать внутреннюю фактическую placement boundary штатного drop алгоритма и бросить ограниченную fixture exception после размещения непустого собственного prefix, пока хотя бы один исходный объект ещё не размещён. Контракт не разрешает разбить production `DropThingsNear` на несколько вызовов, поменять его алгоритм, подделать результат или просто бросить после полного spawn.

Для такого hook Sol сначала устанавливает точную внутреннюю границу по фактической сборке игры; пригоден узкий dev Harmony hook с подтверждёнными signature/build и semantics. Нельзя угадать метод по названию. Hook ограничен текущим синхронным вызовом protected Materialize и точными object references партии (не Thing equality по ID), действительными stand/run/game/map/session, parcel/request/scope/payload digest и one-shot arm. Не перехватывать другие pods, обычные deliveries или чужие pawns. На main thread нет ожидания, сетевого вызова или нового async yield; по достижении проверенного prefix — observation и немедленная fixture exception через обычный catch, без receipt/save/ack/cleanup/retry из hook. Cancellation, смена игры/сессии, утрата verified binding или выход из вызова снимают arm; stale callback ничего не выполняет. Ошибка observation не позволяет объявить partial доказанным.

**Доказательство partial:** до exception зафиксировать исходный count/quantity и actual placement/containment каждого объекта: spawned на map либо реально передан существующему игровому pod/container на этом map с его identity; отдельно оставшиеся неразмещённые references. Сосчитать уникальную партию, не двойной подсчёт pod+contents. Необходим строгий факт `0 < physically placed < expected total`; для quantities и worker UUID указать фактическое распределение. Private evidence сохраняется до обычного AbortToMenu, без попытки сохранить повреждённую колонию. Затем наблюдать настоящий `SaveSync.WritesBlocked`, обычный abort/recovery, отсутствие принятого materialization receipt/ack и сохранённые server parcel/custody/delivery evidence. Hook не устанавливает эти flags и не вызывает abort сам. Reload/reconnect использует оригинальный canonical/outbox; не выдаёт второй prefix, не делает guessed local return. Если нельзя надёжно найти реальную частичную границу, case остаётся NOT RUN; full-spawn-before-receipt записывается отдельным case.

**Unsupported defs:** предпочтительна настоящая parcel fixture со штатно объявленным def, отсутствующим у получателя, если её допускают неизменные login/modpack/manifest gates. Несовместимый client, остановленный раньше delivery, доказывает только тот ранний refusal; ради теста эти gates не обходить. Если настоящий missing-def случай недостижим на квалифицированной паре, допускается отдельный явно помеченный fault-injection case: one-shot deny-only результат проверки наличия ровно одного def, реально заявленного выбранным настоящим parcel, внутри существующего `Incoming.MissingDefs`/`BlobDefs.Missing` lookup при protected validation. Это временный dependency-unavailable result только в данном вызове, не изменение DefDatabase, blobs, manifest, payload digest или совместимости всей игры; нельзя подменять готовый DeliveryDecision, создавать отсутствующий def либо принуждать Allow. Он использует тот же verified stand/game/session/parcel context, снимается после одного срабатывания и запрещён в product. В evidence отдельно указывать actual missing-definition fixture либо injected availability failure: второе не выдавать за проверку реального cross-mod login.

Missing-def refusal наблюдается на настоящем validation path до materialization: нулевой физический spawn, нет BeginDelivery/receipt/ack от этой отказавшей попытки, server имущество сохранено. Это **не** partial spawn. Проверить отдельно удержание delivery, RecoveryRequired и разрешённость save/game mutations: `held`/сообщение об ошибке не равны `WritesBlocked`. Требование G3 о блокировке небезопасных writes не снимается; если нужная блокировка фактически отсутствует, фиксируется failing acceptance с точным pre-spawn/post-spawn состоянием для исправления основной Sol, а не новый policy от Astra или PASS по наличию сообщения. Для уже начатой частичной выдачи обязательна именно реально наблюдаемая write fence до ухода в меню.

**Negatives/контроль:** disarmed/product no-op; wrong parcel/def/request/map/session/run не срабатывают; пустой prefix или вся партия не удовлетворяют partial; unrelated placement неизменён; duplicate arm не бросает повторно; stale release/cancel не порождают spawn. В контрольном успешном прогоне та же настоящая форма партии полностью размещается и проходит штатные save/accept/ack. Private fault evidence не становится authority и не импортируется в saves/receipts. Новые hooks входят в обычные automated gates и единственный финальный review после G1–G7; это не waiver и не результат проверки.

## 5. G6: dev-only offline restore adapter

**Интерфейс:** отдельный offline adapter того же `Rimlink.OutpostAcceptanceHost` к существующим typed `OutpostRestoreProcedure.ExecuteAsync`, `ResumeAsync`, `BackoutAsync` и inspection. Он передаёт реальный исходный typed request/journal selection и подключает существующий internal `Checkpoint: Action<string>`. Имена команд — деталь Sol; контракт не добавляет switches к normal CLI, runtime HTTP/gRPC или product configuration и не меняет restore APIs/source evidence. Выполнение остаётся настоящей stopped-server процедурой с настоящими backend, executor/schema, ownership, restore и storage locks.

**Request codec:** существующий `OutpostRestoreJournalCodec.Freeze(RestoreRequest)` формирует проверяемый canonical RestoreSelection, а public `SelectionDigest`/`BackoutDigest` остаются единственным источником соответствующих confirmation digests. Сейчас обратного готового typed-request decoder у этого codec нет; не считать Encode journal взаимозаменяемым с CLI request JSON. Минимальный выбранный путь — выделить существующий bounded request codec из `BackupCommands` в небольшой общий helper для normal CLI и dev adapter, сохранив wire representation и все ограничения byte-for-byte по смыслу существующего формата: Web JSON, MaxDepth=32, запрет duplicate/unknown properties, required/nullability checks, request 1..32MiB; protobuf ByteString — массив целых byte 0..255 длиной не более 4096, не новая Base64-форма. Не копировать второй расходящийся parser, не применять reflection injection или permissive fallback. Типы RestoreRequest/RestoreBackoutRequest, exact selection freezing, исходные confirmation fields и Resume/journal semantics не меняются; shared codec не создаёт новой confirmation/grant/auth процедуры. При выборе вместо extraction явного адаптера frozen selection→typed request он обязан восстанавливать только исходные доказанные поля, проверять exact round-trip SelectionDigest и не обновлять stale inspection по текущему состоянию; отсутствие доказуемого round-trip — отказ, не догадка.

Перед запуском заморозить и сверить exact owned stand descriptor/digest, run/process identity, действие Execute/Resume/Backout, канонические request paths и request commitment, а для continuation — точный существующий journal и его identity. Source archive, target, anchor, journal/staging/retained roots должны принадлежать отдельному стенду и отвечать существующим isolation/path rules; ни произвольные пути из control channel, ни shared/production состояние не допускаются. Сервер этого стенда остановлен, ownership lock удерживается; busy/unknown owner, изменившийся descriptor/request, неподтверждённый backend или требуемый executor — отказ. NoActiveWorld, Maintenance или незавершённый restore могут быть нормальным **объектом** Resume/Backout: adapter не требует фиктивного Ready, но никогда не снимает соответствующие настоящие fences и не ослабляет prerequisites.

**Controller:** bounded one-shot `Arm(exact hook, exact path/occurrence, run/action binding)`, `Observe`, `Release`, `Cancel`. При path-bearing hook путь берётся из настоящего callback и сверяется с frozen selected inventory; это observation, не команда переместить указанный пользователем файл. Только известные literal hook names и точное ожидаемое occurrence, без regex/wildcard «любой путь», reflection или произвольного кода. Ограничены размер команды/записи, число arms и ожидание; IDs делают повтор Release/Cancel идемпотентным, чужой/stale ID не действует.

Синхронный `Action<string>` вправе блокировать **только отдельный restore worker** на достигнутой существующей границе, сохраняя штатные locks и порядок операций. Controller работает независимо и остаётся доступным для Observe/Release/Cancel; не вызывает restore повторно, не захватывает его locks и не выполняет параллельные DB/file mutations. Observe читает опубликованный private event, не открывает заблокированный mutable store ради снимка. Не делать async-void callback или fire-and-forget continuation: restore не пересекает armed boundary до разрешённого Release. Cancel/timeout/controller loss будит worker только для штатной отмены/ошибки, не означает success, rollback, Backout или cleanup. Если cancellation в этой фазе по существующему контракту требует завершить защищённый шаг, сохраняется именно его семантика; жёсткое прерывание — отдельное завершение собственного CLI процесса.

**Evidence перед ожиданием:** callback сначала долговечно записывает и читает обратно bounded private reached-event: последовательность, run/PID/start identity, stand/request commitment, action, точное hook name/path/occurrence, известную journal identity/phase и реальные UTC/монотонное время harness; затем объявляет reached и ждёт. Файл находится в заранее проверенном собственном evidence root вне DataDir/anchor/source/staging/retained/journal replacement trees, не входит в backup/authority и не заменяет настоящий restore journal. Если запись не удалась, граница не объявляется доказанно достигнутой; процедура не продолжается «для удобства теста». Не выдумывать journal phase из имени hook и не считать private event доказательством commit, если hook стоит раньше него.

**Обязательная fault matrix:** для каждого реально выбранного file-switch path/действия пройти hard interruption после `AfterSwitchPlanned:<path>`, `AfterSwitchEffect:<path>`, `AfterSwitchCompleted:<path>`, а также `AfterInstalledVerified`. Включить реально возникающие install/replace/remove ветви; если ветвь отсутствует в fixture, отметить это и подготовить подходящий штатный сценарий, не редактировать journal вручную. Остальные применимые restore boundaries не исчезают: настоящий `AfterJournalCreated`, `AfterExternalFence`, stage/retain hooks, `AfterStagedVerified`, `AfterOldSetRetained`, `AfterMainPlanWritten`, `AfterMainPlanBound`, `AfterMainPrepared`, `BeforeSchemaMigration`/`AfterSchemaMigration` при additive пути, `AfterMainDatabaseCommit`, `AfterMainCommitted`, `AfterCompletionCommitted`, `AfterRestorePublication`. Для требуемого Backout также использовать существующие `AfterBackoutPlanned/Effect/Completed:<path>`, `AfterBackoutCurrentFile:<path>`, `AfterBackoutStarted`, `AfterBackoutPublication`, `AfterBackedOut`; previous-anchor ветвь использует свой существующий hook, если она применима. Неприменимый hook фиксируется с причиной, а не как PASS.

Каждый crash запускается на собственной согласованной исходной timeline/fixture через штатную подготовку. После durable reached-event harness проверяет принадлежность PID/start identity и жёстко завершает только свой restore CLI worker процесс обычным CLI harness; игровые GUI процессы по-прежнему управляются только CUA Driver. Restart inspection и **явно выбранный** Resume либо Backout используют исходный journal/request и настоящие validators. Проверить actual files/hashes, external marker, main head/schema/restore record и original evidence; lag между file effect и journal phase устраняется только существующей процедурой. Не переписывать selection, не переинициализировать authority, не очищать journal/marker и не рестартовать server автоматически ради превращения Maintenance в успех.

**Проверяемые negatives/controls:** незапущенный arm не останавливает обычный путь; точный release продолжает один раз; другой path/occurrence/run/journal, changed descriptor/request и foreign PID не управляют worker; evidence write failure не выдаёт reached; cancel/controller loss не создают successful result; занятый stand/server и product invocation отказывают. Нужны реальные kill→inspect→same-journal Resume и допустимый Backout, включая effect-before-record gap; несовместимый executor на pre-DDL и повреждённый/чужой journal остаются refused/fenced. DB/external completion и publication подтверждаются отдельно; crash не означает разрешение ни на Backout, ни на новый Execute. Ни failure, ни Maintenance не становятся автоматической repair ветвью.

Codec cases: прежний CLI request/inspection с Anchor ByteString читается обеими оболочками с теми же typed values и selection/backout digest; изменённые confirmation, scope/paths/mode/previous-anchor facts не переутверждаются. Duplicate/unknown/missing fields, неверная byte-array форма/элемент/размер, depth и общий размер за пределом отказывают до restore. Стандартный CLI output/request round-trip и старые journal/intent bytes сохраняются; control event никогда не становится input evidence для самого restore.

**Почему/цена ошибки:** существующие hooks дают точную фазу без изменения production restore. Без отдельного worker/controller зависший callback блокировал бы управление; без долговечной private reached записи нельзя доказать, какую фазу прервали. Эти события служат только test evidence. Process kill не является power-loss proof; offline adapter не является новым recovery policy.

### 5.1. Последовательные coherent fixtures и missing-path case

«Собственная согласованная timeline/fixture» не требует нового installation/каталога для каждой строки fault matrix. Допустим один собственный stopped stand с настоящими полными cutA и более новым cutB, полученными штатным backup из реальных клиентов той же installation. Перед каждым независимым crash-case явный успешный ExistingInstallationRestore cutB с новым restore ID/boundary подготавливает исходную timeline; затем новый ExistingInstallationRestore cutA с другим новым ID/boundary достигает выбранного hook. После interruption — inspect и explicit same-journal Resume либо действительно допустимый Backout. Следующий case начинается только после доказанного terminal состояния предыдущего и нового штатного восстановления B. Незавершённый/непригодный case не «сбрасывают» новым Execute или копированием DB/anchor. Все старые evidence/markers/journals сохраняются по обычным правилам, graph bounds и nested provenance не обходятся ради числа прогонов.

Независимость здесь — новая зафиксированная исходная coherent cut/observation и отдельный request/fault/result log, а не отсутствие общей защищённой истории. Для каждого case записать реальные source A/B digests, исходный head/boundary, выбранный request/journal и фактический old/new file inventory. Новый restore B не делает target побайтово первоначальным B: он создаёт очередную законную свежую boundary со своим provenance. Наличие настоящего old set даёт возможность replace/delete, но не гарантирует их: coverage каждой выбранной file action подтверждается actual inventory/hook. Этот маршрут не заменяет отдельную проверку отказа **same-boundary older DB**: successful fresh-boundary restore сам по себе stale-copy detection не доказывает. Если отдельный negative не выполнен, он остаётся NOT RUN, а не наследует PASS от A/B matrix.

**Missing pathname:** достаточный реальный G6 negative для «missing anchor; Maintenance переживает restart» — контролируемая недоступность исходного anchor path при наличии protected history, без потери сохранённых bytes. Только на своём stopped stand, без незавершённой restore/Pending или hot-journal неопределённости, после владения всеми необходимыми fences зафиксировать согласованный physical anchor artifact set (DB и существующие journal/sidecars как единый набор), exact пути/length/hash, текущие main/domain/head и отсутствие writers. Явное временное перемещение этого набора в собственную quarantined evidence область — только fault fixture, не эксплуатационная рекомендация по перемещению/очистке journal. Не оставлять journal от другого DB, не менять bytes, не Provision/Initialize missing путь. Проверить настоящий startup refusal/Maintenance, затем повторный startup при всё ещё отсутствующем пути, отсутствие capability/обычных writes и отсутствие нового anchor/authority. Конкретный host, отказавшийся запускаться целиком, также фиксируется как отказ, не изображается работающий green endpoint.

Восстановление **этого же** набора на исходный путь — отдельное явное снятие fixture fault после полной остановки и проверки: никаких intervening main/domain/anchor changes, нового fence/store, restore/publication или стороннего writer; сохранённые artifact hashes неизменны. При любом расхождении не возвращать старый anchor поверх нового состояния и не repair автоматически. Это не rollback authority из backup. Процесс может менять неавторитетные наблюдательные артефакты лишь в рамках штатного startup; они не оправдывают игнорирование domain/head mismatch.

Называть case **controlled original-path unavailability, original store retained**, не безвозвратной потерей и не successful LostAnchorRecovery. Известные сохранённые bytes нельзя переименовать в `PreviousAnchorObservation.Unavailable` для принудительного admission. Fresh-boundary successful restore проверяется отдельно по настоящему ExistingInstallationRestore, с client download/quarantine/parcel/no-yield evidence. Утверждённая G6 matrix и основная §11 требуют missing-anchor refusal и реальный coherent fresh-boundary restore, но не предписывают дополнительно успешный LostAnchorRecovery в реальных клиентах для каждого mode. Поэтому эта пара cases покрывает указанные **подпункты**, не всю G6; existing/import/lost mode automated coverage Task14 и все остальные G6 пункты сохраняются. Отдельный успешный LostAnchorRecovery можно заявлять только по его собственному real inspected KnownLocation/admissible-unavailable witness и свежему qualified fence, с exact confirmation и guards bulk-restore §11; данный pathname fixture такого заявления не даёт. Неизвестная декларация, forged observation и скрытое исключение required automated case запрещены.

**Clock journal при отказавшем startup:** допустимо создать exact private TimeProvider и зафиксировать выбранные origin/run identity до BuildIsolatedAsync, но публиковать новый clock-run Origin только после успешных startup/domain-checkpoint checks и привязки настоящего OutpostClock sampler. Это отделяет неудавшийся запуск от начавшегося clock run; выбранный UTC/timestamp origin не пересоздаётся по более позднему времени публикации. До publication запрещены Advance, listener/game requests, hosted production/settle и любые durable domain/checkpoint effects, использующие этот ещё неопубликованный clock run. Если Build/startup может сделать такие записи, отложенная publication на этой границе недопустима: сначала обеспечить указанное ordering либо публиковать до первого такого effect. Обычные реальные startup проверки не подменяются фиктивным Ready; прочие штатные startup writes должны быть явно учтены при проверке неизменности missing-path fixture.

Каждая попытка до Build сохраняет отдельные bounded private launch/process evidence (run identity, выбранный origin, previous-log commitment, source/stand identity); ошибка сохраняет настоящий startup refusal и факт отсутствия sampler/listener/domain-clock effects, не создаёт synthetic Closed. Clock journal создаётся create-new с durable readback до открытия обслуживания; ошибка publication закрывает запуск, а не включает host без журнала. Уже опубликованные, в том числе incomplete, журналы неизменны и продолжают действовать по существующим restart guards. Это уточнение не разрешает удалить прежний Origin, задним числом записать Closed, игнорировать `acceptance-restart-needs-closed-run` или объявить уже существующий incomplete run «не запускавшимся». Новый порядок устраняет создание такого orphan при будущих ранних refusals, но не чинит старый orphan автоматически.

Для repeated missing-path evidence требуются две настоящие startup попытки на допустимой исходной clock timeline: обе доходят до штатного `anchor-missing-with-history`, не до более раннего instrumentation guard; для обеих сохранены process output/exit, actual missing path, неизменные domain/head/retained-anchor facts и отсутствие sampler/listener/Advance. Если старый incomplete clock journal не позволяет повторить запуск, эта повторная проверка остаётся NOT RUN до отдельно доказанного допустимого продолжения либо подготовки новой согласованной fixture; простая замена controller-кода не превращает её в PASS. Успешный startup отдельно проверяет один опубликованный Origin, настоящий sampler, штатный Closed и следующий restart; fault после publication сохраняет обычный incomplete-run отказ.

### 5.2. Применимость typed archive/restore к ordinary owner после BulkRestore

Механическое уточнение [lifecycle §§3.1,4.1](2026-11-04-passive-outposts-lifecycle-clarification.md) и [bulk restore §§1,2,4](2026-11-04-passive-outposts-bulk-restore-clarification.md): обязательство typed archive/restore определяется также действующей restore/lifecycle projection, а не только локальной protected custody-history. Это не code review, новый gameplay/recovery policy или утверждение PASS; реализацию и проверки выполняет основная Sol.

Если текущая canonical projection владельца ограничена применимым committed BulkRestore baseline, последующие archive/restore проходят существующий typed lifecycle. Его ordinary save остаётся LegacySnapshot: отсутствие локальной outpost-history не устраняет зависимость от restore projection. Archive закрепляет настоящий допустимый ordinary successor, exact legacy identity/raw bytes и verified archive locator до удаления live rows/files; restore ссылается на тот же доказанный архив. Сохраняются прежние lifecycle transitions, Pending protocol и retained evidence; synthetic OutpostSnapshotLink, registry, metadata или bridge не создаются. Current-projection validator принимает доказанный typed archive/restore descendant исходного baseline, продолжая проверять исторический R; вечное наличие исходной live SaveVersion не требуется.

Новый unjournaled archive после R нельзя задним числом признать descendant только по наличию корректного manifest/hash: это доказывает содержимое, но не разрешённое изменение projection. Прежние законные архивы при этом сохраняются: архив, уже включённый в проверенный selected source cut/restore map, проверяется как исходная архивная projection по exact bytes/identity, без ретроактивного lifecycle journal. Missing/corrupt/foreign/ambiguous evidence не становится legacy fallback. Доказанно unrelated ordinary путь без применимой restore/lifecycle projection и protected dependencies сохраняет прежнее поведение; одна лишь чужая global history не фабрикует локальную custody history.

Зависимость и полный реально затронутый owner set повторно проверяются под A→sorted O→S→Live→T до effects. Нельзя брать A внутри удержанного legacy O/S: входить через authority-aware маршрут либо отпустить предварительные locks и полностью перепроверить под правильным порядком. Между classification и effects не оставлять незащищённого окна. Исходные scopes/bytes/история других owners неизменны; это не право переписать уже нарушенную историю или автоматически repair maintenance.

Обязательные регрессии, пока NOT RUN этим уточнением: ImportNewHost с двумя обычными canonical saves → protected outpost у А → ordinary forward save Б → archive Б → корректные startup/authority/backup → restore Б и следующий ordinary save; preexisting ordinary archived owner в selected source cut без invented journal; missing/corrupt/foreign/ambiguous archive, substituted successor/hash/scope и новый untyped archive после R отказывают; archive races с save/backup/restore/protected mutation и crashes на lifecycle boundaries сохраняют достижимые bytes и fencing; unrelated ordinary путь и custody/история А остаются прежними. Итоговый whole-branch review этим уточнением не используется.

## 6. Обязательные проверки и предел результата

До G-run основной Sol проверяет реальные positive/negative случаи provisioning, clock monotonicity/overflow/replay/restart и pause ownership/cancellation/no-op; product packaging не включает dev controller/host и normal runtime не может активировать их config/env/API. Проверить отсутствие state/receipt fabrication, неизменные gameplay constants и тот же qualification evaluator. Unit/fixture доказательства лишь дополняют реальные G1–G7.

В отчёте перечислить каждый fault point, actual outcome, original operation/snapshot/parcel/custody IDs, counts до/после, cold/continuous branch, control-clock log и невыполненные случаи. Unknown/cold branch никогда не получает guessed local return. Crash tests не становятся power-loss доказательством. Browser-check записать SKIPPED BY USER отдельно; другие safety/platform/real-game проверки не пропускать по аналогии.

Эти seams не требуют нового игрового или recovery решения пользователя. Потребность в новом grant, fake receipt, ослаблении qualification/locks, normal runtime test switch, восстановлении потерянного anchor через Provision или исключении обязательного G-сценария выходит за механическое уточнение и требует отдельного решения. Никакого PASS, Qualified, публикации или завершения Task16 из этого документа не следует.
