# Rimlink — дельты старых версий сейвов: дизайн

Дата: 2026-10-30. Статус: на рассмотрении владельца.
Основа: `2026-10-28-rimlink-core-design.md` (версии сейвов, ретеншн, бэкапы);
`2026-10-30-rimlink-world-hygiene-design.md` (архив колоний). Этот спек меняет только способ хранения файлов на диске.

## 1. Цель и границы

Хранение сейвов и бэкапы не растут со скоростью «версии × полный размер». Откат, архив колоний и бэкапы продолжают
работать, падение сервера на любом шаге не теряет ни одной читаемой версии.

Решения, принятые в обсуждении:

- Старые версии лежат как дельты против базового файла игрока. Текущая версия всегда полный файл, поэтому загрузка,
  скачивание, протокол и мод не меняются. Работа только на сервере.
- Состояние версии определяется именем файла на диске, а не колонкой в `save_versions`. Причина: `rimlink-tools backup`
  работает при живом сервере и снимает БД раньше файлов. С колонкой снимок мог бы сказать «версия полная и текущая»,
  а в tar попала бы только её дельта, и после восстановления текущий сейв не прочитался бы. Миграция схемы не нужна.
- Дельта делается сразу при загрузке, рядом с ретеншном, а не фоновой службой. Сейвы, лежавшие до обновления,
  ужимаются разовым проходом при старте сервера.
- База своя у каждого игрока. Общая на сервер хуже по замерам (§2).

Вне границ: дельты при загрузке с клиента (трафик остаётся прежним), общая база на игроков, настройка `KeepLatest` и
`KeepDailyDays`, изменение уровня сжатия на клиенте.

## 2. Замеры

Живой сервер (7 версий, 19 МБ в распакованном виде) и стенды s2, s4, s5, 2026-10-30:

| Что | Результат |
|---|---|
| Сейв при zstd 3 | 4,45 МБ, из них 3,6 МБ (81 %) сетки планеты `tile*Deflate`, уже сжатые внутри файла |
| Сетки между версиями одного игрока | совпадают побайтово |
| zstd 19 вместо 3 | 4,16 МБ, 6,5 с: выигрыш около 6 % |
| Дельта против первой версии игрока, `--patch-from`, уровень 3 / 9 | стенды 129–514 / 97–425 КБ, живой сервер 167 / 145 КБ |
| Дельта против первой версии другого игрока, уровень 3 / 9 | 269–718 / 229–605 КБ |
| ZstdSharp 0.8.8, уровень 9 | живой сервер 120 КБ, s5 367 КБ в среднем; сжатие около 80–150 мс, распаковка единицы мс, восстановление побайтовое |

Оценка для 17 версий при сейве 4,45 МБ: сейчас 76 МБ на игрока, с дельтами 11–16 МБ. Стенды покрывают часы игры, рост
дельт за недели не измерен. Его ограничивает правило новой базы (§4.3).

## 3. Файлы игрока

Каталог `<DataDir>/saves/<playerId>/`:

| Файл | Что это |
|---|---|
| `<n>.rws.zst` | полная версия `n` |
| `<n>.d<k>.zst` | дельта версии `n` против базы `k` |
| `base-<k>.rws.zst` | база `k`: копия полного файла версии `k` |
| `upload-*.tmp`, `compact-*.tmp` | временные файлы |

Новый `SaveFiles` (`Application/Saves`) один знает эти имена, им пользуются `SaveStore`, `SaveArchive`, `SaveCompactor`.
Форма версии определяется по диску:

- есть `<n>.rws.zst` — версия полная, лишняя дельта этого номера игнорируется и удаляется следующим проходом;
- иначе есть `<n>.d<k>.zst` и `base-<k>.rws.zst` — версия в виде дельты;
- иначе файла версии нет, как и сегодня при потерянном файле.

Две дельты одного номера не возникают: старая удаляется, пока полный файл ещё на месте (§4.2).

Значения `Size` и `Sha256` в строке всегда относятся к полному файлу. Для версии в виде дельты они описывают файл,
которого на диске нет, и не проверяются; целостность дельты держит контрольная сумма кадра. При пересборке (§5.1)
строка получает размер и хеш нового файла, потому что байты могут отличаться от загруженных. Клиент хеш скачанного
файла не проверяет.

## 4. Сжатие

### 4.1 `SaveDelta`

`Application/Saves/SaveDelta.cs`, единственный `unsafe`-код сервера (`AllowUnsafeBlocks` в проекте): обёртка над
`ZstdSharp.Unsafe.Methods`, потому что `Compressor` не даёт API префикса.

- `Compress(reference, content)`: `ZSTD_CCtx_refPrefix`, уровень 9, long distance matching, окно больше большего из двух
  файлов, контрольная сумма кадра (`ZSTD_c_checksumFlag`).
- `Decompress(reference, delta)`: `ZSTD_DCtx_refPrefix`, разрешённое окно с запасом на предел из §4.3. Порча дельты или
  неверная база дают `InvalidDataException`.

Обычный `Compressor` и уровень 3 остаются для пересобранных полных файлов.

### 4.2 Проход по игроку

`SaveCompactor.Run(playerId)`, вызывается под `PerStoreLock`. Для текущей версии: если полный файл есть, лишняя дельта
удаляется. Для каждой нетекущей версии с полным файлом, по возрастанию номера:

1. Удалить лишнюю дельту этого номера, если она есть.
2. Распаковать полный файл. Если он больше предела (§4.3), версия остаётся полной.
3. Взять базу с наибольшим номером, если она есть и не больше предела, и сжать версию против неё.
4. Если базы нет или дельта вышла за порог (§4.3), версия `n` становится новой базой: полный файл копируется
   в `base-<n>.rws.zst` (временный файл, сброс на диск, rename), дельта считается против него.
5. Проверка: распаковать дельту и сравнить с исходным содержимым побайтово. Несовпадение: версия остаётся полной,
   ошибка в лог.
6. Записать дельту во временный файл, сбросить на диск, rename в `<n>.d<k>.zst`.
7. Удалить полный файл. Ошибка удаления (на Windows файл может быть открыт скачиванием) не страшна: следующий проход
   удалит дельту, посчитает её заново и удалит полный файл.

В конце удаляются базы, на которые не ссылается ни одна дельта в каталоге.

Вызовы: `SaveStore.Store` после ретеншна и `integrity.OnStored`, `SaveStore.Rollback` после переключения версии,
разовый проход при старте (§4.4). Ошибка прохода логируется и не отказывает ни загрузке, ни откату: сейв уже сохранён.

### 4.3 Константы

Рядом с `SaveRetention.KeepLatest`, настройками не становятся:

| Константа | Значение | Смысл |
|---|---|---|
| `DeltaLevel` | 9 | уровень zstd для дельт |
| `RebaseRatio` | 4 | новая база, когда дельта больше 1/4 полного файла |
| `MaxRawBytes` | 128 МиБ | версия или база больше этого не участвует в сжатии: `refPrefix` держит оба файла в памяти |

Старая база живёт, пока на неё ссылаются дельты, и уходит вместе с последней из них. Худший случай, когда каждая версия
становится базой, стоит примерно как сегодня плюс маленькие дельты. Пик памяти на обычном сейве 60–100 МБ, у предела до
600 МБ; проход один за раз, его держит `PerStoreLock`.

### 4.4 Проход при старте

`SaveCompactionService` (`BackgroundService`, как `ColonyHygieneService`, но разовый). Для каждого игрока, у которого есть
нетекущая версия с полным файлом, держит `ColonyLocks.Hold(playerId)`, затем `PerStoreLock`, вызывает `Run`, отпускает
оба. Так ужимаются сейвы, лежавшие до обновления, версии после возврата архивной колонии и остатки после падения.
Настройка `CompactOldVersions = false` (§9) отключает этот проход и `Run`, существующие дельты читаются как обычно.

## 5. Чтение и удаление

### 5.1 Пересборка и текущая версия

`SaveStore.EnsureFull(version)` вызывается под `PerStoreLock`: распаковать базу и дельту, сжать `Compressor(3)`, записать
`<n>.rws.zst` через временный файл, обновить `Size` и `Sha256` в строке, удалить дельту. Сборку файла делает `SaveFiles`,
строку обновляет `SaveStore`: `SaveFiles` — синглтон и БД не касается.

Обычно текущая версия полная, и `OpenCurrent` ничего не собирает. Исключение: бэкап снял БД, потом версия ужалась, и после
восстановления строка говорит «текущая», а на диске только дельта. Тогда `OpenCurrent` вызывает `EnsureFull` до открытия
файла. Запрос игрока не ждёт прохода при старте.

### 5.2 Откат

`Rollback` берёт `PerStoreLock`: `EnsureFull(target)`, затем переключение текущей версии как сегодня, затем `Run`, который
ужимает прежнюю текущую. Версия, которую нельзя собрать, даёт тот же ответ, что потерянный файл (`false`), с ошибкой в логе.

### 5.3 Ретеншн

`SaveRetention.Select` не меняется. `ApplyRetention` удаляет файл версии в любой форме и затем базы без ссылок, даже при
`CompactOldVersions = false`.

### 5.4 Архив колонии (`ColonyArchive`, `SaveArchive`)

- `EnsureFilesExist` принимает обе формы; дельта без базы считается потерянным файлом.
- `CopyOut` кладёт в каталог архива только полные файлы. Полная версия копируется и сверяется с `Sha256`, как сегодня.
  Дельта пересобирается в файл архива, манифест получает размер и хеш этого файла. Порча дельты прерывает архив так же,
  как несовпадение хеша сегодня, колония остаётся на месте.
- `CopyIn` не меняется: формат архива тот же, старые архивы читаются. Версии возвращаются полными и ужимаются при
  следующей загрузке или старте.
- `DeleteFiles` удаляет версию в любой форме, затем базы без ссылок.

### 5.5 Сброс игрока и пересоздание мира (`SaveStore.Archive`)

Этот путь без манифеста, строки версий забываются, поэтому файлы должны остаться пригодными сами по себе. `Archive` берёт
`PerStoreLock`. Полная версия переносится, дельта пересобирается в `<n>.rws.zst` каталога архива и удаляется. Дельта, которую
нельзя собрать, переносится как есть вместе с её базой, с ошибкой в логе: ничего не пропадает молча. Базы без ссылок
удаляются, каталог игрока остаётся пустым, поэтому номера новой колонии не встречают старых файлов.

## 6. Бэкап

`BackupArchive.Create` упаковывает `saves/` как есть, дельты и базы попадают туда без особой логики, а размер бэкапа падает
вместе с каталогом. CLI работает из другого процесса, общая блокировка с сервером невозможна, поэтому архив сам переживает
смену файлов:

- `*.tmp` не упаковываются;
- файл, исчезнувший между перечислением и чтением, пропускается;
- второй проход по каталогу добавляет файлы, которых ещё нет в архиве: так попадает дельта, созданная после первого прохода.

Порядок §4.2 создаёт базу раньше дельты, а полный файл удаляет после неё, поэтому версия, живая на момент снимка БД, попадает
в архив хотя бы в одной форме. Исключение то же, что сегодня: старая версия, удалённая ретеншном после снимка, остаётся строкой
без файла, и откат на неё отказывает. `Restore` не меняется.

## 7. Блокировки

`PerStoreLock` переезжает в `SaveFiles` (синглтон) и защищает любую смену файлов версии:

| Кто | Что держит |
|---|---|
| `Store`, финальный шаг с ретеншном и `Run` | `PerStoreLock` |
| `Rollback`, `SaveStore.Archive`, `OpenCurrent` при пересборке | `PerStoreLock` |
| Проход при старте, на одного игрока | `ColonyLocks`, затем `PerStoreLock` |
| `ColonyArchive.Archive`, `Restore` | `ColonyLocks`, как сегодня |

`OpenCurrent` без пересборки блокировку не берёт, как и сегодня. Порядок всегда `ColonyLocks`, затем `PerStoreLock`.
Архив и откат одного игрока могут пересечься, как и сегодня: файл исчезнет под `CopyOut`, архив прервётся чисто и повторится
следующей уборкой.

## 8. Отказы

| Что случилось | Что остаётся |
|---|---|
| Падение на шагах 1–5 §4.2 | полный файл, следующий проход повторит работу |
| Падение между шагами 6 и 7 | полный файл и дельта, читается полный, лишнюю дельту убирает следующий проход |
| Падение на пересборке | дельта на месте, временный файл игнорируется |
| Порча дельты | откат на эту версию отказывает, ошибка в логе; текущая версия не страдает |
| Порча базы | недоступны старые версии, ссылающиеся на неё; текущая версия от базы не зависит |
| Возврат на сервер 0.6.1 | текущая версия работает, откат на ужатые версии отказывает, файлы остаются на месте |

Порча базы — новый риск: сегодня каждая версия независима. Он принят, потому что касается только точек отката, а не текущей
колонии, и база есть ещё и в бэкапах.

## 9. Настройка, статус, документация

- Новая секция `Saves` (`SaveStorageOptions` в `Hosting/`): `CompactOldVersions`, по умолчанию `true`. Выключает создание
  новых дельт, чтобы обойти возможный баг без нового выпуска. В `deploy/appsettings.example.json` и в `/config` панели.
- `/status`: в `saves` добавляется `diskBytes`, реальный объём каталога `saves/`. `totalBytes` остаётся суммой `Size`.
  Обзор панели показывает `diskBytes`.
- Журнал: строка на каждую ужатую версию (версия, игрок, размер до и после, база).
- Документация: `docs/server-setup.md` (раскладка каталога, ключ, замечание про откат на старый сервер), `AGENTS.md`
  (правило про формы файлов сейва), `docs/manual-checklist.md`.
- Версия 0.6.2 по обычному правилу. `ProtocolVersion` не меняется, миграций нет.

## 10. Тесты

xUnit на реальном сервере (`tests/Rimlink.Server.Tests/Saves`), сейвы из `SaveFixtures`:

- `SaveDelta`: круг на случайных и почти одинаковых данных, порча дельты и неверная база дают `InvalidDataException`.
- Две загрузки: старая версия стала дельтой и намного меньше полной, текущая полная, скачивание отдаёт её без изменений.
- Откат на дельту: содержимое совпадает побайтово, версия полная, прежняя текущая стала дельтой, `Size` и `Sha256` описывают
  новый файл.
- Текущая версия только в виде дельты (бэкап снял БД раньше сжатия): `Download` собирает и отдаёт её.
- Порог: дельта больше 1/4 создаёт новую базу, старая живёт, пока на неё ссылаются.
- Ретеншн: уход последней дельты удаляет базу, даже при выключенной настройке.
- Предел: версия больше `MaxRawBytes` остаётся полной.
- Следы падения: полный файл и дельта одного номера читаются как полный, следующий проход оставляет одну форму; база без
  дельт удаляется.
- Архив: `CopyOut` и `CopyIn` с дельтами дают полные файлы, совпадающее содержимое, новая загрузка ужимает их снова.
- `SaveStore.Archive`: каталог архива с полными файлами, каталог игрока пуст; испорченная дельта переносится с базой.
- Бэкап: круг `Create` и `Restore` с дельтами и базами; файл, исчезнувший при упаковке, не роняет бэкап; `*.tmp` не упакованы.
- Проход при старте: каталог старых полных версий ужимается, текущая не меняется; при `CompactOldVersions = false` ничего
  не происходит.
- Настройка выключена: загрузки не создают дельт, существующие читаются.

На живом сервере после обновления (пункт в `docs/manual-checklist.md`): размер `saves/` упал, откат через панель на ужатую
версию работает, игрок заходит с откатанным сейвом, бэкап восстанавливается в отдельный каталог и сервер стартует на нём.
