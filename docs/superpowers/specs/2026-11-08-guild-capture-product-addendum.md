## 1. Решение границы authority из §8

**Выбран один расширенный authority domain и один существующий внешний anchor.** По структуре исходников append-only V3 реализуем без пересчёта старой истории. Это вывод о возможности конструкции, а не уже выполненная квалификация миграции.

Проверенные факты:

- `OutpostDomainDigest.cs` имеет отдельные V1/V2 writers и фиксированный список таблиц; digest включает точные байты table DDL, состав колонок и данные. Изменять прежние таблицы или список V1/V2 нельзя.
- `OutpostAuthorityChain.cs` выбирает формат только свёрткой проверенной цепи; уже поддерживает явную активацию V1→V2 и versioned BulkRestore. Он сверяет текущий digest с Effects последнего перехода, а не переписывает прошлые Effects.
- `OutpostTransitionDigest.cs` связывает предыдущий head, intent и непрозрачные Effects. `AnchorRecordCodec` хранит head и pending/restore, не перечень таблиц. Их существующее байтовое кодирование можно сохранить.
- `OutpostAuthority.cs` владеет единственной SQLite-транзакцией и порядком pending external anchor → DB commit → committed external anchor; отмена после попытки durable pending не компенсируется. `AcquireAsync` держит anchor, отсортированные colony locks, затем SaveFiles storage barrier.
- `OutpostDomainSchema.cs` проверяет весь `sqlite_schema` и migration lineage, а не только outpost tables. Любая новая таблица без нового точного профиля будет отказана. Старые профили и их hashes остаются историческими допустимыми профилями.
- `OutpostRestoreDomain.cs`, schema migration/backup manifest и admin intent/evidence readers сейчас конечны и знают V1/V2. Новый enum сам по себе не расширит восстановление.

### V3 без второго anchor

1. V1/V2 hashing, transition encoding, anchor encoding и все существующие записи/DDL сохраняются побайтно. Новые бизнес-таблицы только additive. EF migration не активирует формат, не выдаёт согласия, не создаёт ресурсы, объекты или игровые сущности.
2. Новый V3 digest имеет свой discriminator и фиксированную композицию: exact V2-domain digest + canonical guild-domain digest. Guild digest связывает DDL/колонки/строки новых protected tables в фиксированном порядке; формат явно версионирован. Нельзя пробовать V1/V2/V3 по очереди до случайного совпадения.
3. Guild-domain включает отдельную каноническую проекцию существующих союзов: `AllianceGroup.Id/OwnerId/Disbanded` и `AllianceMember.AllianceId/PlayerId/JoinedAt`. Денежные остатки, чат, withdraw permissions и unrelated social rows в неё не входят. Все create/join/leave/kick/leadership/disband, меняющие эту проекцию после V3, выполняются в общем authority transition; существующие финансовые проверки/receipt сохраняются. При V1/V2 старый social путь допустим, поскольку capture отсутствует. При неисправном V3 authority нельзя продолжить такие mutations через legacy fallback.
4. Явная admin preview/commit активация V2→V3 связывает прежний head/domain digest, точный source/target schema profile, migration lineage и новый V3 digest. Protected guild tables должны быть пусты; существующая governance projection импортируется как проверенный срез текущей БД, без имитации прошлой защиты союзов. Только этот переход вводит её в authority. V1 сначала штатно проходит V2. Новая установка может выполнить тот же проверяемый путь, не скрытый shortcut.
5. Существующий admin codec V1 и его immutable receipts не меняются. Новое versioned command/evidence расширение допускает V3; старые Initialize/Activate/Resolve/Restore декодируются прежними правилами. После V3 обычные personal-outpost transitions также вычисляют общий V3 Effects.
6. Новый schema profile допускает pre-activation V1/V2 на additive schema лишь при пустых новых protected tables и точном legacy digest. После V3 нельзя откатить format, удалить guild rows или назвать текущий schema историческим. Старый бинарник должен отказать новую схему, а не открыть её как V2.
7. Capture transitions получают собственный kind и типизированный intent, `PlayerId=0` для системного результата; они не подделывают personal `OutpostId`, custody ID или generation. Common readiness проверяет shared storage/anchor и применимую qualification; availability capture не зависит от фиктивного наличия личного работника. Личные операции сохраняют свои readiness checks. Ни одного bypass через `RuntimeComposition=false` в production.

**Обязательный доказательный gate до Product mutations:** golden V1/V2 chain/DDL/receipt invariance; V2→V3 activation crash matrix; исторический V1/V2 backup на V3 binary; V3 restore с новым boundary; unknown/tampered schema отказ. Если эти свойства не достигаются без изменения старых hashes/истории, реализация зависимых операций останавливается. Тогда нужен отдельный cross-domain контракт с атомарным coordinated commit/restore и утверждением пользователя; этот документ не разрешает два независимых anchor или «временный обычный DB update».

## 2. Защищённые сущности и общий порядок изменений

Новые имена ниже — проектируемые сущности/API, не заявление об уже существующей реализации.

| Сущность | Существенные поля/назначение |
|---|---|
| GuildOutpost | UUID, world/tile, immutable Steel/WoodLog profile, owner alliance nullable, owner revision, stock 0..1000, fixed-point remainder, accrual checkpoint, production phase, shield/cooldown, defence window + delayed change |
| GuildCaptureConsent | object/alliance/head identity, exact rules version, window, consent digest, durable timestamp; не подменяется согласием на influence |
| GuildResourceObligation | origin object + owner revision/campaign/transition, creditor alliance, resource/count, reserved/remaining, immutable provenance; не FK cascade на текущего владельца |
| GuildResourceClaim / GuildParcelLink / GuildDeliveryAttempt | request digest, закреплённый recipient/world/generation/boundary, valuation manifest, parcel/payload digest, canonical save proof, delivery state/receipt |
| GuildCampaign | object/revision, обе alliance IDs, commanders, policies/cut, UTC slot, phase, rules digest, terminal reason; readiness/terminal time/pair cooldown — связанные typed operation receipts из §4.1 |
| GuildAcquisitionReservation / BattleSlotReservation | объём лимита трёх объектов и один реальный executor slot; уникальные активные reservations |
| GuildBattle | battle/attempt ID, campaign, boundary, executor/fence, start nonce, start/final evidence references, terminal decision, application receipt |
| GuildBattleArtifact | immutable descriptor/hash/size завершённых initial/final artifacts и sealed transport manifest; не upload progress или mutable journal head |
| Battle transport journal (вне asset domain) | durable request→server sequence→accepted tick/ack и latest view; данные ограничены allowlist, terminal cut связан общим authority |
| GuildCaptureOperation | durable idempotency receipt для mutations, с original intent digest и resulting references |

Хранение initial/final snapshots и журналов — отдельный каталог через собственный `BattleArtifactStore`, внутри общей backup/storage fence; не `SaveFiles` имена личных сейвов. Артефакт завершён и проверен до ссылки в Start/result. Staged upload без ссылки не является committed результатом. Удаление только после доказанного retention/preflight, без orphan cleanup неизвестного исхода.

Общий существующий порядок: external authority lease (A) → colony locks по возрастанию (O, все затронутые recipients/owners) → SaveFiles storage barrier (S) → `LiveStateLock`, когда он нужен операции → одна DB transaction. Это контракт `src/Rimlink.Server/Application/Outposts/CustodyEntry.cs`: A/O/S приобретаются до Live, transaction начинается только после всех необходимых locks. Запрещено приобретать authority под уже удерживаемым Live. Вложенный caller использует `CustodyEntry.Borrow()` либо `UseHeldEntry(OutpostLease)`, не захватывает те же locks повторно и не освобождает чужой lease. Существующие lock paths массово не перестраиваются.

Новый отдельный alliance/geography mutex не вводится: mutations этих областей, касающиеся capture, сериализуются authority lease. Предварительное чтение списка owners лишь подсказка: после acquire повторная проверка; если набор изменился — release/retry всех необходимых locks в том же порядке без частичного эффекта. RPC результата не держит transaction во время network/file transfer. Events публикуются после external commit; потеря event компенсируется чтением состояния.

### 2.1. Горячий боевой журнал и единственный имущественный authority

Уточнение по измерению `build/authority-command-cost.json`: 48 000 команд (24 000 на сторону) дают 358–408 ms на один V3 digest даже в SQLite in-memory, без диска и external commit; пустой digest — 5–10 ms. При 40 commands/sec бюджет всего 25 ms/command. Поэтому command/ack/view не выполняют полный финансовый transition. Это изменение размещения транспортных данных, не второй asset authority или cross-anchor протокол.

Из текущих **14 новых, ещё не опубликованных** таблиц:

| Таблицы | Окончательная граница |
|---|---|
| `guild_outposts`, `guild_capture_consents`, `guild_resource_obligations`, `guild_resource_claims`, `guild_parcel_links`, `guild_delivery_attempts` | Оставить в V3 целиком: владение, запас, долг и физическая выдача |
| `guild_campaigns`, `guild_acquisition_reservations`, `guild_battle_slots`, `guild_capture_operations` | Оставить в V3: policy/слот/reservation и имущественные idempotency receipts |
| `guild_battle_control_grants` | Оставить в V3: выдача/отзыв права, side/player/epoch/expiry/capability digest. Ни heartbeat, last-seen, cursor, ни ack не обновляют эту таблицу; connection replay state — в transport journal |
| `guild_battles` | Оставить в V3, убрать текущие `View`/`ViewSequence` как mutable поля. Если terminal view хранится в row, назвать `TerminalView`/`TerminalViewSequence`: null/отсутствуют до terminal commit, затем immutable и связаны FinalDigest. Identity/campaign/world/boundary/executor/attempt/fence/StartNonce остаются protected; StartManifest/StartDigest/StartedAt записываются только при StartCommitted; FinalManifest/FinalDigest/Receipt и terminal view — только при terminal commit; Phase/Active — лишь lifecycle transitions, не каждый tick/poll |
| `guild_battle_artifacts` | Оставить в V3, но только завершённые immutable descriptors, закрепляемые в Start/terminal/lifecycle transition; никаких per-chunk/per-command updates |
| `guild_battle_commands` | Убрать из основной EF-модели, основной V3 schema и digest до shipping; перенос command/ack/request index в отдельный durable per-battle transport journal |

Итого 13 protected guild tables плюс существующая governance projection. Это не разрешает изменить V1/V2 migration/DDL/digest/catalog. Неопубликованную V3 migration/model/profile/qualification можно пересобрать под окончательную границу; ранняя V3 test DB/backup не получает молчаливую совместимость с новым форматом. Только disposable stand пересоздаётся либо получает явно проверенную миграцию. После изменения повторить V3 qualification и прежние V1/V2 golden проверки.

Journal размещается под `Data.Archive` в каталоге world/boundary/battle/attempt; путь строит сервер, не peer. Допустим append-only журнал либо отдельная SQLite с `Pooling=False`, открытая строго внутри storage lease. Формат versioned и bounded; записи связывают identity/fence/grant epoch, request digest, server sequence, side/actor, command, ack/tick и предыдущий hash. Persist/flush ДО успешного ack. Exact request/ack/view replay идемпотентен, conflicting sequence refused. View — последняя durable baseline плюс журнал её sequence/digest; compaction допустима только с атомарным checkpoint, сохраняющим replay watermarks и terminal evidence. Это журнал транспорта, не источник права менять владельца или выдавать ресурс.

Горячий путь берёт **S → per-battle lock**, повторно проверяет под S опубликованные readiness, текущие world/boundary/lease/fence/grant и expiry, затем пишет journal/читает последние facts. Никогда не приобретает A из-под S/battle lock и не вызывает financial BeginHeldAsync. До старта сервера и reconciliation readiness закрыт. Authority writer под своим A/O/S публикует fail-closed состояние перед неоднозначным pending/restore/revoke и новую допустимую projection только после external commit; stale cached lease не авторизует hot call. Restore устанавливает глобальный durable fence, отзывает executors и закрывает transport admission до переключения файлов. Membership/grant changes и lease revocation обновляют admission под тем же S.

Финансовый Start/final/revoke путь: **A → ordered O → S → Live, если нужен → per-battle lock → DB**. Финал после приёма файлов заново берёт эти locks снаружи, сверяет lease/fence и journal, прекращает новые commands, запечатывает immutable transport manifest (identity, format, byte length/hash, side watermarks, ack chain, terminal view digest) и связывает его с отдельным simulation journal/final snapshot арбитра в общем FinalManifest. Неисполненные accepted commands получают terminal `not executed`, не ложный accepted tick. Только общий authority commit меняет owner/stock/obligation и выдаёт receipt. Seal без asset commit после crash не означает победу; повтор использует тот же проверенный seal/envelope. После seal журнал не дописывается, duplicate final возвращает прежний receipt.

До отпускания S закрываются ВСЕ journal SQLite connections/readers/transactions и file handles; pooled handle на Windows не может переживать lease и мешать restore/rename. Ни network wait, ни долгий idle stream не держат S/battle lock. BackupArchive уже переносит `Data.Archive`, но наличие файла не заменяет согласованный cut: под общей storage fence фиксируются/flush-ятся journal checkpoints и их bytes/hash/watermarks в backup manifest; restore сверяет их с соответствующими battle rows и sealed manifests. Повреждённый/отсутствующий live journal → RecoveryRequired/abort без guessed replay и без передачи. Terminal manifest mismatch → отказ evidence. Старый restored journal не оживляет executor после новой boundary.

`AllianceService.Mutate` сейчас начинает свою Serializable transaction перед dispatch. Governance/disband ветви должны войти в held authority stage ДО открытия transaction, а не вызвать authority внутри неё. При отказе disband казна, membership, объекты и obligations не меняются. Все остальные callers сохранения/архива/переноса тайла проходят общий bidirectional claim check: settlement/NPC/personal outpost/prepared reservation/guild object. Guild marker не расширяет influence.

## 3. Экономика без личной custody

Сохраняются все утверждённые числа: Steel 10 или WoodLog 20 за час, склад 1000, три объекта на alliance, 32 в мире. Администратор размещает свободный объект на основной поверхности; первоначальное назначение только после точного consent главы. Профиль/тайл после размещения неизменны. Нейтрализация после disband не создаёт бесплатный first-click capture.

Начисление целочисленное с остатком, под authority, по monotonic elapsed между durable checkpoints. Нормальный restart использует проверенный UTC checkpoint для bounded offline accrual до cap; отрицательное время не списывает ресурс, скачок часов не создаёт отрицательный/повторный интервал. Bulk restore явно выставляет новый checkpoint без начисления downtime. На cap остаток не копит скрытый бесконечный запас. Poll не создаёт отдельный интервал начисления поверх уже settled cut.

В PreparingBattle settle, pause, блокировка новых claims; pending неоднозначная выдача требует reconciliation до Start. Уже committed parcels сохраняют получателя. При capture единая transaction: оставшийся целый stock → obligation прежней alliance; новый owner/revision; stock/remainder=0; завершение campaign/reservations; результатный receipt. При defender/draw stock/remainder сохраняются; производство возобновляется от terminal commit. Во время paused/unknown battle yield не идёт; TechnicalAbort не начисляет outage backlog.

Claim главы из текущего склада или прежнего obligation → конкретному действующему участнику: проверки freeze/debt, generation/canonical snapshot, допустимого ресурса и места для безопасной выдачи. Immutable request фиксирует источник, recipient, количество и valuation revision до списания. В одной authority transaction уменьшается available/reserved, создаётся typed parcel/link и receipt. Failed insert откатывает весь stage. Повтор intent возвращает тот же parcel; иное содержание с тем же request ID отказано. После commit смена главы/членства не перенаправляет parcel.

**Атрибуция ServerWealth:** общий stock объекта и old-stock obligations до committed immutable claim принадлежат alliance и не приписываются личной колонии главы или любого участника: персональный получатель ещё не определён. Поэтому capture, накопление общего stock и смена главы сами по себе не меняют личный ServerWealth. Существующее правило казны с единственным refund recipient этим не меняется и на ресурсные обязательства не переносится. При committed claim стоимость typed parcel по закреплённому manifest/valuation revision учитывается единожды как server-held wealth конкретного recipient; тот же ресурс не считается параллельно через obligation/stock или обычный mailbox payload. Смена главы/членства после claim не меняет атрибуцию.

Server-held value снимается только при доказанном canonical acceptance материализации: в согласованном срезе тот же ресурс переходит в physical wealth домашнего сохранения и перестаёт учитываться как ожидающий parcel. Local materialization, lost ack, generic receipt/DeliveredAt или старый клиент сами по себе не снимают server-held value и не дают второе начисление. Claim receipt, delivery evidence, canonical snapshot и используемый wealth snapshot должны согласовываться; неоднозначность требует recovery, а не преждевременного обнуления held value. Rollback/restore восстанавливает эту атрибуцию по выбранному согласованному cut и receipt proof, без двойного учёта или потери стоимости между pending и accepted состояниями. Это anti-doublecount правило, не новый баланс, налог или признание главы личным владельцем общего склада.

Новый `GuildResourceParcelPayload` содержит только Steel/WoodLog, количество, value/manifest binding, guild origin и recipient scope. Это не `ItemBlob` и не `OutpostParcelPayload` с выдуманным personal outpost. `Parcel` proto расширяется свободным полем после инвентаризации (1..13 заняты в базе). Таблица existing parcels не перестраивается: origin/delivery evidence в новых linked tables. Получение использует типизированный BeginDelivery → материализация дома → durable canonical snapshot → acceptance receipt. Generic mailbox delivered/delete и старый клиент не обходят этот путь. `PawnCustodyRegistry` не получает матчевых бойцов; для resource receipt используется отдельный guild delivery registry/save evidence.

Archive/reset/rollback recipient generation не возвращает claim в общий склад и не создаёт второй parcel. Исходная привязка удерживается; безопасный retarget только через доказанный reconciliation/типизированный admin intent, без произвольного редактирования. Disband: сначала resolve все claims/obligations и подготовить safe issuance текущему главе, затем neutralize и штатный treasury refund в той же согласованной операции; если нельзя — отказ до effects. На активной campaign disband отказан. Перед принятием кампании резервируется место для одного будущего old-stock obligation; технический предел 256 outstanding obligations на alliance блокирует НОВЫЕ кампании, но не уничтожает заработанное и не блокирует погашение. Это capacity guard, не налог или новый экономический баланс.

### 3.1. Guild delivery в общем canonical snapshot envelope

Проверены текущие owning seams: `SaveStore.Store` хеширует полный decompressed XML через `SaveRecoveryData.ReadXml`, затем одним authority commit записывает SaveVersion и `OutpostSnapshotLink`; `SnapshotAccepted.Intent` равен точным bytes `OutpostSaveMetadata`. `OutpostSnapshotGuard` сверяет raw bytes/hash, RecoveryJson, metadata/link/transition и прежние delivery receipts. `OutpostRecoveryData` уже хранит versioned bounded protobuf внутри единственного XML-раздела `rimlinkOutposts`; `SaveHeader.outpost_metadata` занимает поле 16. В `OutpostSaveMetadata` поля 1..11 заняты, 12 свободно на момент проверки. Эти факты определяют минимальное расширение, а не готовность новой доставки.

**Выбран отдельный typed guild payload внутри прежнего общего envelope.** В независимый `guild_resources.proto` добавить `GuildSaveMetadata` и `GuildDeliveryReceipt`, использующие собственные `GuildColonyScope`/`GuildSnapshotProof`, без imports outposts/economy. `outposts.proto` импортирует resources и добавляет `GuildSaveMetadata guild_metadata = 12` после повторной проверки свободного номера. Не создавать `GuildSnapshotAccepted` с альтернативным combined intent: сохраняются прежние kind, schema envelope, transition/link и XML layout. Guild family остаётся отдельной: никакого fake PawnCustodyId, personal OutpostParcel, OutpostTransitionReceipt или worker registry. В guild-only save outer scope настоящий, personal registry пуст; это общий protected snapshot container, не личный аванпост. Если personal evidence уже существует, оно сохраняется полностью и не очищается ради guild-only представления.

Не добавлять дублирующий guild metadata в `SaveHeader` поле 20 и второй XML-раздел. Единственное содержимое — вложенный field12 в `OutpostMetadata16` и тот же protobuf внутри XML; сервер проверяет равенство ВСЕГО metadata, включая guild field, между заголовком и raw XML. RecoveryJson лишь производная проекция. Отсутствующий guild field у старого сохранения остаётся отсутствующим: не переписывать historical bytes и не вставлять пустой submessage при старом hash readback. `GuildSaveMetadata` имеет собственный version, current recipient scope и bounded unique receipts; outer/inner current coordinates обязаны совпасть. Неизвестные guild version, duplicated section/receipt/attempt/parcel и превышение общего metadata limit отказаны.

Отдельная `GuildVersion` negotiation добавляется additive в login/session/capability/download metadata по свободным номерам, не подменяет `OutpostVersion` и не включает personal feature. Потребность в guild-aware клиенте выводится не из наличия поля в присланном upload, а из серверной retained history: claims/parcels/attempts, accepted snapshot links и restore/rollback provenance. Она сохраняется после acceptance, пока такая история нужна. Старый клиент может продолжать колонию без guild history, но не загружать/скачивать защищённую guild timeline как обычную, не принимать её parcel и не затирать поле12. Unknown-field preservation protobuf не считается поддержкой. Source-referencing operations также требуют подходящую family version, даже если текущий mutable registry пуст.

Common `RequiresProtectionAsync`/upload lock/download lock учитывают guild history и повторяют проверку после acquisition. `ValidateHeldAsync` и authority Begin/commit разделяют common storage/anchor readiness и фактически присутствующие personal/guild families: нынешний безусловный `RequireCustodyReadiness` нельзя использовать как разрешение guild-only доставки либо глобально отключить. Для personal family прежние проверки сохраняются; для guild — собственный применимый gate, для mixed нужны оба. На недоступной authority нет legacy save fallback. Вход на battle mirror и его save остаются запрещены независимо от корректного envelope.

Порядок доставки и доказательства:

1. **Before proof.** Действующий recipient готовит и сервер принимает canonical home snapshot с guild-aware common envelope. Если protected history ещё нет, допустим bootstrap с пустым GuildSaveMetadata v1 и пустым personal registry, но настоящими world/player/generation/epoch/boundary. Это обычный доказанный SnapshotAccepted, без materialization или custody. `GuildSnapshotProof` ссылается на его сохранённые snapshot ID/raw hash/scope; клиентский произвольный hash не принимается.
2. **Claim и BeginDelivery.** Claim фиксирует recipient и payload/manifest value. BeginDelivery под общим authority проверяет текущий canonical before proof, неизменный payload digest, generation/epoch/boundary, отсутствие другого активного attempt и допустимость домашней доставки. Durable authorization связывает claim/parcel/attempt/request ID, intent digest, before proof и свой transition ID/digest; повтор возвращает ту же авторизацию, другой intent отказан. No network wait под transaction.
3. **Local materialization.** Отдельный guild delivery registry принимает только типизированную авторизацию и allowlisted ресурс дома, создаёт ресурс один раз и записывает immutable `GuildDeliveryReceipt`. Receipt содержит attempt/claim/parcel/request identity, payload digest, authorization transition ID/digest/intent digest и BEFORE proof; local applied marker связывается с attempt. В receipt НЕТ raw hash нового содержащего его сейва и НЕТ digest будущего SnapshotAccepted. После crash registry и локальный save reconciled до новой materialization; generic parcel ID alone недостаточен.
4. **Новый raw snapshot.** Receipt сериализуется в field12; save получает собственный snapshot ID обычным путём. Только после полного XML EOF сервер вычисляет новый raw hash. Проверяет before proof/authorization/attempt/payload, наличие разрешённого physical receipt, полноту сохранённой guild истории и personal evidence. Привязка receipt к raw snapshot доказывает запись metadata в сохранении; она не является независимым аудитом честности всей клиентской игровой симуляции.
5. **Одно принятие.** В существующем `SnapshotAccepted` stage фиксируются SaveVersion/raw hash, common OutpostSnapshotLink с полным metadata и guild attempt/link first-acceptance (новый snapshot ID/raw hash), parcel delivered и согласованное wealth переключение. Всё в одной common authority transaction/external commit. Новый acceptance proof хранится снаружи уже записанных bytes; нельзя дописать его в тот же XML и сохранить прежний hash. События/ответ только после commit. Lost response возвращает прежний результат; тот же snapshot ID с другими bytes отказан.
6. **Поздние сохранения.** Несут прежний immutable guild receipt, не импортируют ресурс заново и не заменяют first accepted snapshot более поздним. Retained source receipt не удаляется после generic ACK или при смене главы. Допустимые сокращение/перенос истории требуют отдельного доказанного provenance, не silent omission.

Скачивание, individual rollback и bulk restore используют существующие common snapshot/source bridges, сохраняющие исходные bytes/provenance. Guild validator дополнительно доказывает, какие immutable receipts пришли из actual source/authorized view, и сверяет их с guild attempts/first acceptance; прежняя проверка только personal mutable registry не достаточна. Ни новая boundary, ни epoch не переписываются внутри исторического receipt: effective current scope находится в envelope и подтверждённом bridge. До принятия materialized snapshot повторное разрешение импорта возможно только после reconciliation; после принятия исключается повтор даже при lost ack и локальном rollback. Если selected cut/bridge не даёт нужной guild связи — RecoveryRequired, не очистка registry. Retention сохраняет canonical before/first accepted snapshots и ссылки как common evidence.

Обязательные negative guards: пропущенный field12/receipt при retained history; valid generic parcel receipt без guild authorization; чужой attempt/parcel/payload/recipient; подменённый before hash; отсутствующий protected before snapshot; stale epoch/boundary; разные header/XML guild bytes; неизвестный GuildVersion; history из другой restore timeline; replay уже accepted parcel в новом snapshot как новая materialization. Все отказы до переключения canonical save/DeliveredAt/wealth. Публичный handler и Product qualification этим уточнением не объявляются готовыми.

## 4. Campaign, политика и время

Ежедневное окно 2 часа UTC; notice ≥24 часа; ближайший допустимый слот ≤7 суток; shield первого владельца 72 часа, cooldown после боя 72 часа; delayed window change 7 суток. Одна campaign/object, одна объявленная attack/alliance. Резервируются свободный acquisition slot и реальный executor slot до принятия заявки. V1 production scheduler предоставляет один slot; масштабирование отдельно. Слот резервирует 5 минут attacker readiness + 20 минут боя и ограниченное время подготовки/очистки; непроверенная capacity не рекламируется. Server downtime не сжимает notice и не запускает просроченный матч сразу: missed slot terminal technical cancellation/rebooking с новым согласованным временем и сохранённым notice, без автоматической бесконечной очереди.

### 4.1. Ready, terminal time и резерв единственного исполнителя

Текущие `GuildCampaign` и `GuildBattleSlot` уже хранят необходимые ссылки/phase и границы слота; `GuildCaptureOperation` имеет Kind/Receipt/TransitionId и immutable intent digest. **Новая schema amendment для Ready/TerminalAt/PairCooldownUntil не нужна:** низкочастотные факты записываются как отдельные versioned typed receipts в существующих `guild_capture_operations`, защищённых common authority. Это не hot command/view journal. Kind dispatch и stored-evidence validation расширяются явно; произвольный JSON со свободными строками не является контрактом.

- `GuildAttackerReady` receipt связывает campaign/battle/attempt/world/boundary, attacker alliance/commander, grant epoch, rules и подготовленный start manifest digest, server-observed `ReadyAtUtc` и `ReadyDeadlineUtc`. Время назначает сервер, не клиент; intent связывает подтверждаемый manifest и role. Valid Ready принимается в readiness window до deadline, пока campaign не terminal. Exact request replay возвращает прежний receipt; changed payload отказан. На тот же battle/commander/grant/manifest повтор Ready не создаёт бесконечную историю; при действительной смене binding прежний receipt остаётся историческим, новый допускается только до deadline. Под Start locks заново сверяются membership/policy/grant/session, manifest/fence и существование подходящего Ready. Ready не заменяет StartCommitted, не даёт управления заранее и не разрешает начать другой battle после restart.
- `GuildCampaignTerminal` receipt связывает campaign/object/owner revision/world/boundary, упорядоченные attacker/defender alliance IDs, terminal reason, server `TerminalAtUtc`, optional battle/result reference, освобождаемые reservations и optional `PairCooldownUntilUtc`. Для `NoAttackerReady` последний равен `TerminalAtUtc + 24h`; для иных причин этот penalty отсутствует. Это cooldown направленной пары attacker alliance → defender alliance, независимо от смены главы/командира, leave/rejoin и выбора другого объекта того же defender. Он не запрещает обратную атаку по одному лишь этому receipt. Terminal operation и Phase/TerminalReason/Active/reservations фиксируются одной common transaction; replay не сдвигает TerminalAt и не продлевает cooldown.
- Проверка новой заявки читает все релевантные retained terminal receipts пары, валидирует их связь с authority/campaign и берёт максимальный ещё действующий deadline. Нельзя выводить cooldown из текущего владельца объекта, last-seen, mutable `UpdatedAt` или исчезновения active reservation. Exact schema/receipt bounds сохраняются. Безопасный in-memory индекс допустим как ускорение с rebuild из проверенных receipts, не как источник факта. Retention этих фактов не заканчивается удалением transport journal; restore сохраняет соответствующие selected-cut receipts.

**Одна operation на transition:** при принятии Final `GuildCaptureOperation.Kind=GuildBattleApplied` содержит один versioned typed receipt результата с вложенным `GuildCampaignTerminal` receipt (scope/campaign/object/revision/alliances/reason/TerminalAt/result reference/slot/acquisition, pair penalty отсутствует). Вложенный terminal — часть тех же immutable bytes, привязанных к общему transition; это не вторая operation и не отдельный commit. Owner/stock/obligation, terminal campaign/reservations, outcome receipt и occupancy barrier атомарны. Для pre-Start cancellation остаётся самостоятельный operation kind `GuildCampaignTerminal`, включая допустимый NoAttackerReady penalty. Terminal/cooldown/evidence readers используют явный конечный codec dispatch ровно этих двух форм и проверяют согласованность вложенного terminal с outer result/campaign/transition. Не искать terminal по произвольному JSON, не считать вложенный receipt вторым завершением и не записывать второй финансовый переход ради него; новые таблицы не нужны.

Для первого однослотового deployment фиксируется **30-минутная reservation**: `[ScheduledAtUtc, ScheduledAtUtc + 30m)` = до 5m readiness/initial preparation + максимум 20m от actual Start + до 5m finalization/cleanup. Весь резерв размещается внутри выбранного 2h окна; соседние интервалы half-open могут соприкасаться, но не перекрываться. Подготовка initial snapshot выполняется в первых 5m, а не отнимает время у уже запущенного боя. Если attacker готов, но executor не подготовился/не совпал manifest — техническая отмена, не `NoAttackerReady` penalty. Deadline race Ready/Start/cancel сериализуется authority; поздний Ready не воскрешает terminal campaign. Пропущенный из-за server downtime слот — техническая отмена, не доказательство неготовности игрока.

20m боя и 5m readiness — утверждённые правила; 5m cleanup — операционный резерв, не новый игровой таймер или право присудить победу. Если final/cleanup не завершены к концу резерва, слот становится unavailable/Maintenance: неизвестный исход сохраняется, новый процесс не назначается поверх старого. Следующая future reservation не превращается в гарантированный Start при неисправном исполнителе; её техническая отмена/переназначение сохраняет notice и не выдаёт победителя. Cleanup failure не откатывает уже committed capture. Досрочный terminal не разрешает вставить незаявленный бой без notice.

**Durable occupancy отдельно от результата.** В transaction принятия результата campaign и acquisition/calendar reservations завершаются, owner/stock/obligation/receipt фиксируются окончательно, но `GuildBattle.Active=true`, `Phase=AppliedAwaitingCleanup` сохраняют занятие физического executor slot. `Active` здесь означает незавершённую эксплуатацию runtime, а не возможность продолжать бой или принять иной результат. Terminal receipt/seal уже immutable; команды и simulation ticks запрещены. Prepare/Start следующего боя проверяют persistent active battle, а не только пустой memory registry или истёкший календарный интервал. Эта проверка восстанавливается до открытия admission после restart. Terminal без передачи владельца также не освобождает реально занятый runtime без cleanup; uncertain executor сохраняет barrier.

Отдельный common authority transition `GuildExecutorCleanup` с versioned typed `GuildCaptureOperation` receipt подтверждает проверенный возврат approved runtime в Entry, отсутствие текущего battle context/активных tick hooks и допустимую новую готовность процесса. Receipt связывает battle/executor/runtime instance, текущие boundary/fence и свежий server challenge, исходный immutable terminal result digest и server-observed cleanup time. Старый heartbeat, reconnect, elapsed cleanup budget или неподтверждённое сообщение «процесс завершён» не являются доказательством. Проверка и снятие barrier сериализуются A/O/S→Live при необходимости→battle lock→DB; только этот переход меняет Active=false и фазу на завершённую эксплуатацию, не outcome/owner/receipt. Exact cleanup replay возвращает прежнее подтверждение; stale/conflicting cleanup отказан. Если runtime погиб или недоступен, barrier остаётся до явно проверенного operator recovery: revocation прежнего instance и подтверждение чистого approved replacement, с отдельным audit evidence в том же типизированном переходе, без автоматического освобождения по таймеру. Новых таблиц для barrier/cleanup не требуется.

Executor registry содержит единственный допущенный operational slot со стабильным ExecutorId, approved build/manifest, опубликованным health/readiness и runtime lease/fence. Presence/heartbeat — текущая доступность, а не durable future booking. Future bookings — `GuildBattleSlot.StartsAtUtc/EndsAtUtc/ExecutorId/Active` в common authority. При объявлении под A/O/S повторно сверяются registry admission и отсутствие перекрытия со ВСЕМИ active future reservations единственного slot; если нужен battle lock/Live — соблюдается общий порядок. Непосредственно перед preparation/Start снова проверяются точный reservation, expected object revision, current executor health/build/lease/fence и фактическое отсутствие незавершённого процесса. Reconnect/re-register того же ExecutorId не стирает reservations; неизвестный/заменённый executor не наследует старую lease. Heartbeat не переписывает financial row.

Campaign states: Scheduled → PreparingBattle → StartCommitted → AwaitingResult → Completed либо Cancelled/TechnicalAbort/RecoveryRequired. Только подготовленные terminal evidence дают Completed. Повторные technical abort переводят объект в Maintenance (порог 3 последовательных abort, сброс только успешным боем или проверенным admin recovery); оператор не выставляет победителя. Новый бой после unknown outcome — новый battle ID, после fences/reconciliation, не continuation прежней симуляции.

**Object cooldown после terminal:** 72 часа назначаются после каждого доказанного игрового исхода `AttackerWin`, `DefenderWin` или `Draw`, от времени committed terminal transition; exact replay не продлевает срок. `TechnicalAbort` не создаёт и не продлевает 72h shield/cooldown: прежние owner/целый stock/дробь сохраняются, checkpoint возобновления rebased без outage backlog, `ConsecutiveAborts` увеличивается один раз, при трёх — Maintenance. Уже существующий независимый срок защиты не обнуляется. Physical slot остаётся занят до verified cleanup независимо от наличия object cooldown. Это различие не превращает technical cancellation в успешную оборону; отдельный 24h pair cooldown `NoAttackerReady` сохраняет собственное правило.

Перед первичным consent/attack: глава с активной колонией вне newbie/peaceful/off-delay; глава и attacker commander без freeze/debt; commander член нужного союза. Defender peaceful/offline не даёт veto, AI защищает объект. До Start повторная policy проверка; новый attacker запрет отменяет заявку без capture. Attacker не Ready через 5 минут — cancel и pair cooldown 24 часа. После Start personal freeze/debt не отменяет результат; membership/session loss отзывает control, AI после 30 секунд. Нельзя перейти на противную сторону в текущем battle: membership epoch и side binding неизменны.

Глобальный capture/raid freeze сериализуется с result: ранее committed result сохраняется, ранее committed abort/fence запрещает поздний result. Household raid правила, newbie shields, wallet и казна не ослабляются. Archive/reset теряет управление командиром, не владение форпостом. Lead transfer сохраняет consent/window/campaign, новый глава видит риск. Guild ID не меняется вместе с главой. Pair/object cooldown не сбрасывается leave/rejoin.

## 5. Production transport и игровой контекст

**Уточнение scheduler к §4.1 — основание NoAttackerReady.** На фиксированном deadline ScheduledAtUtc+5m отсутствие Ready само по себе недостаточно. Штраф допустим только при положительном evidence: исходный assigned runtime был аутентифицирован, healthy и готов к Start; initial полностью staged/verified/reloaded; exact session-bound proposal прошёл проверки и был опубликован до deadline как Ready offer; сервер получил authenticated подтверждение доставки этого exact offer назначенному атакующему до deadline. Подтверждение доставки — автоматический transport acknowledgment с proposal sequence/digest, session binding и server receive time, **не Ready и не согласие на результат**. Одного write-to-stream или наличия proposal на диске недостаточно. Offer/ack хранятся typed durable journal records и связываются с terminal receipt reference/digest; это не ещё одна financial operation.

Для NoAttackerReady между подтверждённой доставкой offer и deadline не должно быть известного server/executor/profile/artifact сбоя, закрытого Ready admission или потерянной согласованности scope. На deadline authority повторно проверяет exact current proposal, отсутствие committed Ready и техническую возможность Start при наличии Ready. Player disconnect после подтверждённого offer сам не является неисправностью арбитра. Но relogin/смена binding, требующая superseding proposal, делает прежний offer недостаточным: нужен доставленный новый exact offer. Если attacker изначально offline и session-bound proposal построить/доставить нельзя, отмена техническая без directed24h penalty; отсутствие игрока нельзя подменять доказанным отказом от доступного Ready. Утверждённый общий пяти минутный preparation/readiness interval и deadline не сдвигаются; новый минимальный отдельный таймер ответа этим не вводится.

Assignment без initial/proposal, недоставленный offer, публикация/ack в deadline или позже, stale proposal, неопределённая health после downtime/restart, missing journal evidence дают pre-Start technical cancellation без pair penalty. Это не игровая защита/победа и не новый72h shield. Technical cause имеет приоритет над NoAttackerReady; доказательства штрафа обязан предоставить сервер, отсутствие доказательств трактуется в пользу отмены без штрафа. Ready/cancel race решается одним common commit order: committed Ready исключает NoAttackerReady; поздний Ready не оживляет уже terminal campaign. Terminal receipt фиксирует reason, server terminal time и qualifying offer/assignment references; replay не переклассифицирует причину и не продлевает cooldown.

Минимальный cleanup tag `AppliedResult` содержит именно `committedFinalDigest`; tag `PreStartCancellation` содержит `terminalTransitionId` и `runtimeAssignmentTransitionId` (UUID common transitions), с ожидаемыми typed kind/record version и scope/battle/attempt. Если assignment вложена в Prepare receipt, reader извлекает только предусмотренный codec record; произвольные UUID без проверки существующего committed transition/intent/receipt binding не являются proof. Terminal receipt/assignment bytes уже входят в common evidence, дублирующая financial запись не нужна. Для pre-Start tag committedFinalDigest отсутствует, а не заполняется hash отмены. Cleanup intent связывает tag целиком со свежим challenge/current scope/runtime; outcome/penalty не меняется. Для отмены без assignment cleanup отсутствует, а не ссылается на фиктивный UUID.

Прототипные named pipes и bridge не становятся публичным боевым API. Новые отдельные gRPC сервисы: authenticated executor lane и player commander lane, по TLS с существующей pin-проверкой на клиентах. Executor credential отдельный от player/admin token, хранится оператором вне mod/shared files, связывается с allowlisted executor ID/build manifest; rotate/revoke увеличивает durable fence. Server-side credential validation не принимает role из payload. Commander grants ограничены player session + alliance epoch + campaign/battle/boundary/side, короткий срок и nonce; renewal не меняет сторону. Один активный control connection/side, новый connection epoch отзывает старый. Сервер назначает sequence после idempotent client request; ack арбитра не назначает серверную identity.

`BattleStartManifest` фиксирует полный ordered runtime/mod/content/config/defs inventory, game/client/executor build, template/rules/roster, initial snapshot hash/size, commanders, owner revision, production cut, fence и nonce. Executor сверяет фактически загруженное. Ни DLL, ни клиентский Scribe blob, ни generic TakeJob от игрока не принимаются. Сетевая сторона имеет bounded command/control 16 KiB, 20 commands/sec/side, 64 pending/side, восемь controlled fighters; snapshot chunks ≤256 KiB, общий snapshot ≤64 MiB, full delta frame ≤1 MiB с отдельным total/rate budget. Oversize typed refusal; неподходящий approved template не обрезается до лимита.

### Runtime identity и cleanup до Start

**Handshake и transport lease.** Допускаются два явных server-issued lane: `Execution` и battle-scoped `RecoveryDelivery`. Запрошенный lane не является правом клиента: сервер определяет разрешённые операции по durable assignment/phase/readiness. Authenticated Hello begin передаёт executor ID, process runtime ID, measured profile/build/inventory binding и, для recovery, battle/StartDigest либо pre-Start assignment reference. Сервер выдаёт случайный одноразовый challenge с коротким ограниченным TTL и server-boot identity; challenge связан с exact request digest, текущей credential generation, lane/target и scope. Hello complete под той же executor authentication возвращает challenge и exact binding. Это проверка свежести authenticated peer, **не аппаратная attestation** и не доказательство владения PID. Достоверность measured facts опирается на доверенный shipping adapter/profile.

Challenge consume и публикация lease атомарны под S→registry/battle lock, с повторной проверкой readiness/current scope/credential/profile/occupancy. Нет A/DB transaction через handshake RTT и нет нового financial transition ради transport reconnect. Exact complete replay в пределах живого handshake record возвращает ту же lease, не создаёт конкурирующую; изменённый request, истёкший/чужой challenge отказаны. Challenge cache bounded/rate-limited. После потери record/ответа допустим новый handshake, который для того же instance атомарно заменяет его прежнюю transport lease. Lease содержит server-issued ID/generation, runtime identity, lane, allowed target/scope и expiry; stale lease сразу теряет доступ. Секретные credentials не попадают в receipt/log. Restart сервера инвалидирует прежние challenges/transport leases по boot identity, но не меняет durable battle fence/assignment/Start.

`Execution` для занятого executor допустим только исходному runtime instance из common RuntimeAssignmentV1 и лишь для операций, разрешённых текущей phase. Новый транспорт не означает новую симуляцию. Живой исходный процесс после reconnect подтверждает фактический retained battle context/tick/dispatch-cut state до возврата к work; server restart сам не разрешает rebuild/resume симуляции из initial. Потерянный/непроверенный context закрывает execution и оставляет recovery. Если сервер восстановил финальный/terminal phase, даже исходный instance не получает Poll с preparation/commands. `AppliedAwaitingCleanup` и `CancelledAwaitingCleanup` разрешают лишь соответствующие evidence/replay/cleanup сообщения. До реконструкции common readiness/occupancy после restart никакой lane не выдаёт работу.

Новый runtime при active assignment может получить **только `RecoveryDelivery` для конкретного battle**, с отдельной записью transport registry; он не заменяет occupant/execution runtime и не получает Poll/Prepare/Start/command dispatch или tick authorization. Это допустимо и пока исходный процесс ещё жив: courier лишь доставляет immutable evidence. В envelope остаются original assignment/runtime/start lease/fence/nonce; новая lease идентифицирует доставщика, не автора симуляции. Совпадение executor/profile и полная проверка common evidence обязательны; профиль, отозванный после Start, допускается только по существующему as-of-Start recovery правилу, текущий credential revoke не обходится. Несколько deliveries сериализуются existing result identity/once checks; конфликтующий Final не вытесняет прежний.

RecoveryDelivery разрешает scoped artifact upload/immutable Final delivery/receipt replay и допустимый cleanup evidence. **Исходный живой runtime вправе подтвердить собственный SameProcessEntry через RecoveryDelivery**, если authenticated lease runtime ID в точности совпадает с RuntimeAssignmentV1, а actual build/profile совпадают с историческим binding этой assignment/Start. Текущий configured profile может уже отличаться: для terminal cleanup проверяется исторически разрешённый профиль (as-of-Start, либо as-of-assignment при pre-Start cancellation), без допуска к новым work/Start. Отдельная terminal-only Execution lane не нужна. Смена config/profile не обходит текущий credential revoke, durable scope/fence или запрет compromised runtime; неверный actual build/profile остаётся recovery failure, а не автоматическим cleanup.

Для этого исходный процесс отвечает на свежий server cleanup challenge main-thread измерением **actual Entry/no Game/no battle context/no tick hooks/no pending work callbacks**, с durable rejection исходной assignment и задержанных work packets. Отсутствие уже закрытой Game не мешает проверке: это ожидаемое terminal состояние; возобновлять Game или симуляцию ради cleanup нельзя. Common GuildExecutorCleanup проверяет exact terminal tag/assignment/current boundary/fence и только затем снимает occupancy. **Новый courier runtime ID не вправе подтвердить SameProcessEntry за исходный**, даже с тем же executor credential/profile; для него остаётся явный ProvedReplacement с доказательством прекращения прежнего процесса.

Если occupancy уже снята, exact result/cleanup replay возвращает только прежний receipt. Старый cleanup не меняет Active у новой assignment того же executor: binding включает исходный battle/attempt/assignment transition и terminal/challenge, а не только executor ID. Для следующего боя необходимы ordinary Execution handshake, текущее approval и Entry readiness, затем новая common assignment. Ни recovery lease, ни Hello не освобождают слот автоматически. Persistent common authority остаётся единственной authority; transport lanes — ограниченные эфемерные разрешения, не второй anchor.

`runtime_instance_id` создаётся shipping executor один раз на запуск процесса (случайный идентификатор высокой энтропии, не повторно используемый файл/PID). Additive Hello/Lease поля сообщают его серверу **до получения любой работы**, с executor/profile/build identity и challenge-response под executor authentication. Runtime ID сам не credential. Reconnect того же живого процесса сохраняет ID; перезапуск создаёт новый. Registry не может молча заменить instance при active occupancy.

До первого work/poll с инструкцией подготовки common Prepare transition сохраняет immutable `RuntimeAssignmentV1` в своей typed GuildCaptureOperation receipt: battle/campaign/attempt, executor/runtime instance, исходная lease identity, world/boundary/fence/nonce, profile approval/build binding и server assignment time. Это может быть вложенный record единственной Prepare operation, не второй commit/новая таблица. GuildBattle.Active=true резервирует физическую occupancy **до** выдачи work; даже потеря первого ответа не доказывает отсутствия работы. Poll/initial staging/prepared manifest/Start обязаны совпадать с assignment; неизвестный runtime ID не получает работу. После restart assignment читается из common history, не восстанавливается по догадке из текущего Hello. Новый транспортный lease того же instance не переписывает исходную assignment.

Pre-Start cancellation, включая NoAttackerReady, сохраняет своё настоящее campaign terminal reason/receipt и закрывает calendar/acquisition reservations, но при наличии committed runtime assignment оставляет `GuildBattle.Active=true/Phase=CancelledAwaitingCleanup`. StartManifest/StartDigest/FinalManifest/FinalDigest остаются null: не создаются фиктивные Final/winner. Work/Start/commands закрыты. Отсутствие initial upload, RPC ack, истёкший timeout или пустой registry не снимают barrier. Если campaign завершилась до любой runtime assignment, физический cleanup ей не нужен; отсутствие assignment должно быть доказано под authority, а не отсутствием сетевого ответа.

Cleanup использует tagged terminal binding: `AppliedResult` содержит реальный committed final/result digest; **`PreStartCancellation` содержит digest/reference точного typed campaign terminal receipt и RuntimeAssignmentV1**, без поля CommittedFinalDigest. Common `GuildExecutorCleanup` receipt связывает этот tag с battle/executor/original runtime ID, current boundary/fence, свежим одноразовым server challenge и observed time. Для `SameProcessEntry` отвечает аутентифицированный исходный instance: проверка на main thread подтверждает Entry, отсутствие battle Game/context/hooks и pending work callbacks, а также durable отказ от задержанных work packets данной assignment. Свежий challenge/cut не позволяет старому Entry heartbeat освободить уже занятой процесс. Cleanup commit один раз ставит Active=false; replay возвращает исходный receipt, не меняет terminal reason/pair cooldown и не вызывает owner/economy effects.

**`ProvedReplacement` — отдельный tag и явный operator recovery intent**, не Hello нового процесса вместо старого. Он связывает исходную assignment/terminal, доказательство прекращения старого owned процесса (проверенные host/process start identity, не только PID/недоступность сети), durable revoke/fence прежних полномочий, новый runtime ID/approved build и свежий Entry challenge нового процесса. Эти сведения/дескрипторы evidence входят в common receipt; нельзя заявлять same-process cleanup от replacement. Если прекращение старого процесса доказать нельзя, occupancy остаётся blocked/Maintenance. Ни timeout, ни новый healthy runtime сами не являются proof. Тот же порядок A→O→S→Live при необходимости→battle lock→DB; OS/network проверка вне held locks, её свежесть/identity повторно проверяются перед commit.

Restore сохраняет CancelledAwaitingCleanup и исходный terminal/assignment как historical facts, затем требует cleanup/recovery под новой boundary/fence. Старый challenge/cleanup proof не освобождает новую timeline. NoReady pair penalty не пересчитывается от времени cleanup/restart. AppliedAwaitingCleanup по-прежнему сохраняет уже applied capture. До согласованного восстановления обоих видов occupancy startup/poll/Prepare остаются закрыты. Все facts помещаются в существующие GuildBattle/GuildCaptureOperation и common archive evidence; 13 таблиц и единый anchor сохраняются.

**Lost Start authorization: retained `StartAcknowledgementPending`.** Добавляется явный enum/tag в retained runtime Hello proof, а не новая financial GuildBattle phase или третья transport lane. `InitialLoaded` сам по себе не разрешает post-Start reconnect. Новый tag означает: тот же непрерывно живой original runtime сохранил original assignment и prepared checkpoint/request UUID; actual initial Game всё ещё загружена; TickRuntimeBound=false, simulation не запускалась, native tick в точности InitialTick; command execution receipts и pending cuts отсутствуют. Main-thread challenge proof связывает это с exact prepared manifest digest (он же committed StartDigest), initial raw descriptor, original nonce/assignment/profile/build. Файл checkpoint без retained live Game и неизменного process instance недостаточен.

После server restart сервер сначала восстанавливает common readiness, затем проверяет existing StartCommitted того же assignment/digest/nonce, current boundary/fence, отсутствие abort/terminal/cleanup и фактически dispatched commands/неразрешённых cuts. Только при полном совпадении выдаётся `Execution` lease с ограничением **StartReplayOnly**: она разрешает exact replay исходного Start request UUID и получение прежней immutable authorization/StartedAt. Никаких Prepare, нового proposal/Start, command dispatch или разрешения simulation по одному Hello. Source request UUID извлекается из retained original request и сверяется с common idempotency binding; новый UUID не создаёт заменяющий Start. Остальные текущие authentication/profile/admission guards сохраняются.

Получив и проверив прежнюю authorization, runtime устанавливает tick controller и receipt journal один раз и сообщает authenticated `RuntimeStarted` proof, связанный с StartDigest/assignment/instance/lease. До durable transport acknowledgement этой готовности сервер не dispatch commands, а runtime удерживает tick barrier; повторы proof/ответа идемпотентны и не переустанавливают controller. После этого применяются обычные Running/context/dispatch-cut правила. Если ответ RuntimeStarted потерян, повторяется готовность уже связанного controller, а не возврат в StartAcknowledgementPending. A/S/DB не удерживаются через RTT; transport readiness record находится в существующем journal, не создаёт второй financial Start. Client controls могут ожидать, но не получать execution ack до действительного исполнения.

Changed nonce/digest/instance, tick≠InitialTick, уже существующий tick runtime/receipt, неизвестный cut либо утраченный live context запрещают этот узкий путь: применяется соответствующий доказанный Running/Terminal reconnect или recovery, не переигрывание initial. Cold process не получает resume даже при наличии всех файлов. Существующие wall-clock/coordinator deadlines продолжаются от первоначального StartCommitted и не сбрасываются replay: истёкший/неразрешимый Start уходит в technical recovery без winner. Проверенный исходный процесс лишь завершает потерянный handshake уже committed Start; состояние симуляции не восстанавливается предположением.

**Readmission после committed cleanup с потерянным ответом.** Исторический cleanup replay возвращает receipt, но сам не снимает hold новой registry lease. Для того же живого runtime instance допускается fresh ordinary Entry Hello: текущая authentication, новый challenge/boot, current approved profile/build, main-thread actual Entry/no Game/no context/no hooks/no pending callbacks и retained rejection старых assignments. В Complete под S→registry/battle lock повторно проверяются опубликованный verified common cut/readiness, отсутствие **любого active battle** в однослотовом stand и закрытие **всех сохранённых assignments удерживаемого runtime ID** точными typed common cleanup receipts (`Cleaned`), а не terminal reason/timeout/TechnicalAbort или одним совпавшим последним receipt. При missing/unknown/unclosed assignment, pending common transition, stale cut или конфликтующей provenance readmission отказан. History не сканируется как недоказанный произвольный список: проверяется полная assignment closure этого runtime в текущем common cut.

Только после этих проверок Complete атомарно удаляет устаревшую registry occupancy projection/lease и выдаёт свежую Entry execution lease; financial rows/cleanup history/outcome не меняются. Это восстановление проекции **уже доказанного** освобождения, не ProvedReplacement, не proof прекращения процесса и не новый cleanup. Новая assignment всё равно требует отдельного common Prepare. Race с Prepare/restore решается общей S/battle-lock границей и повторной проверкой cut; fresh Hello не освобождает вновь занятый slot. Actual Entry со старым/отозванным profile не даёт ordinary readmission, даже если cleanup исторически допустим.

RecoveryDelivery допускает read-only exact cleanup replay также для **pre-Start cancellation, уже Cleaned**: request содержит валидный tagged CleanupTarget PreStartCancellation с исходными terminal/assignment transition references и scope/runtime binding; сервер возвращает существующий committed cleanup receipt без требования несуществующего Start/Final. Новый courier вправе доставить запрос и получить разрешённый receipt, но не заявить Entry исходного процесса. Получение receipt разрешает клиенту reconcile локальный cleanup guard только для exact assignment, не служит разрешением нового work. Replay не снимает registry hold и не ставит Active=false повторно. Прежние boundary/restore provenance ограничения сохраняются; исторический receipt сам не авторизует новую timeline.

### 5.1. Typed profile и prepared manifest до Start

Полный inventory передаётся отдельным bounded artifact, не строкой display names внутри control frame. Descriptor содержит typed kind, SHA-256 полных bytes (ровно32 bytes), exact length; путь назначает сервер. Versioned canonical encoding задаёт порядок полей/списков, без maps и generic JSON bag; unknown/duplicate поля и неканонические bytes отказаны, digest domain-separated по типу/версии. Self digest не входит в хешируемые bytes.

**Два разных hash-контракта:** `ArtifactDescriptor.sha256 = SHA256(raw file bytes)`, без префикса; применяется к initial/final `.rws`, inventory/profile/start artifacts и проверке архива. `ProfileDigest`/`ManifestDigest` — отдельные 32-byte `SHA256(фиксированный discriminator типа + однозначно закодированная version + canonical document bytes)`. Codec фиксирует разделители/length encoding, исключая неоднозначную конкатенацию. Descriptor raw hash и semantic document digest имеют разные имена/назначение и никогда не сравниваются между собой; оба проверяются по одним полным bytes там, где artifact содержит typed document. Native `.rws` не получает выдуманный canonical document digest вместо существующего raw hash.

**Commander session binding:** поскольку текущая session имеет bearer token, но не отдельный Session.Id, использовать `session_digest = SHA256(фиксированный session discriminator + version + length-delimited exact bytes высокоэнтропийного bearer token)`, вычисленный сервером для аутентифицированного соединения. Plaintext token не входит в manifest/receipt/archive/log. Binding также содержит player ID, alliance ID, точные `AllianceMember.JoinedAt.Ticks` и control epoch; server session digest не принимается на веру из player payload. При Ready и Start сервер заново выводит digest из текущего bearer token и проверяет membership/epoch. Token rotation/relogin или leave/rejoin делают прежний binding непригодным до нового разрешённого Ready; после Start потеря binding отзывает control, но не отменяет outcome. Digest идентифицирует session, не является самостоятельным credential. Оба commander bindings обязательны; только defender может быть явным tagged `DefenderAI`, отсутствие полей не означает AI.

Строки версий только diagnostic, не замена hashes |
| `BattleProfileV1` | profile ID/revision, требуемый inventory descriptor; executor и viewer build/compatibility descriptors; template descriptor; typed rules 3000/30000/20min, AI30s/grace60s и allowlist Move/Attack/Draft; arena/zone; ровно8 стандартных fighter specs с side/placement и roster digest; exact encoding versions и admission limits |

Profile задаёт ожидаемые утверждённые facts, prepared manifest — конкретный матч. Executor attests фактическую среду после сохранения/reload initial; сервер сверяет её с approved profile, не признаёт присланный новый inventory автоматически approved. Viewer получает совместимость и snapshot descriptors без executor credentials. Hash не доказывает честность скомпрометированной ОС; доверие к операторскому runtime сохраняется. Shipping executor — собственный адаптер мода без BridgeTools/RimBridge dependency.

Лимиты v1: prepared manifest ≤8 KiB, profile ≤16 KiB, inventory ≤8 MiB/16 384 file entries/256 mods; package/version text ≤128 UTF-8 bytes, relative path ≤512 UTF-8 bytes. Load-order indices уникальны; file entries отсортированы root/path, дубли и case-ambiguous пути отказаны. Paths без absolute/UNC/`..`/reparse aliases. Runtime/config/defs обязательны; исключённые logs/cache/savedata перечисляются профилем явно, без wildcard, исключающего непроверенный исполняемый content. Snapshot ≤64 MiB/chunk≤256 KiB, control request/reply≤16 KiB. Profile/inventory/snapshot идут отдельным bounded artifact stream, затем адресуются digest. Quotas считают staged bytes; partial file не готовый artifact; oversize отказан, не усечён. Full approved inventory bytes удерживаются в archive/backup, одних hashes недостаточно.

Profile approval/revoke без новой таблицы: typed `GuildBattleProfileApproved`/`GuildBattleProfileRevoked` receipts в `GuildCaptureOperation` и immutable archive descriptors. Новый profile revision/digest требует нового operator approval; cached registry не обходит revoke. Это процедура допуска конкретной сборки, не повторное согласование числовых правил. Approval не заменяет qualification и не включает Product. Старый approved profile нельзя менять на месте.

Конфигурация `ApprovedProfileDigest` задаёт **semantic domain-separated ProfileDigest**, ожидаемый registry/Hello/Lease. До выпуска это имя заменяет ещё не развёрнутый `ApprovedProfileSha256`; старое имя не становится alias с другой hash-семантикой. Config не поставляет profile и не создаёт approval автоматически. Нужен явно заданный оператором локальный источник полного profile и всех referenced inventory/config/defs/template artifacts (новый config path либо контролируемая operator staging процедура, не путь из player RPC). Сервер читает bounded bytes, проверяет canonical encoding, вычисленный semantic digest против config/Hello/Lease и действующего common approval; raw SHA256/length проверяются независимо против staged profile descriptor и descriptors в approval receipt. Все referenced raw hashes/lengths и полная reference closure также обязательны; exact bytes удерживаются в Data.Archive. Missing bytes, только digest без документа, отсутствующий/отозванный approval или неполная reference closure → executor admission закрыт. Network download произвольного URL, доверие inventory присланному игроком и конструирование profile из defaults запрещены. Receipt ≤8 KiB содержит descriptors/digests/references, не полный inventory/profile; bytes доступны через bounded artifact store.

Prepared manifest допустимо хранить как отдельный immutable artifact kind `start`: raw hash/size/ref плюс semantic ManifestDigest в journal/Ready receipt. Это конкретная форма durable proposal из следующего порядка, без новой financial artifact row до Start. Ready может создать соответствующий control grant в той же common transition: его ID/epoch и commander binding заранее включены в proposal, grant credential не входит в manifest/receipt plaintext и не участвует в циклическом digest. В GuildBattle.StartManifest/StartDigest записываются canonical document bytes и semantic digest только при StartCommitted; start artifact raw hash сохраняется отдельно как descriptor. Approved profile и start artifact проходят одинаковые bounded archive/retention checks.

Порядок до первого simulation tick:

1. **Lease/initial staging.** Campaign/slot/acquisition/production cut закреплены common authority. Battle row Prepared содержит identity/fence/nonce, но StartManifest/StartDigest/StartedAt пусты. Executor создаёт карту, сохраняет и reload initial без боевых тиков, проверяет roster/profile. Initial и inventory artifacts завершены, flushed и hashed в Data.Archive.
2. **Prepared proposal.** Арбитр предлагает typed manifest; под S→battle lock сервер повторно проверяет опубликованные readiness/lease/fence/approval, descriptors и actual facts. Exact bytes/digest/proposal sequence записываются durable immutable записью в transport journal. Финансовый GuildBattle и per-upload GuildBattleArtifact не мутируют. Exact proposal replay идемпотентен; changed bytes под тем же sequence отказаны. Ready-enabled публикуется только после durable proposal.
3. **Attacker Ready.** Commander получает точные proposal bytes/digest, initial descriptor и viewer requirements и проверяет загрузку/совместимость. Ready intent связывает battle/fence/proposal sequence+digest/commander binding, не назначает rules/snapshot. Common GuildAttackerReady receipt под A/O/S→battle lock повторно проверяет proposal/role/approval/deadline. Это Ready для точного manifest, не для любого последующего состояния battle. Defender Ready не требуется; AI указан явно.
4. **StartCommitted.** Под A/O/S→Live при необходимости→battle lock заново проверяются policy/occupancy/slot/lease/fence/approval/Ready и artifact hashes. Один common commit копирует ТОЧНЫЕ prepared bytes в StartManifest/StartDigest, записывает server StartedAt, initial descriptors и start receipt со ссылкой на Ready receipt. Manifest не включает digest будущего Start transition или Ready receipt — иначе цикл Ready→manifest→Ready. Executor проверяет committed authorization/manifest/fence/nonce и только затем снимает tick barrier. Потерянный ответ повторяет прежнюю авторизацию/StartedAt, не второй Start.

До Start допустима явная superseding proposal с новым sequence при допустимом изменении commander binding/повторной подготовке; старые bytes остаются, прежний Ready больше не подходит, нужен новый до того же deadline. Максимум8 proposals/attempt; превышение — technical/recovery отказ без winner. У игрока нет API загрузки proposal. Profile/lease/boundary не меняются внутри proposal: требуется закрыть попытку, reconcile и назначить новый battle ID. После Start proposal immutable. Crash до Start не разрешает играть по найденному файлу; partial initial, отсутствие Ready или committed authorization оставляют staging. Backup связывает journal checkpoints/proposal и referenced bytes; restore не превращает proposal в Start. GC сохраняет всё, на что ссылаются Ready/Start/terminal/unresolved recovery.

**Loaded defs measurement v1.** `BattleRuntimeFacts.LoadedDefs` адресует отдельный canonical `BattleLoadedDefsV1` document: ordered packs с normalized package ID, load index и content SHA; внутри каждого pack — actual loaded Def identities, ordinal sorted по отдельным полям CLR type full name и defName, без неоднозначной конкатенации. Type привязан к соответствующей assembly entry полного inventory. Document также содержит явно помеченный `outpost-game-defs-v1` fingerprint существующего `OutpostManifestCapture.DefsFingerprint()` и descriptor отдельной canonical settings projection. Старый fingerprint не переименовывается в новый semantic digest и не меняет свой codec. Pack identity/load order/content и settings должны согласовываться с тем же измеренным runtime inventory. Измерение actual defs проводится на game main thread после завершения загрузки defs/settings, не по списку XML filenames; отсутствие content readiness, дубли identities, неизвестные assembly references или неполное измерение дают отказ.

Bounded codec: document ≤8MiB, ≤256 packs и ≤65 536 Def entries суммарно; package ID ≤128 UTF-8 bytes, type full name и defName каждый ≤512 UTF-8 bytes. Checked counts/lengths до allocation; превышение — отказ, без truncation. Raw descriptor и domain-separated document digest различаются по §5.1. Полные exact Defs/Patches/Assemblies source bytes и approved settings projection доступны в referenced inventory/archive closure; один существующий fingerprint не заменяет это evidence. Измерять после reload initial перед proposal; до tick authorization удостовериться, что runtime/config generation не менялась после измерения. Изменение требует новой подготовки, а не игнорирования расхождения.

Это **compatibility provenance и состав actual loaded defs**, не сериализация всех значений runtime fields Def, не доказательство детерминированного replay и не защита от произвольной injected mutation внутри доверенного процесса. Для C с отдельным operator-owned executor этот scope достаточен: доверие опирается также на approved full content/build/config и квалификацию shipping adapter. DirectXmlSaver, generic recursive reflection serializer и копирование игрового кода не требуются. Отдельная обязательная проверка после reload initial подтверждает фактические восемь бойцов, side mapping, roster/loadout и arena/objective по typed profile; она не называется полным Def-state hash. Профиль с неизвестной runtime мутацией, мешающей этим проверкам/квалифицированному исполнению, не получает admission; v1 не обещает поддержку произвольных модов через один fingerprint.

### 5.2. Initial defender control и reconciliation после Start

**Техническая нормализация standard baseliner (9 ноября 2026).** «Без генетических боевых преимуществ» не означает `Genes.Count=0`: RimWorld1.7.5000 создаёт core Melanin/HairColor genes и без Biotech, а отсутствие melanin после reload может вызвать его восстановление. Для всех восьми бойцов фиксируются ровно два одинаковых **endogenes**: `Verse.GeneDef` с defName `Skin_Melanin6` и `Hair_DarkBlack`; xenogenes и любые другие genes отсутствуют. Дубли, substituted cosmetic genes, overridden/inactive дополнительные genes и mod-specific gene implementations не допускаются. Нельзя просто удалить все genes и принять повторно появившиеся как произвольную норму. Это уточнение уже утверждённой одинаковой baseliner-нормализации, без изменения roster силы/правил боя и без нового Product approval.

Названия проверены в measured loaded-defs artifact `e13b442763b172473ac2695d3d712f5d3314f9573027f26dd82345758c4620b6` stand D (package `ludeon.rimworld`). В локальном Core `Defs/GeneDefs/GeneDefs_Endogenes.xml` прочитаны concrete definitions и их abstract parents: Skin_Melanin6 задаёт skinColorBase `(242,199,140)` и minMelanin0.63; Hair_DarkBlack задаёт hairColorOverride `(0.2,0.2,0.2)`. Parent payloads содержат косметические категории/selection/display/exclusion и не задают боевые stats/abilities/hediffs. SHA256 этого exact XML `783012a9d8bc5f24c171fd9744a9579abd2f3b51c7457a370ac07d857abed07f` присутствует в measured full inventory. Название категории само по себе не является доказательством безопасности; profile/content/patches/loaded-def identity closure остаётся обязательной. Это локальные доказательства разрешённой пары, не утверждение о произвольных GeneDef/mod runtime mutations.

HairColor parent имеет randomBrightnessFactor0.12, поэтому одних двух defNames недостаточно для одинаковой внешности: нормализация закрепляет actual story hair color `(0.2,0.2,0.2)` и skin base `(242/255,199/255,140/255)` с полной alpha, одинаково для всех8. Пара genes, фактические цвета и baseliner identity входят в versioned roster/template contract и его digest; source/profile после правки заново измеряются/утверждаются штатным operator profile admission, прежний artifact не редактируется на месте. Верификация выполняется после нормализации ДО сохранения и после реального reload initial, включая разрешение story colors, которое может вызвать lazy восстановление gene: exact set/endogene count2/xenogene count0, отсутствие остальных genes/добавленных преимуществ, одинаковые цвета и остальные roster/health/loadout параметры. При расхождении — отказ initial, а не молчаливый post-reload repair перед Start. Для core цветов допускается только заранее заданная малая tolerance сериализации float, не случайный диапазон яркости. Native HOME/SLICE после изменения остаются NOT RUN до фактических проверок. Исходники игры/decompiled implementation в репозиторий не переносятся.

`ReconcileControl` — authenticated player request с request ID, battle ID, ожидаемым StartDigest и прежним epoch, если он известен. Сервер выводит сторону из заранее назначенных `GuildCampaign.AttackerCommanderId/DefenderCommanderId`; payload не назначает сторону, командира или membership. Initial attacker grant остаётся частью AttackerReady. **Initial defender grant выдаётся через ReconcileControl после StartCommitted**, без DefenderReady и без дополнительного условия Start. До появления действующего соединения защитника исполняет AI. Human binding в Start — исходная identity, не доказательство выдачи capability или присутствия. Пропавшая/заменённая session защитника не блокирует Start и не требует нового attacker Ready: exact manifest bytes сохраняются, текущее управление проверяется отдельно. Проверка текущей session на Ready/Start из §5.1 обязательна для атакующего; её несовпадение у защитника закрывает human control, а не начало боя.

Tagged DefenderAI также фиксирует заранее назначенного eligible defender player ID, если он есть в campaign, без фиктивной session. Этот командир может подключиться через ReconcileControl. Если командир не назначен к Start, сторона остаётся AI весь матч: назначения нового игрока после Start в v1 нет. C сохраняет одного заранее выбранного командира на сторону; relogin не является переназначением. Campaign commander IDs и alliance IDs после Start неизменны.

Общий transition `GuildBattleControlReconciled` под A→ordered O→S→Live при необходимости→battle lock→DB проверяет StartCommitted, current scope/fence, ещё исполняемый бой (не terminal/AppliedAwaitingCleanup), действующий profile/admission, командира, membership и server-derived session digest. Existing policy/freeze/debt guards не обходятся. Он отзывает прежний active grant стороны, создаёт один `GuildBattleControlGrant` и одну typed `GuildCaptureOperation` receipt ≤8KiB. Receipt связывает battle/StartDigest/world/boundary/fence, сторону/player/alliance/JoinedAt, session digest, grant ID/epoch, capability digest, expiry, причину InitialDefender/Reconnect/Renew и заменённый grant. Для первой выдачи допустим зарезервированный manifest epoch при точном исходном binding; последующие epoch строго выше всех прежних для стороны. Для AI baseline первый epoch задаёт сервер. Новых таблиц и изменений StartManifest/StartDigest не требуется; дополнительные bindings хранятся в typed receipt под общей authority.

Capability — высокоэнтропийный секрет, выдаваемый только текущей authenticated session; в storage/receipt/archive только digest. Exact request replay возвращает ту же grant identity/receipt и не генерирует другой секрет под тем же epoch. Если секрет потерян и его нельзя безопасно повторно выдать, новый request явно заменяет grant новым epoch; historical receipt не служит credential. Expiry ограничен концом боя и коротким control TTL; renewal — редкий rate-limited common transition, не каждый command/poll/ack. Старый epoch/session теряют admission после публикации committed projection под S. Leave/rejoin требует проверки текущего JoinedAt и нового grant; членство другой стороны не переносит контроль.

Один authenticated control channel на сторону; attach/replacement проверяет действующий grant и connection epoch под S→battle lock. Grant сам по себе не означает живое соединение. Для отсутствующего защитника AI действует с первого tick; после потери установленного control — через 30s отсутствия валидной активности по monotonic clock. Невалидные сообщения не сбрасывают таймер. Policy/session/membership revoke немедленно запрещает human commands, AI подхватывает по тому же правилу 30s; terminal/recovery закрывает новые команды полностью. Новый подтверждённый channel возвращает human control на следующей границе tick, без одновременных AI и human orders. Только Move/Attack/Draft для сущностей своей стороны, с server-side проверкой.

Journal фиксирует control cut/epoch с distributed dispatch barrier, описанным ниже. **Отзыв grant прекращает admission новых команд и dispatch, но не отменяет задним числом уже выданное разрешение исполнения.** Side sequence при смене epoch не сбрасывается. Start описывает начальное состояние, subsequent common receipts и transport cuts — историю control; все входят в terminal evidence closure. Hot path не приобретает authority.

#### 5.2.1. Accepted / Dispatched / Executed и distributed cut

`Accepted` означает durable journal append под S→battle lock после проверки session/grant/fence/limits, с server side sequence и immutable command digest. Это не исполнение. `Dispatched` означает отдельную durable запись **до** выдачи poll response: batch ID, exact command IDs/digests/sequences, runtime instance/start identity, fence и control epoch/cut generation. Эта запись — точка выдачи bounded разрешения исполнителю; delivery без такой записи запрещён. Lost response не возвращает batch в Accepted: retry повторяет тот же batch/identity. Повторная доставка не исполняет команду второй раз.

`Executed` означает, что доверенный executor действительно применил Move/Attack/Draft на native main thread; это не обещание завершения игрового job или попадания атаки. Ack связывает command/batch/cut, execution ordinal и simulation tick. `NotExecuted` означает, что команда не применялась, с явной причиной. Сервер может самостоятельно завершить таким статусом только Accepted, **никогда не Dispatched**. Поздний authenticated Executed от разрешённого batch не переписывается в NotExecuted из-за более позднего revoke. Конфликтующие terminal ack — recovery/integrity failure, не last-write-wins.

Revoke/session replacement/profile withdrawal под common authority закрывает admission и новый dispatch прежнего epoch; под S сохраняет `ControlCutRequested` с возрастающим cut ID, common transition reference и полным bounded набором unresolved dispatched commands. Accepted без dispatch получает NotExecuted(RecalledBeforeDispatch). Dispatched остаётся `AwaitingCut`, даже если poll response потерялся. После commit новое control connection может получить grant, но **новые human dispatch этой стороны не разрешены до CutApplied**. Отказ/неоднозначность записи cut удерживает admission закрытым; recovery восстанавливает недостающий journal cut из committed authority facts до открытия hot path. A/S/DB не удерживаются через сетевой или игровой RTT.

Executor обрабатывает cut и выполнение команд последовательно на game main thread. Полученный cut устанавливает tick boundary: ранее реально применённые команды подтверждаются Executed с их исходными tick/ordinal; остальные перечисленные команды удаляются/помечаются NotExecuted и больше не применяются, включая delayed packets прежнего batch. `ControlCutApplied` содержит cut ID, boundary tick/ordinal, полный набор этих terminal outcomes и digest. Tombstone/cut сохраняется для повторной доставки. Проверка «current cut перед исполнением» означает последний **применённый executor cut**, а не недостижимое знание текущего server state через сеть: Dispatched до server revoke может легально исполниться до получения cut. Это ограниченное уже выданное разрешение, не новая команда от отозванной session. Cut не откатывает уже применённые orders и их игровые последствия.

До CutApplied runtime не принимает successor human epoch для стороны. AI/human handoff также сериализуется на tick boundary; прежнее правило AI30s сохраняется, выдача AI orders не должна обгонять ещё не разрешённый cut. Для изначально отсутствующего защитника без dispatched commands AI доступен сразу. Server-side cut считается завершённым только после durable проверки exact coverage всех unresolved dispatched IDs и их непротиворечивых outcomes. Ack от старого control player не нужен: его выдаёт текущий authenticated executor transport с исходной batch/runtime identity, по правилам cold evidence. Нельзя обойти restore/global fence или заменить утраченную симуляцию новым runtime.

Лимиты сохраняются: 40 commands/s и 64 pending/side, причём pending включает Accepted, Dispatched и AwaitingCut до terminal ack. Не более одного unresolved dispatch batch на сторону; batching позволяет выдать несколько команд за poll и не требует financial digest на команду. На каждом poll/ack под S повторно проверяются опубликованные readiness/lease/fence и pending cut. Typed append records хранятся в том же durable battle transport journal; новая финансовая таблица/authority не нужна. Backup cut включает dispatch/cut/outcome records, handles закрываются до отпускания S.

Final допускается к финансовому Apply только при полном terminal manifest, непротиворечивых command outcomes и закрытых cuts для всех dispatched разрешений. Даже если runtime уже увидел победу, unresolved delivery/cut не становится NotExecuted по timeout и не даёт capture. Транспортная пауза использует существующий coordinator grace60s/frozen tick; потеря достоверного runtime/evidence ведёт в RecoveryRequired либо отдельный подтверждённый TechnicalAbort, без победителя/передачи и без нового72h shield. Crash между применением команды и durable ack не решается её повторным исполнением: прежняя симуляция не возобновляется догадкой; нужен допустимый полный durable final/evidence либо technical recovery. Already-applied outcome сохраняется по прежним cleanup/restore правилам.

**Operator startup inventory/config.** §5.1 уже требует runtime/config/defs и явные исключения. Gameplay config включает все настройки simulation/defs/mod load/rules. Credential, endpoint/pin, локальные roots/state directory, PID/log/cache и чисто оконные настройки — operational data; исключения перечисляются явно в approved profile, не скрывают executable/content и не исключают весь Config с gameplay настройками. Отдельный строго типизированный connector config можно исключить целиком; смешанный файл требует versioned canonical projection с точным allowlist operational keys и отказом неизвестных ключей, а не произвольного удаления перед hashing. Secret bytes не входят в inventory/archive/log. Startup измеряет gameplay projection и full content inventory и сверяет approval/semantic digest/raw descriptors; config ApprovedProfileDigest сам ничего не утверждает.

Build roles v1: `GameBuildSha256` — реально загруженный Assembly-CSharp.dll; `RuntimeBuildSha256` — assembly `typeof(object)` (System.Private.CoreLib.dll); `ClientBuildSha256` — Rimlink.Client.Core.dll; `ExecutorBuildSha256` и `ViewerBuildSha256` — shipping Rimlink.Client.dll с соответствующим adapter. Build facts получают из реально загруженных `Assembly.Location` и проверяют против full inventory/approved profile; совпадение hash произвольного файла не доказывает загрузку нужной сборки. Недоступный/неоднозначный location — fail-closed, не подстановка operator path. Runtime hash не заменяет проверку остального engine content. Operator config задаёт roots/source canonical bundle и отдельные credential path/endpoint pin/state directory; готовый launcher или новые engine flags этим не объявляются.

Для боевого tick/rules/arena адаптируется собственный прототип после выделения game-free rules/contracts; production не ссылается на `tools` или RimBridgeServer. Реальный исполнитель — установленный лицензированный game process с отдельным executor adapter и operator config. Нет выдуманных headless flags. Один процесс/матч, отдельный supervisor launcher допускается только с проверенными путями и собственными PID. Auto-download game/mod binaries не входит в поставку.

Полноценный viewer — настоящая загруженная battle map у двух клиентов с authoritative snapshots/deltas, selection/боевыми orders и overlay зоны/результата. Не debug grid. `BattleClientContext` отдельно от `LiveSession`, `VisitSession` и pawn custody. Он устанавливается ДО смены Game и живёт до восстановления дома. Домашняя canonical save до входа закрепляется обычным протоколом; неподтверждённый upload/pending recovery запрещает вход. Выход всегда загружает проверенную домашнюю canonical version; при missing mods — Entry/recovery, не пустая карта и не загрузка battle save как home.

Battle context запрещает personal save/upload, ordinary/custody/market/mailbox materialization, incident/caravan/pod/outpost actions на battle map, стандартный autosave и загрузку произвольной колонии. Quit/crash оставляет persistent battle-view marker с home world/generation/boundary/version/hash; relogin reconciles его до обычной загрузки. Session network живёт для player auth/command, но не делает battle map «собственным домом». Executor вообще не создаёт player `RimlinkSession`.

Переиспользуются только доказанные части DeltaCollector/MirrorApplier/ThingBlobs; `LiveGuest` через personal VisitSession не вызывается. Старые MirrorMode patches должны учитывать typed mode и маршрутизировать battle orders отдельно. Viewer не симулирует TickManager, RNG, здоровье/смерть/production; разрешены визуальные interpolation updates. Восьмёрка бойцов получает side mapping, не ложные player custody IDs. Snapshot/entity IDs строго battle-local; reconnect заменяет mirror baseline и command watermark. Duplicate view принимается идемпотентно, conflicting seq отказан; старые deltas не откатывают карту. Зрители, если есть, read-only; v1 grants только двум командирам, без spectator feature expansion.

## 6. Result, crash и restore

Результат: только lease-bound executor; server валидирует identity/rules/build/initial/final artifact manifests, terminal predicates, expected owner revision, reservations, freeze/fence/boundary. Доверие к operator/runtime не превращается в обещание независимого deterministic replay. Main-thread evaluation в конце каждого DoSingleTick; следующий тик после terminal не исполняется. Native final snapshot и journal durable до envelope. Command/results и acknowledgements идемпотентны; промежуточный game replay не поддерживается.

**Cold Final: transport authorization отдельно от исходной battle identity.** После restart сервера/доставщика разрешена новая текущая authenticated transport lease того же ExecutorId с тем же semantic ProfileDigest для доставки готового финала. В immutable Final envelope остаются исходные runtimeInstanceId, start lease identity, battle attempt/fence/nonce, StartDigest и profile/build identity; они сверяются с durable StartCommitted, а не заменяются новой registry lease. Новый runtime instance выступает только доставщиком, не автором прежней симуляции. Сам restart transport registry не повышает persistent battle fence и не переписывает StartManifest. Если же был явный durable revoke/fence/abort/restore, новая transport lease его не обходит.

Первое принятие cold result требует существующего StartCommitted (одного Prepared недостаточно), текущей boundary, неизменного разрешённого battle fence, Active occupancy и отсутствия ранее committed abort/конфликтующего результата. Все referenced initial/start/final/simulation/transport artifacts полностью доступны и совпадают с immutable manifests; формальные predicates результата проверяются обычным путём. Разрешена только доставка sealed bytes/получение receipt и последующий verified cleanup, не возобновление тиков, новый Start или выдача команд от старого instance. Если result уже applied, exact повтор возвращает тот же receipt даже после завершённого cleanup (`Active=false`), при действующей boundary и корректном authenticated recovery access; это read/replay, не второе применение. Изменённый envelope отказан. Новая boundary или противоречивая provenance требуют recovery, а не автопринятия прежнего финала.

**Profile revoke после Start.** Право конкретной сборки исполнять уже начатый бой доказывается approval, действовавшим на позиции StartCommitted в authority chain, не только wall-clock timestamp и не текущим config. Последующий profile revoke блокирует новые preparation/Start и выдачу/renewal player control; текущие control grants отзываются, стандартное offline AI правило действует. Сам revoke не меняет winner и не отменяет автоматически честный уже исполненный outcome. Для restricted cold-final/receipt/cleanup lane допускается исторический profile, approved именно для этого Start, даже если ordinary Hello/admission уже запрещает его для новых боёв. Текущая аутентификация executor всё равно обязательна; отдельный credential/executor revoke не обходится ссылкой на старый profile approval. При подозрении на неправильный runtime/build либо actual manifest mismatch — RecoveryRequired; остановка активного боя выполняется явным common abort/fence transition, сериализованным с result. Profile revoke не считается таким abort молча и не выдумывает defeat.

**Ready и новая player session.** Сохранённый Ready не переиспользуется как разрешение под новым bearer/session digest. До Start relogin требует разрешённой superseding proposal с новым commander binding и нового Ready в исходном deadline/лимите attempts; старый receipt остаётся историческим. После Start proposal/StartManifest неизменны: применяется только control reconciliation с текущими membership/session/control epoch и полномочиями стороны. Relogin не отменяет outcome, не создаёт новый Start и не делает игрока другой стороной. Исторический Ready допустим как доказательство принятого Start, но не как текущий login/control credential.

Server loss → pause на tick boundary, 60 секунд grace; wall limit 20 минут → TechnicalAbort, не defender victory. Executor crash без durable финала → revoke/recovery/abort, без guessed owner. Crash с durable финалом → resend exact envelope; захват один раз в общем authority transition вместе со stock obligation. Это включает external-anchor crash checkpoints, не только SQLite commit. Duplicate terminal return содержит тот же receipt и terminal view; conflicting final не заменяет его.

Backup берёт общий согласованный cut: existing saves/custody + guild tables/projection + referenced battle artifacts/commands/manifests + parcel delivery proofs. Uploaded staged unreferenced files не становятся доказательством. Versioned restore сначала проверяет неизменный исходный cut в его V1/V2/V3 формате, затем отдельно квалифицированную additive schema step. V1/V2 cut не получает выдуманной guild history. V3 cut сохраняет completed transitions/old obligations/accepted parcels; незавершённые campaigns закрываются без победы, reservations освобождаются только после reconciliation. Production checkpoint rebased без downtime yield.

Перед переключением DB/files durable restore fence отзывает executors и control grants; после restore новый boundary. Старые настоящие envelopes, cached maps, pending commands и guild delivery outbox не переносятся автоматически. Selected snapshots сохраняют прежний provenance; typed restore authorization связывает исходный parcel/save proof с новой timeline, не переподписывает прошлое. Late post-cut physical import обнаруживается как existing recovery problem и запрещает повторную материализацию. Однопользовательский rollback также обязан учитывать guild delivery proofs, хотя владение object не привязано к generation.

Restore различает незавершённый боевой исход и **уже applied результат с ожидающим cleanup**. Для `AppliedAwaitingCleanup` selected cut сохраняет принятый owner/obligations/result/receipt, не превращает campaign в TechnicalAbort или новое поражение и не применяет capture второй раз. Старое physical occupancy остаётся blocked/recovery до подтверждения clean runtime под новой boundary/fence; прежний cleanup proof не освобождает новый executor автоматически. Restore reconciliation может менять лишь operational barrier/lease по доказанному cleanup/recovery переходу, не пересчитывать завершённый исход. Даже cut с уже очищенным runtime не даёт права стартовать в старом процессе без новой runtime admission после глобального restore fence.

## 7. Готовность и предел этапа

Первый измеримый slice: два настоящих player clients + независимый executor, один заранее размещённый Steel объект → настоящая победа → один owner transition → old-stock obligation прежнему союзу → будущая выработка новому → типизированный claim/materialization/canonical save receipt дома. Ни одна battle pawn/вещь не экспортирована; home snapshot не заменён battle map. На acceptance composition разрешено ускорять SERVER test clock для 24h/72h, но production game victory не подменяется SetWinner, а real tick rule не ускоряется обходом.

Сначала slice на изолированном стенде и общей authority, затем вся campaign/policy/restore fault matrix. Безопасность не откладывается: до начала slice должны пройти format/history и home-save isolation gates. Изменение общего source/build требует новой применимой Safety и Product qualification для затронутого personal domain. Ранние G1–G7 и prototype receipts не являются seal.

### 7.1. IsolatedAcceptance composition до Product qualification

**Общая V3 safety и независимые capabilities.** GuildRuntimeAdmission не может сам выставить CanRunDomainWriters/CanResolveCustody поверх отрицательного common readiness. Минимальная композиция — **один evidence-backed acceptance provider** с двумя проекциями одного immutable bootstrap/prerequisite record: common safety через существующий `IOutpostBuildQualification`, guild HOME/SLICE scope через typed GuildRuntimeAdmission. Dev host заменяет production default provider единожды, а не регистрирует два конкурирующих IOutpostBuildQualification и не подделывает OutpostProductQualification. Common projection имеет Mode=IsolatedAcceptance, State=Pending для полной Product qualification, фактически подтверждённые AutomatedPrerequisitesVerified/IsolationVerified и exact SourceIdentity. Полный native acceptance не обозначается пройденным ради bootstrap. Required integration coverage/prerequisites проверяются явно для этого acceptance scope; неизвестный или непроверенный необходимый safety seam не объявляется Implemented ради снятия блокировки.

Common readiness получает явно поддержанный V3 safety contract: проверенные current schema/catalog, activation/history, Ready authority/anchor, scope/source/build evidence и отсутствие pending/maintenance. Просто заменить сравнение V2 на «V2 или V3» недостаточно без этих доказательств; V1/V2 qualified/historical readers и правила не ослабляются. Для V3 common writers/custody доступны только при положительном common safety readiness, включая пустой guild stand: старый shortcut «нет истории» не даёт V3 admission сам по себе. GuildRuntimeAdmission затем **сужает**, а не расширяет это разрешение до HOME/SLICE и допустимых guild operations. Несовпадение common/guild source/stand/world/boundary или evidence record закрывает обе проекции.

В guild acceptance `AdvertiseCapability` личных passive outposts жёстко false независимо от config; их create/assign/production/claim требуют собственной passive capability и не получают права из CanResolveCustody/CanRunDomainWriters. Common custody разрешает необходимые обычные transfers/returns и защиту существующей истории только в пределах прошедших общих guards, не создание пассивного объекта. HOME не разрешает guild owner/economy Apply; SLICE разрешает их лишь через отдельный guild scope. Unknown readiness остаётся refusal, RuntimeComposition=true. Это разделение safety от feature admission, а не второй authority или blanket «Product qualified». Обычная production composition не получает IsolatedAcceptance provider из config и остаётся OFF до своей qualification.

Для native HOME/SLICE нужен отдельный **dev-only host**, использующий shipping server services и shipping game adapter, но собственный строго ограниченный qualification/admission provider. Его capability называется `GuildCaptureIsolatedAcceptanceV1`, mode — `IsolatedAcceptance`; это не `ProductEnabled`, не Safety/Product seal и не `RuntimeComposition=false`. RuntimeComposition остаётся true, все обычные authority/session/custody/save/transport проверки исполняются. Production composition не регистрирует acceptance provider и остаётся fail-closed; unit storage fixtures не становятся сетевым host. Никакого общего config/env switch, превращающего обычный сервер или существующую DB в acceptance, не добавляется.

Dev host создаёт **только новый пустой owned DataDir** под отдельным выделенным stand root: canonical absolute path, запрет reparse/symlink aliases и пересечения с любым используемым production/game/user data root, exclusive creation/lock до DB creation. Нет attach/import/copy существующей DB. До инициализации создаётся versioned immutable acceptance marker: случайный stand ID, canonical root, owner/run identity, source fingerprint (включая untracked shipping sources), exact server/core/client/executor build hashes, schema/catalog version, approved runtime/profile identities и prereq evidence descriptors. Путь/marker сами по себе не дают допуска: host проверяет полный bootstrap record и фактические bytes. Общая authority initialization связывает mode+stand ID+world/boundary с этим record, чтобы удаление marker не превращало acceptance world в production. Потеря/несовпадение marker, identity или source/build закрывает startup; restart возможен только для ранее созданного тем же host stand с проверенной цепочкой, не adoption произвольного каталога. Смена build требует нового проверенного acceptance run/bootstrap, не редактирования старого record.

Изолированный host слушает только loopback, использует отдельные порты, credentials/TLS pin и allowlist тестовых player/executor identities; credentials production не импортируются. Три лицензированных локальных процесса имеют собственные savedata и shipping build, executor без player session. Negotiation включает отдельный typed mode/capability и stand ID: GuildVersion1 здесь означает поддержку протокола, а не Product enable. Обычная composition продолжает GuildVersion0/OFF до своей qualification; default client не входит в acceptance автоматически, только явно выбранное локальное тестовое подключение с проверенными pin/stand identity. UI/status/evidence явно показывают IsolatedAcceptance, Product OFF; личные passive outposts не включаются.

**До первого native HOME** обязательны фактические source-bound automated prerequisites: V1/V2 history/golden неизменны, V3 schema/activation/digest и common authority pending/replay/fence tests зелёные; targeted session/role/artifact bounds/dispatch-cut guards зелёные; typed battle context/home recovery/canonical save isolation tests зелёные; shipping server/core/mod собраны из закреплённых bytes; approved local profile/reference closure и executor identity измерены, чужие процессы/data исключены. Это предварительный acceptance safety record со списком реально выполненных checks и оставшихся NOT RUN, не утверждение о пройденном native HOME. Начальный scope допускает HOME/transport на disposable colonies, но не economy/owner Apply: итог может быть собран и cleanup проверен без применения capture. **До SLICE** дополнительно нужны native HOME PASS на этих identities и targeted capture/claim/receipt/wealth/generic-negative checks; отдельный append-only acceptance admission record расширяет scope до isolated SLICE. Нет циклического требования пройти native HOME до разрешения его первой проверки. Незавершённые полная fault matrix/RESTORE/Wiki/итоговое review явно остаются pending.

**Точное завершение HOME — вариант A.** Под «итогом и cleanup без capture» выше понимается pre-Start terminal, не боевой Final. HOME загружает verified initial map у исполнителя и pre-Start mirrors двух игроков через shipping battle context, проверяет home save isolation/return/reconnect/crash guards, затем выполняет настоящую pre-Start cancellation и `PreStartCancellation` cleanup исходной assignment. В HOME сервер запрещает StartCommitted, RuntimeStarted/tick authorization, command dispatch и любой battle Final Apply, включая TechnicalAbort через Final. Поэтому не нужны acceptance-only outcome kind, fake Final или фиктивная победа. Для штатной проверочной отмены используется существующая разрешённая pre-Start cancellation с честной причиной, а не искусственный NoAttackerReady penalty.

HOME scope явно допускает необходимые **setup common transitions**: создание тестовых alliances/колоний, operator placement и initial owner assignment после настоящего head acquisition consent, approval измеренного profile, campaign/slot/acquisition reservation, Prepare/runtime assignment, initial/proposal artifacts, pre-Start viewer access, cancellation и verified cleanup. Все идут через штатные authenticated services, правила consent/лимитов/window/notice/common authority сохраняются; прямые DB seed или обход RuntimeComposition не допускаются. Начальное назначение согласившемуся владельцу — разрешённый setup, не capture result Apply. Необходимые штатные settlement/pause/rebase при prepare/cancel сохраняют настоящий accounting; HOME не разрешает отдельный production/clock RPC для выдачи ресурсов. Claims/parcel materialization/боевой owner transition остаются закрыты. Allowlist scope проверяется сервером по типу операции, не просьбой клиента «это HOME».

HOME PASS доказывает именно безопасность pre-Start map/home lifecycle. Positive human Move/Attack/Draft, RuntimeStarted, реальная battle tick simulation/Final, applied-result cleanup и возврат домой после боевого результата проверяются впервые в SLICE после HOME и money-negative prerequisites; они остаются NOT RUN до своего сценария. В HOME проверяются отсутствие ticks/command execution и отрицательные side/phase guards, а не заявляется успешное боевое управление. Прохождение HOME не заменяет эти части Task5/6/7 и не является полным native acceptance.

**HOME setup clock — разрешённое уточнение test SERVER clock.** Dev-only host может предоставлять operator-authenticated локальную команду `AdvanceSetupClock` с finite purpose `EligibilitySetup` либо `ScheduledWindowNotice`, stand/run ID, request UUID, expected clock revision, exact positive delta/target и ссылкой на конкретные setup identities/campaign. Это не production API/config flag и не запрос игрока. `EligibilitySetup` используется для возраста тестовых участников/колоний и предусмотренных shield/window сроков до объявления campaign; `ScheduledWindowNotice` — для достижения уже законно зарезервированного окна после полного notice. Clock не меняет значения правил 7d/24h/72h, membership timestamps или campaign rows задним числом: исходные записи и последующие проверки используют один согласованный domain clock. Один шаг ≤7 суток; конечные cumulative budget и число steps фиксируются в immutable run/bootstrap до запуска и исчерпание даёт отказ, не безлимитное ускорение.

Перед step и непосредственно перед публикацией provider проверяет HOME scope, точные source/build/world/boundary/bootstrap, verified current common cut/readiness, отсутствие pending/recovery и **любого Active battle**, включая Prepared/CancelledAwaitingCleanup/AppliedAwaitingCleanup. Порядок A→ordered O при необходимости→S→battle lock; никакой acquisition A из-под S. Scheduler/Prepare сериализуются на той же границе: если assignment успела commit, step отказан. При существующей scheduled campaign target не позже самого раннего active ScheduledAtUtc; step не перепрыгивает Ready window/deadline, не создаёт NoAttackerReady штраф и не переносит booking. Несоответствующий purpose, отсутствие target campaign для notice, нулевой/отрицательный/overflow delta и превышение run budget отказаны. После Prepare реальный pre-Start lifecycle идёт без clock jumps.

До изменения наблюдаемого времени flush-ится append-only step journal: request/digest, purpose/target references, before/after domain clock samples/revision, real observation time, stand/source/scope и common cut reference. Exact retry не добавляет delta повторно; changed request digest отказан. Crash до/после durable step восстанавливает только полный проверенный prefix до открытия admission; неизвестный prefix/разрыв scope закрывает host. Журнал и начальный clock mapping входят в согласованный acceptance backup/evidence cut; нельзя откатить clock отдельно от domain state. Это audit/test-control evidence, не второй asset authority/anchor. Clock projection согласует UTC и используемый OutpostClock elapsed/checkpoint semantics, не считает разные времена для eligibility и accounting.

Сдвигается только явно внедрённый **business-domain test clock**. TLS/auth/challenge/lease expiry, network deadlines, coordinator grace, AI30s, executor wall20m, heartbeat health и native simulation ticks используют реальные wall/monotonic clocks и не ускоряются. HOME clock step сам не вызывает settle/production/claim/parcel/Final и не выдаёт ресурсы. Разрешённый позднее штатный Prepare/cancel может выполнить своё обычное settlement/pause/rebase на согласованном времени; его реальные accounting effects фиксируются общей authority, но отдельная issuance/claim остаётся закрытой. SLICE требует отдельного admission, clock scope сам его не даёт. Report явно отделяет virtual eligibility/notice от реально пройденных суток и native runtime evidence; это не доказательство многодневной стабильности.

Provider проверяет scope, source/build/stand/world/boundary, prereq record integrity и реальное common readiness при каждом admission; «есть marker» не заменяет проверки. Record scope не даёт bypass другого guard. Source drift или незавершённый authority recovery закрывает admission до повторной применимой проверки. Все acceptance outcomes/receipts сохраняют common authority semantics и отдельное происхождение; их нельзя использовать как Product qualification. Использование тестового SERVER clock ограничено dev host, game victory остаётся настоящим.

Первичный HOME/SLICE host **не предоставляет импорт/bulk restore/reset существующего мира**. Acceptance backups явно несут mode+stand/bootstrap identity в проверяемом manifest и authority provenance; обычный Product restore отказывает таким cut, даже после переименования пути/удаления внешнего marker. Production backups не принимаются dev host. Поздний Task9 restore fault stand допускается только отдельным acceptance scope с заранее проверенным cut того же isolated lineage и новым owned target, с теми же source/fence/boundary проверками; это не универсальный restore bypass. Acceptance host/provider/launcher не входят в release/package и не включают Product flags. Полная Product qualification и enable остаются отдельными последующими действиями.

Capture capability по умолчанию OFF, server выдаёт её лишь при применимых доказанных gates, корректной authority V3, approved manifest и доступном executor. Личные пассивные аванпосты сохраняют отдельный Pending/OFF и свои условия; capture не включает их побочно. Документация RU/EN описывает фактические доказательства и оставшиеся ограничения. Один итоговый обзор всей новой реализации; никакого повторного ревью прототипа.
