# Admin reset возвращает старый локальный сейв

**GAME FAIL, 2026-11-02, Rimlink 0.7.0 / `25f6c8a`.** После административного сброса колонии клиент загрузил прежнюю карту,
поскольку автоматически отправил оставшийся локальный файл на сервер. Новая серверная версия получила номер 1 и старый tick 91517.

Это выполнено только на копии частной тестовой базы `build/game-acceptance/reset-archive-server`, порт 25786.
Рабочий сервер и исходная тестовая база не сбрасывались. Runtime в ходе исследования не менялся.
Логика уже присутствует в `main@9e70b25`: reset появился в `9558c34a`, recovery без pending — в `a4f8bed9`;
оба коммита являются предками main. Это не только ограничение новой тестовой ветки.

## Воспроизведение

1. У игрока есть сохранённая колония и обычный локальный multiplayer-файл; игрок входит и сохраняется.
2. Для проверки escrow продавец выставляет настоящий Wood ×1, этот игрок резервирует ставку 10.
3. Игрок выходит; администратор выполняет reset. Аукцион отменяется, товар и ставка возвращаются один раз.
4. Подождать 31 секунду, чтобы тест не маскировал результат лимитом Saves.Upload — 3 запроса за 30 секунд.
5. Тем же игровым профилем войти снова, сохранив старый локальный файл.

**Ожидалось:** прежняя колония сброшена, переход к новой колонии; старый файл сам не возвращает её на сервер.

**Наблюдалось:** `rimlink/connect` завершился `Loading`, а не `NewColony`; открыта прежняя карта 131351,
программа Playing, tick 91525. Сервер перед загрузкой принял старый файл как v1 с tick 91517.
Сохранность экономики отдельно подтверждена: одна возвратная посылка, один delivery ack, кошелёк восстановлен без второго кредита.

Первый случай reset продавца попал на ограничение частоты выгрузок: отказ UploadLocal отложил старый файл как rejected,
после чего действительно открылась новая колония. Этот случай подтверждает возврат escrow, но **не опровергает дефект**.
Повторный сценарий с паузой исключил маскировку лимитером.

## Причина по исходникам

- `AdminOperations.ResetPlayer` архивирует серверные сейвы и удаляет мировые объекты.
- `SaveStore.Archive` удаляет версии и обнуляет LastOutgoingTick для следующей колонии.
- `LoginPlan.Decide` выбирает UploadLocalThenLoad при наличии локального файла и отсутствии серверного сейва.
- `LoginFlow` отправляет этот файл и после успеха загружает его. На этой границе нет отличия административного reset
  от восстановления после не дошедшей первой выгрузки.

Нельзя исправлять это безусловным удалением локальных файлов при пустом сервере: это сломает существующее восстановление после сбоя.
Нужен однозначный признак смены колонии/поколения сохранений, проверяемый сервером и клиентом. Конкретный контракт исправления здесь не утверждался.

Минимальный вариант для отдельного проектирования: постоянный SaveGeneration игрока, увеличение при reset,
передача в LoginReply/SaveHeader и запись поколения в самом локальном сейве. Файл старого поколения сохраняется отдельно,
но не выгружается автоматически; отсутствие legacy-поля после reset не означает текущее поколение.
Сервер повторно проверяет поколение перед commit под общей с reset блокировкой. Поколение из нового login нельзя просто
присвоить старому файлу: иначе защита отсутствует. Recovery того же поколения, в том числе crash до pending.flag, должен сохраниться.

Имеющиеся Feed.Epoch и ColonyRestore решают другие задачи. Первое — запуск feed-процесса, второе — восстановление архива;
они не являются поколением сохранения. Производный маркер из reset-аудита также потребовал бы новых гарантий:
нынешний reset пишет аудит после операций со сейвами. Предложение не реализовано; схема/протокол не менялись.

и отдельным подтверждённым эффектом не объявляется. Автоматический suite остаётся зелёным: он не проверяет этот полный игровой путь.
