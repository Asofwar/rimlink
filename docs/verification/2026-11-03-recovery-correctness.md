# Восстановление сохранений и передач — 0.8.1

Исправление десяти проблем восстановления, найденных в 0.8.0. База — `404a67edd62e4114046500f3e0eab7ff4e306abb`.
Проверки выполнены 3 ноября 2026 года. Это протокол разработки, а не сообщение о публикации релиза.

## Что изменилось

| Проблема | Результат и проверка |
|---|---|
| Почта читалась до восстановления локального сейва | Сначала выбирается и проверяется снимок, выполняется его восстановление и согласование журнала, затем перечитываются независимые состояния. Порядок проверен по `LoginFlow`; игровой перезапуск после доставки описан ниже. |
| Журнал создавался после изъятия, а возврат забывался до сохранения | Фазы Prepared → Ready и Returning с XML-подтверждениями удаления/возврата; запрос не отправляется до принятого снимка. Проверены файловые границы, настоящий отказ и авария перед записью файла. |
| Терминальное live-состояние могло отделиться от возврата escrow | Возврат пешек и конечное состояние фиксируются одной транзакцией. Тесты прерывают INSERT посылки и UPDATE состояния; настоящий незавершённый визит восстановлен после входа. |
| Откат отменялся старым клиентом | Отдельный монотонный write epoch; проверка при commit сейва и изменениях имущества. В игре старая карта блокирует запись, выход через кнопку не сохраняет отменённое состояние, новый вход загружает разрешённую ветвь. |
| Pending-флаг появлялся слишком поздно | Намерение фиксируется до записи основной XML; следующий запуск согласует его с реально записанным файлом. Целевые тесты покрывают смерть до postfix, неудачную запись и старый cache. |
| Параллельные выгрузки читали меняющийся файл | Неизменяемые копии и последовательная очередь; старое завершение не очищает новое pending-состояние, уборка защищает queued/in-flight файлы. |
| Один игровой тик не отличал две доставки | GUID снимка, raw hash и список receipts вместо одного tick. В игре проверены два снимка на одном тике, авария до ack, три повторных входа и единственное зачисление серебра. |
| Ключ запроса пересекался между игроками и операциями | Индексы actor/operation/key и проверка неизменности намерения. Тесты разных игроков, операций, изменённых данных и legacy-записей. |
| Настройки модпака раскрывались до пароля | Пароль проверяется до settings-bearing diff, включая регистрацию. Добавлено поле пароля регистрации, прежние номера protobuf сохранены. AdminBypass остаётся. |
| Ошибка кошелька обрывала всё восстановление | Кошелёк, почта, рейды, инциденты, social и live загружаются независимо и повторяются. Старый клиент воспроизвёл потерю видимости почты/Ending при global freeze, обновлённый восстановил оба состояния. |

## Итоговое ревью и исправления

Проведён один обзор всего неизменяемого пакета, SHA-256 патча:
`df90dada47af5e3f20d837782e04b9ecf1f87a1a525dabff86ebffdf8bfc1528`.
Один проход исправлений закрыл четыре P1 и два P2:

- повторный rollback с ранее отслеженным Player теперь перечитывает epoch внутри транзакции;
- fencing распространяется на raid launch/announce/land/report, live proposal/report и shop publish/ack;
- отложенные запросы привязаны к авторизации снимка; replay и callback не могут подставить новый токен после reconnect;
- старый shop-ответ проверяет game, connection, авторизацию и scope до поиска ThingId;
- download выбирает текущий файл и его generation/epoch под одной storage-блокировкой;
- pruning выполняется с защитой всей очереди выгрузки, включая снимок между двумя другими.

Регрессионные тесты сначала воспроизвели epoch 1 вместо 2, старые байты с новым epoch, семь принятых RPC старой ветви,
отправку старого запроса с новой авторизацией и удаление ожидающего файла. После исправлений они проходят.
По той же причине отчёт о пешках без добычи сохраняет требование removal-proof; посадка рейда подтверждается только
после сохранения его на карте. Повторного параллельного ревью не проводилось.

## Автоматические проверки

На окончательном коде после исправлений:

- Windows, `dotnet test Rimlink.sln -nologo -v minimal`: **1644/1644** — server 1113, client 404, Discord 122, BridgeTools 5;
- Ubuntu 24.04 в WSL, Release, ограничение на **два CPU**: те же **1644/1644**, все четыре сборки;
- мод и dev companion собираются; релизная папка мода содержит только обычные восемь DLL;
- новые локализованные ключи есть на английском и русском; protobuf только расширен, ProtocolVersion не изменён;
- новая миграция сохраняет старые файлы и ключи, дополняет известное владение legacy и не выдумывает хеш старого намерения.

## Настоящая игра

Отдельная копия RimWorld 1.7.4995, два профиля и свежая БД, HTTPS :25650. Рабочий сервер и установленный мод не менялись.
Для воспроизведения использован релизный клиент 0.8.0, затем мод 0.8.1 из текущего дерева. Проверки выполнены на английском.
Товары считались по всем вложенным объектам XML карты, включая закрытые капсулы.

## Границы доказательства

- Если выбранный холодный снимок не доказывает удаление Prepared-операции, отсутствие маркера не считается доказательством
  наличия товара в старом сейве. Payload и локальные файлы сохраняются для ручной сверки; автоматического возврата наугад нет.
- Каждый возможный момент физического сбоя, отключение питания, disk full и все межпроцессные сочетания не воспроизводились.
  Части матрицы подтверждены транзакционными и файловыми тестами, а не принудительным завершением игры.
- Обычная новая продажа через shop UI и отдельный торговый диалог не перепроверялись в этом прогоне; их серверные и core-тесты проходят.
- Реальные GOG, Steam-аутентификация и Discord не перепроверялись; новой GOG-копии и Discord-профиля нет.
- Downgrade после новых scoped keys требует восстановления предварительного backup, а не удаления индексов с новыми данными.
