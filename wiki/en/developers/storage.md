# Storage and escrow

Applies to: Rimlink 0.10.1 · RimWorld 1.7 · protocol 1.

## Usage {#usage}

Schema changes require an EF Core migration and a schema test. Run dotnet ef migrations add &lt;Name&gt; --project src/Rimlink.Server (without -nologo). Migrations apply at startup.

Only SaveFiles knows filenames: &lt;n&gt;.rws.zst is full, &lt;n&gt;.d&lt;k&gt;.zst is a delta against base-&lt;k&gt;.rws.zst. Size/Sha256 describe full content even when stored as a delta. Only OpenCurrent guarantees rebuilding the current version; never assume a full file exists for every older row. Verify hashes before trusting an existing file.

Escrow retains outgoing items/pawns/silver until settlement and returns them through mail. Live state changes under LiveStateLock with the row read inside it. Backup holds PerStoreLock and save-storage.lock through the database snapshot and save packing.

### Colony generation versus write epoch

`SaveGeneration` changes on reset so an old local save cannot become a new colony's first version. `SaveWriteEpoch` changes on administrative rollback within the same generation so an old session/outgoing operation cannot overwrite the administrator's selected timeline. The save version number is a separate sequential identifier, not either counter.

Upload checks header generation/epoch, recovery proof and the epoch captured by the session; mismatch yields SaveGenerationMismatch or SaveWriteEpochMismatch. After rollback the client must receive current authority and a snapshot, not replay stale outbox intent with rewritten metadata. Regression scenario: begin an old upload, roll back, then continue that upload; it must be refused without changing the current save.

## Investigating a damaged save safely {#storage-repair}

Preserve version rows and an immutable file copy first, then open full content through SaveFiles. Do not derive an older path from its number: it may be a delta. Size/Sha256 describe full reconstructed bytes, not delta size.

Full+delta can signal interrupted rebuilding. Compare raw contents/metadata before deleting a supposedly spare file. A matching filename does not prove its hash. Backup/restore share the storage lock; manual SQL/copying outside it destroys consistency evidence.

Schema changes need migrations and schema regression tests. Reproduce repairs on a copy and name unrecoverable/recovered versions explicitly rather than promising complete recovery.

## Limits and safety {#limits}

Do not delete the lock file. A full file plus spare delta may be an interrupted rebuild: compare raw contents and metadata first. A zstd prefix and input must not share one array. Never commit *.db or data directories.

## How is legacy history preserved when adding guilds? {#guild-domain-v3}

Version 0.10.0 adds 13 separate financial guild tables through one additive EF migration. Existing tables, V1/V2 writers, immutable receipts, and old descriptors remain unchanged. The V3 digest binds the exact V2 digest, new tables, and canonical alliance ownership/membership; ordinary treasury changes are outside that projection. New tables stay empty until explicit activation. Financial operations hold authority → ascending colony locks → storage → LiveStateLock when needed → battle lock when needed → DB transaction.

Commands, acknowledgements, and current views do not recompute the financial digest. Commands use a durable transport journal under archive, with a hash chain, size/queue bounds, and refusal of damaged records. It cannot change owner/stock and has no second asset anchor. Its final seal must enter the common financial transition; the arbiter transport delivers it. Only a terminal view belongs in the battle table.

Eight new exact schema profiles were generated by actual Windows/Linux migrations and read by both readers. Earlier 14-table development profiles were superseded before shipment; their results do not qualify this schema. Do not normalize SQL bytes. qualification-v3.json qualifies catalogs, not Product. Shared stock/obligations are not personal colony wealth; a typed claim assigns manifest value to a fixed recipient, and canonical acceptance must move it into physical wealth without double counting. Delivery and restore were verified on isolated stands on 10–11 November 2026; the setting is off by default.

Battle transport uses S → the single battle lock with a separate read-only SQLite context, no pooling, and no A acquisition. It compares the published verified head/world/boundary with the current database header; publication occurs only after the common external-anchor commit. Startup errors or incomplete commits close admission. Polling, initial upload, and prepared proposals do not change the financial head.

Full profile/inventory/config/defs/template/qualification bytes are immutable under archive/guild-profiles, addressed by typed raw hashes. GuildBattleProfileApproved/GuildBattleProfileRevoked are common authority receipts in the existing GuildCaptureOperation table. The proposal journal uses consecutive immutable start-1…start-8 artifacts within battle/fence; a partial newer proposal prevents falling back to an older Ready. GuildAttackerReady and GuildBattleStarted are low-frequency protected receipts, separate from the hot journal. StartManifest/StartDigest/StartedAt and completed initial/start artifact references appear in one StartCommitted transaction. A command not executed before terminal receives an acknowledgment without an accepted tick. An outstanding dispatch or control cut blocks sealing and returns retryable `Unavailable` from Final. The executor keeps draining acknowledgments, and the same frozen envelope can be applied once the required evidence arrives. Final/capture/cleanup and complete issued-resource restore remain unfinished Product work.

GuildBattleApplied is one common operation with a nested versioned terminal receipt. The whole old stock becomes an obligation of the previous alliance. Capture changes the owner and revision and resets the new stock and remainder. Defence and draw preserve them. Production resumes from the terminal checkpoint and skips battle time. Gameplay outcomes receive 72 hours of protection. TechnicalAbort preserves any existing protection and increments the abort counter. The third enters Maintenance. Campaign, acquisition and slot reservations end atomically, while the battle remains active in AppliedAwaitingCleanup until verified cleanup. A new resource claim publishes a typed mailbox event after the protected commit. An exact replay returns the original receipt without a second parcel or event.

R3 preserves `AppliedAwaitingCleanup` and `CancelledAwaitingCleanup` with the original assignment, fence, and receipt from the selected cut. Cleanup under the new boundary uses a separate scope with the original fence incremented by one. The common receipt proves that the restore plan preserved the exact assignment, and the cleanup changes only arena occupancy. Once committed, fresh Entry can establish a new execution lease. An assignment without a verified result or cancellation remains closed.

The R3 plan binds pending guild parcel IDs, original recipients and payload digests. It retires a started attempt only when the selected canonical save matches the attempt's before-proof. Retired attempts keep their original authorization and never accept a late receipt. Historical accepted receipts cross the new boundary only through the verified source snapshot. Colony rollback with an issued claim remains blocked.

The assignment can retain the host identity, OS PID and process start time verified at Hello. After the durable restore fence, `ProvedReplacement` records both process identities and the evidence for the selected boundary in the common cleanup receipt. Cleanup releases occupancy while preserving the selected owner, outcome and stock. A fresh execution Hello is still required.

The isolated RESTORE plan binds the archive digest and original acceptance identity to a fresh target identity. Retained evidence reads the original cut, while the verified common chain admits the target boundary. The original binding and setup-clock receipts remain in the history.

Technical cancellation before Start admits the finite SimulationAdmissionUnavailable reason: simulation is forbidden in HOME. The common journal validates this reason alongside the other allowed TechnicalBeforeStart reasons; unknown values are refused. Cancellation does not free the physical slot before verified tagged cleanup.
