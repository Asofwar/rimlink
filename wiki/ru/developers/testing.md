# Тестирование и приёмка

Применимость: Rimlink 0.10.0 · RimWorld 1.7 · протокол 1.

## Как пользоваться {#usage}

Для квалификации executor фиксируйте фактически загруженные .NET/ASP.NET runtime, provider и native SQLite identities. Выбор SDK сам по себе не выбирает runtime patch. У квалификации 10.0.14 отдельные точные QualificationId/ProviderProfile; legacy witness 10.0.13 остаётся самостоятельным. CI на main выполняет полный набор; тег может использовать только успешный завершённый main push того же commit с успешными шагами Build/Test, сохраняя run и attempt без заявления о повторном выполнении тестов.

Сначала воспроизведи сценарий и увидь падающий целевой тест, затем минимальное исправление и повтор. Серверные тесты используют настоящий WebApplicationFactory; client-core тесты общаются с тестовым сервером. Полный набор: dotnet test Rimlink.sln -nologo -v q.

Для миграций с точными байтами собирайте свежие Git LF исходники на Windows и Linux. Копирование Windows working tree через rsync сохраняет CRLF и не воспроизводит чистый CI checkout. Проверяйте точный SQL миграции, полный реальный SQLite catalog и lineage, а также закреплённый additive recipe. Сохраняйте исходные профили и отрицательные результаты; проход скопированных исходников подтверждает только эти байты.

Поток Open вернулся — это ещё не peer attached: утверждай по полученным событиям. Таймауты измеряй Stopwatch, не DateTime.UtcNow. Для timing-изменений повтори набор на Linux/двух CPU при доступности среды.

Игровую логику проверяй двумя изолированными экземплярами host/guest, отдельными savedata и сервером/портом. BridgeTools/RimBridge — только доступный dev-инструмент, не зависимость релиза. Запиши фактически выполненные шаги и результат в manual checklist; сценарий сам по себе не является PASS.

Для нового тестового мира администратор может передать dev-компаньону `rimlink/start_colony` параметр `planetCoverage`. Значение `0` сохраняет штатный выбор, доступны `0.3`, `0.5`, `1`. Значение `0.05` требует включённого dev mode и выбирает штатный вариант игры 5%. Ненулевой параметр принимается только до первой генерации мира. Для существующего мира он отклоняется. В результате `steps` сохраняется применённое значение. Экспортируй весь фактический мир и записывай число клеток, seed и идентификатор манифеста.

Wiki: test:checks → check:content → check:reference → check:drift -- --base &lt;commit&gt; → build → check:links, затем реальный браузер/поиск/мобильная навигация.

## Какая проверка отвечает на какой вопрос? {#test-matrix}

| Проверка | Подтверждает | Не подтверждает |
|---|---|---|
| Solution build/tests | Core/server contracts, storage, mocked boundary scenarios | Игровой UI/Scribe/пешки |
| Build-ClientMod | Компиляцию против установленной игры | Успешный двухсторонний сценарий |
| Два изолированных клиента | Реальное исполнение конкретных шагов | Все моды/DLC/GOG-комбинации |
| Wiki validators/build | Структуру, ссылки, inventory | Верность смысла статьи |
| Browser acceptance | Поиск, навигацию, layout в проверенных размерах | Все браузеры и настоящий OS zoom |

Для bugfix сначала наблюдай RED на исходном сценарии, затем GREEN. Для сетевого потока жди полученное событие, не возврат Open. Deadline измеряй Stopwatch; для time/race-изменений повтори Linux/two-CPU, если доступно.

Для Discord проверяй постоянные и временные ошибки отдельно: 403/404 отключают только исходящую доставку в проблемный канал до рестарта, а 429/5xx сохраняют пакет. Тестируй заголовки `#`, `##`, `-#` и начало новой строки как пользовательский текст. FakeDiscordOut позволяет задать точный отказ без настоящих токенов; такой прогон не подтверждает подключение к Discord.

Для ещё не выпущенной проверки модов собственной колонии используй сохранение, которому нужны моды сверх серверного манифеста, включая вход администратора. Отсутствие модов должно останавливать загрузку скачанного сохранения и локальное pending recovery до upload или очистки pending. После восстановления полного набора отдельно проверь настоящую загрузку карты. Обе ветки проверены в настоящей игре: отказ для скачанного сохранения/загрузка с полным набором и отдельный local-pending отказ без DLC с неизменными файлами, последующим однократным принятием того же snapshot и успешной загрузкой. Штатный выход также записал сохранение на изолированном сервере. Штатный выход с новым сохранением на рабочем сервере остаётся непроверенным; эти случаи не означают двухпользовательскую приёмку аванпостов.

## Как проверяется исследовательский арбитр захвата? {#capture-prototype}

Автоматический захват разрабатывается отдельным dev-only прототипом. Сам он не включает гильдейские объекты или экономику на обычном сервере. `tools/Rimlink.BattlePrototypeHost` — локальный coordinator с отдельной SQLite и фиктивным владельцем; в `Rimlink.sln` и release-пакеты он не входит. Нужны три собственных процесса одной установленной игры: арбитр и два контроллера в Entry, раздельные savedata и отсутствие `RimlinkSession`. Разрешение лицензии на такой запуск проверяют до подготовки стенда.

Сначала выполните Task 0 утверждённого плана `docs/superpowers/plans/2026-11-08-guild-outpost-capture-prototype.md`: собственная копия runtime, одинаковые моды, нейтральный vanilla template и проверенные `stand.json`/`evidence/env-verified.json`. Нельзя направлять coordinator на рабочую установку или данные сервера. На уже подготовленном стенде:

```powershell
dotnet run --project tools/Rimlink.BattlePrototypeHost -- prepare --stand 'D:\Build\RimlinkCaptureStand'
dotnet run --project tools/Rimlink.BattlePrototypeHost -- serve --stand 'D:\Build\RimlinkCaptureStand'
# Отдельный терминал:
dotnet run --project tools/Rimlink.BattlePrototypeHost -- inspect --stand 'D:\Build\RimlinkCaptureStand'
dotnet test tests/Rimlink.BattlePrototype.Tests/Rimlink.BattlePrototype.Tests.csproj -nologo -v q
```

`prepare` создаёт отдельный battle ID и три секретных role bindings; не публикуйте их. Companion собирают штатным `Build-BridgeTools.ps1` только в собственную игру при закрытых её процессах. `rimlink/battle_bind` проверяет процесс, savedata, сборки и отсутствие player session. Арбитр использует `battle_prepare`/`battle_start`; контроллеры — `battle_view`. `battle_status` показывает реальные тики, приказы, состояние и receipt; `battle_stop` снимает только собственные hooks. Подготовка ждёт окончания загрузочного затемнения и разрешения игрового управления.

Только для собственного fault-стенда: `fault --stand <root>` отзывает executor; `rotate-boundary --stand <root>` меняет restore boundary и fence. `fault --stand <root> --at <point>` вооружает однократный Exit(86) при достижении точки: `before-initial-file-complete` и `after-final-durable` завершают арбитр, `before-start-commit`, `after-start-commit`, `after-view-commit` и `after-result-commit` — coordinator. Маркер `.consumed`, файлы и SQLite сохраняют для проверки; неизвестный исход не очищают и не запускают заново под тем же battle ID. Точный повтор последней view после потери ответа принимается; иное содержимое с тем же номером и устаревшая sequence отклоняются. Это контролируемое завершение процесса, не физическое отключение питания.

Арбитр сохраняет и повторно загружает карту с восемью одинаково оснащёнными бойцами. Только он симулирует бой. Контроллеры показывают полное малое состояние в native debug окнах и отправляют Move/Attack/Draft своей стороны; это не полный native-map mirror. Правила: 3000 непрерывных тиков удержания, сброс при contest, предел 30000 тиков; wall-clock не превращает техническую остановку в победу защитников. Отключённой стороной через 30 секунд управляет ИИ; при потере coordinator тики приостанавливаются, после 60 секунд — TechnicalAbort. Итог с готовыми native snapshot/journal применяется один раз; холодный арбитр повторяет сохранённый envelope без повторной симуляции.

Фактические gates ENV/CONTRACT/ENGINE/FEASIBILITY/RESULT/FAULT и незавершённые проверки записываются в `docs/verification/2026-11-08-guild-outpost-capture-prototype.md`. Unit tests, три окна или один receipt не заменяют весь набор. Взаимное поражение, подготовленное debug-действиями, отмечают отдельно от естественного боя. Прототип не квалифицирует production restore, массовый scheduler, модпаки, escrow, физический power loss или полный диск. Публикация, deploy и включение Product требуют отдельного решения.

## Как записать воспроизводимую приёмку? {#acceptance-record}

Укажи commit, версии, отдельный DataDir/порт, host/guest savedata и исходное состояние. Запиши действия, ожидаемые и наблюдавшиеся результаты, id операций, return mail и сохранение/повторный вход. Снимок UI без проверки серверного результата не доказывает escrow.

Для coop проверь назначенную/неназначенную пешку, выход, отзыв и rollback. Для экономики — неизвестный ответ и исходный replay. Не запускай чужие игры и не обнуляй общий Player.log. Незавершённый сценарий отмечай partial, не PASS.

В текущем продолжении добавлены целевые Core-проверки tick gate, операторского конфига, полного inventory, отдельного executor transport, трёх приказов, финального capture и personal-save guard. Совместный целевой client-прогон: 214/214 PASS; серверный Upload отдельно отклонил 2/2 варианта боевого XML с сохранением прежней canonical версии. Эти результаты не заменяют полный suite на окончательной сборке, Linux/two-CPU qualification или реальный прогон трёх игр.

Нативные модули собираются штатным Build-ClientMod.ps1 в отдельный OutputDir. Перед подключением hooks сверена установленная Assembly-CSharp.dll и прочитан фактический DoSingleTick: terminal проверяется в postfix, следующий tick закрывается prefix. На той версии нативный арбитр и два viewer ещё не запускались; они проверены позже, на стендах 10–11 ноября 2026 года.

Дополнительные автоматические проверки покрывают неизменность назначения до начала работы, переподключение в том же процессе, результаты отправленных команд и срезы, отдельного доставщика и Final с историческим профилем после смены или отзыва конфигурации. Тесты checkpoint проверяют некорректные поля, смену области и адреса, полный пакет после холодного запуска, потерянный ответ Final и неверные ответы транспорта. Выполнение после перезапуска, полная матрица отказов и замеров и квалификация Product ещё впереди.

## Ограничения и безопасность {#limits}

Не запускай второй сервер на данных живого сервера и не останавливай чужую игру. Общий Player.log может перезаписываться экземплярами. Не называй незапущенный тест успешным.

## Как проверяется Product-разработка захвата? {#guild-capture-product}

В отдельной ветке проверяются GuildProduction/GuildBattleSchedule, 13 финансовых таблиц, явная активация V2→V3 и базовый R3 restore. Восемь новых каталогов прошли чтение на Windows/Linux. После отделения command journal целевые 113 тестов прошли на Windows и трижды на двух CPU Linux. Прежний R3 snapshot прошёл 1717 Outposts/Backup/Storage тестов; это не проверка последующих services. Позднейший семейный серверный срез прошёл 483 теста трижды на двух CPU Linux; это предшествует новым RPC и игровому обработчику.

Внутренние services размещают нейтральный объект, фиксируют exact consent главы, начисляют будущую выработку и атомарно создают typed resource claim/parcel. Вступление и смена главы связаны с общей authority. Роспуск при нерешённых guild assets пока отказан. Обычный mailbox ACK и старый клиент не подтверждают typed выдачу. На той версии вызов новых object/claim services из публичного API ещё не был открыт.

Командный журнал проверен на replay, конфликт, очередь, повреждение, seal и закрытие файлов. Замер 48000 команд с durable ack дал mean 1,05 ms и p99 3,57 ms на локальном диске; сеть/auth/contended storage/game loop в него не входили, это не transport qualification.

Серверные тесты проверили exact canonical receipt, первое подтверждённое сохранение, crashes authority и отсутствие ложной wealth freeze. Клиентский журнал и materialization decision прошли 19 целевых тестов; чтение закреплённого manifest — ещё 3 серверных. Штатная сборка мода успешна, но настоящий игровой прогон новой выдачи ещё не выполнен. На той версии арбитр, полное боевое зеркало, кампании и issued-resource restore ещё не были готовы. Печать квалификации в 0.10.0 снята; по умолчанию настройка выключена. Прототип не заменяет приёмку. Факты находятся в docs/verification/2026-11-08-guild-capture-product.md. Целевая команда: dotnet test tests/Rimlink.Server.Tests/Rimlink.Server.Tests.csproj --filter FullyQualifiedName~GuildCapture.


Позднейший срез доставки: 986 клиентских и 173 целевых серверных теста PASS; сетевой поднабор — 123 PASS. После него начальные registry/campaign/preparation/artifact проверки прошли 38 случаев. Preparation фиксирует накопленный запас и останавливает выработку, но не передаёт владельца и не подтверждает Start. Registry по умолчанию выключен; отдельный credential handler уже подключён, его auth/rate/refusal набор прошёл 278 случаев, отказ startup без обязательных параметров — ещё 1. Подключение Ready/terminal, настоящего боя и результата ещё не завершено.

На исправленной сборке ещё предстоит проверить доставку без выхода из колонии и очистку.

На сборке со штатной кнопкой **Открыть бой** оба командира вошли в изолированный бой с восемью бойцами. До Start все три процесса оставались на тике 580. Оба командира вернулись штатной кнопкой, а ID и хеши их домашних сохранений совпали с каноническими сейвами на сервере. Прогон проверил вход и возврат. Итог боя и выдача остались за его пределами.

Серверные тесты покрывают получение исходным процессом точного задания на подготовку или отмены и отказ для другого процесса или частично загруженной арены. Исправленный вход арбитра ещё предстоит повторить в игре.

Первый настоящий независимый процесс успешно выполнил profile preflight: 7433 файлов, Harmony/Core/Rimlink/RimBridgeServer, без DLC. Предварительный отказ из-за пустой ModVersion Core сохранён отдельно; отсутствующая версия теперь явно unknown, game/runtime всё равно закреплены SHA-256. Крупный inventory проверяется через отдельный compact viewer descriptor. Это измерение runtime/reference closure, не HOME/SLICE PASS и не бой. Процесс штатно закрыт, установленная игра не менялась.

## Порты нескольких игровых мостов {#isolated-gabs-ports}

Standalone RimBridge 2.3 использует один фиксированный порт; второй процесс в таком режиме может отказать с socket address already in use. Для одновременных клиентов используется установленный GABS с собственной конфигурацией через server stdio --configDir и отдельными game IDs/savedatafolder. Глобальную конфигурацию и чужие игровые процессы менять не требуется. Готовность подтверждается game API и фактическими путями; transport contextDelivery unknown не считается доказанным контекстом.
