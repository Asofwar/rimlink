# Тестирование и приёмка

Применимость: Rimlink 0.9.2 · RimWorld 1.7 · протокол 1.

## Как пользоваться {#usage}

Для квалификации executor фиксируйте фактически загруженные .NET/ASP.NET runtime, provider и native SQLite identities. Выбор SDK сам по себе не выбирает runtime patch. У квалификации 10.0.14 отдельные точные QualificationId/ProviderProfile; legacy witness 10.0.13 остаётся самостоятельным. CI на main выполняет полный набор; тег может использовать только успешный завершённый main push того же commit с успешными шагами Build/Test, сохраняя run и attempt без заявления о повторном выполнении тестов.

Сначала воспроизведи сценарий и увидь падающий целевой тест, затем минимальное исправление и повтор. Серверные тесты используют настоящий WebApplicationFactory; client-core тесты общаются с тестовым сервером. Полный набор: dotnet test Rimlink.sln -nologo -v q.

Для миграций с точными байтами собирайте свежие Git LF исходники на Windows и Linux. Копирование Windows working tree через rsync сохраняет CRLF и не воспроизводит чистый CI checkout. Проверяйте точный SQL миграции, полный реальный SQLite catalog и lineage, а также закреплённый additive recipe. Сохраняйте исходные профили и отрицательные результаты; проход скопированных исходников подтверждает только эти байты.

Поток Open вернулся — это ещё не peer attached: утверждай по полученным событиям. Таймауты измеряй Stopwatch, не DateTime.UtcNow. Для timing-изменений повтори набор на Linux/двух CPU при доступности среды.

Игровую логику проверяй двумя изолированными экземплярами host/guest, отдельными savedata и сервером/портом. BridgeTools/RimBridge — только доступный dev-инструмент, не зависимость релиза. Запиши фактически выполненные шаги и результат в manual checklist; сценарий сам по себе не является PASS.

Для нового тестового мира администратор может передать dev-компаньону `rimlink/start_colony` параметр `planetCoverage`. Значение `0` сохраняет штатный выбор, доступны `0.3`, `0.5`, `1`. Значение `0.05` требует включённого dev mode и выбирает штатный вариант игры 5%. Ненулевой параметр принимается только до первой генерации мира. Для существующего мира он отклоняется. В результате `steps` сохраняется применённое значение. Экспортируй весь фактический мир и записывай число клеток, seed и идентификатор манифеста.

Wiki: test:checks → check:content → check:reference → check:drift -- --base &lt;commit&gt; → build → check:links, затем реальный браузер/поиск/мобильная навигация.

## Какая проверка отвечает на какой вопрос? {#test-matrix}

| Проверка | Подтверждает | Не подтверждает |
|---|---|---|
| Solution build/tests | Core/server contracts, storage, mocked boundary scenarios | Игровой UI/Scribe/пешки |
| Build-ClientMod | Компиляцию против установленной игры | Успешный двухсторонний сценарий |
| Два изолированных клиента | Реальное исполнение конкретных шагов | Все моды/DLC/GOG-комбинации |
| Wiki validators/build | Структуру, ссылки, inventory | Верность смысла статьи |
| Browser acceptance | Поиск, навигацию, layout в проверенных размерах | Все браузеры и настоящий OS zoom |

Для bugfix сначала наблюдай RED на исходном сценарии, затем GREEN. Для сетевого потока жди полученное событие, не возврат Open. Deadline измеряй Stopwatch; для time/race-изменений повтори Linux/two-CPU, если доступно.

Для Discord проверяй постоянные и временные ошибки отдельно: 403/404 отключают только исходящую доставку в проблемный канал до рестарта, а 429/5xx сохраняют пакет. Тестируй заголовки `#`, `##`, `-#` и начало новой строки как пользовательский текст. FakeDiscordOut позволяет задать точный отказ без настоящих токенов; такой прогон не подтверждает подключение к Discord.

Для ещё не выпущенной проверки модов собственной колонии используй сохранение, которому нужны моды сверх серверного манифеста, включая вход администратора. Отсутствие модов должно останавливать загрузку скачанного сохранения и локальное pending recovery до upload или очистки pending. После восстановления полного набора отдельно проверь настоящую загрузку карты. Обе ветки проверены в настоящей игре: отказ для скачанного сохранения/загрузка с полным набором и отдельный local-pending отказ без DLC с неизменными файлами, последующим однократным принятием того же snapshot и успешной загрузкой. Штатный выход также записал сохранение на изолированном сервере. Штатный выход с новым сохранением на рабочем сервере остаётся непроверенным; эти случаи не означают двухпользовательскую или Product-приёмку аванпостов.

## Как записать воспроизводимую приёмку? {#acceptance-record}

Укажи commit, версии, отдельный DataDir/порт, host/guest savedata и исходное состояние. Запиши действия, ожидаемые и наблюдавшиеся результаты, id операций, return mail и сохранение/повторный вход. Снимок UI без проверки серверного результата не доказывает escrow.

Для coop проверь назначенную/неназначенную пешку, выход, отзыв и rollback. Для экономики — неизвестный ответ и исходный replay. Не запускай чужие игры и не обнуляй общий Player.log. Незавершённый сценарий отмечай partial, не PASS.

## Ограничения и безопасность {#limits}

Не запускай второй сервер на данных живого сервера и не останавливай чужую игру. Общий Player.log может перезаписываться экземплярами. Не называй незапущенный тест успешным.
