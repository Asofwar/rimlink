# Размещение и запуск

Применимость: Rimlink 0.10.2 · RimWorld 1.7 · протокол 1.

## Как пользоваться {#usage}

Серверу и CLI версии 0.9.2 нужны Microsoft.NETCore.App 10.0.14 и Microsoft.AspNetCore.App 10.0.14. Проверьте оба через dotnet --list-runtimes. В runtimeconfig задан RollForward=Disable: без требуемого patch процесс остановится до запуска приложения. SDK 10.0.403 включает нужные frameworks. Другие patches могут быть установлены параллельно; следующий security patch сначала квалифицируется и поставляется новым выпуском.

Сервер — ASP.NET Core 10 с gRPC/HTTP2, REST и SQLite. Для запуска исходников нужен SDK из global.json; для framework-dependent релиза — соответствующий runtime. Постоянно сохраняй весь Server:DataDir, а не только БД.

Контейнерный пример в репозитории публикует 25560:25560 и монтирует ./data в /data. Перед запуском заполни секреты окружения. Для своего build используй deploy/Dockerfile. Вне Docker запускай исполняемый файл релиза из стабильного рабочего каталога: относительные пути вычисляются от него.

Прокси обязан пропускать HTTP/2/gRPC и долгие потоки, а не только страницу панели. Проверь сохранение и live-поток с внешнего клиента. Останавливай штатно с предупреждением игроков.

### Минимальный запуск из исходников

Установи SDK из global.json, собери сервер и создай отдельный рабочий каталог данных. Следующие команды выполняются из корня репозитория; парольный вход включён только для примера. В рабочем сервере используй собственные длинные секреты из окружения, не фиксируй их в Git.

```powershell
# Windows / PowerShell
$env:Rimlink__Server__DataDir='./data'
$env:Rimlink__Auth__AllowPassword='true'
$env:Rimlink__Auth__AdminLogins__0='admin'
dotnet run --project src/Rimlink.Server -c Release
```

```sh
# Linux
Rimlink__Server__DataDir=./data Rimlink__Auth__AllowPassword=true Rimlink__Auth__AdminLogins__0=admin dotnet run --project src/Rimlink.Server -c Release
```

### Контейнер

Из корня репозитория настрой секреты окружения, затем выполни `docker compose -f deploy/docker-compose.yml up -d`. Проверь `docker compose -f deploy/docker-compose.yml logs --tail=100`. Пример использует latest; перед рабочим запуском закрепи проверенный тег/ digest. Не запускай вместе с bare-процессом на том же DataDir. Штатная остановка: `docker compose -f deploy/docker-compose.yml down`; не добавляй удаление томов.

### Минимальная конфигурация и проверка

Для framework-dependent пакета файл appsettings.json в каталоге сервера содержит секции верхнего уровня; внешняя оболочка Rimlink в JSON не нужна:

```json
{"Server":{"Port":25560,"DataDir":"./data"},"Auth":{"AllowPassword":true,"AdminLogins":["admin"]}}
```

Запускай пакет через `dotnet Rimlink.Server.dll` из стабильного каталога. TLS включён по умолчанию: для первого подключения сверяй fingerprint по доверенному каналу; для публичного сертификата укажи Tls:CertificatePath и Tls:KeyPath (PEM). Открой TCP 25560 на сервере и маршрутизаторе только для нужной сети. Ожидаемый результат: сервер слушает порт, /health отвечает, клиент успешно сохраняет и повторно загружает колонию. Панель без успешного игрового подключения ещё не доказывает работу HTTP/2 прокси.

## Сеть и постоянные данные: проверка снаружи {#host-checklist}

Проверяй TCP-порт с машины игрока, не только localhost. NAT должен вести на правильный сервер; proxy — пропускать gRPC HTTP/2 и долгие потоки. Успешная загрузка HTML не проверяет streaming. Проверь игровой вход, передачу сейва и live-поток на тестовых колониях.

При контейнере сверь mount DataDir и права записи. Пересоздание контейнера не должно создавать новый пустой мир. Не запускай bare-server параллельно с контейнером на том же каталоге. Отдельно сохраняй настройки процесса, сертификаты и секреты: архив мира не является полной копией инфраструктуры.

## Ограничения и безопасность {#limits}

Один DataDir не должен обслуживаться несколькими серверами одновременно. Не копируй активную БД и сейвы произвольными независимыми копированиями. TLS обязателен по умолчанию; HTTP только для изолированной разработки.


В appsettings.example.json секция GuildCapture по умолчанию выключена. Её отдельные executor identity/profile/credential параметры описаны в справочнике конфигурации; регистрация исполнителя сама не запускает кампанию. Собственный DataDir, единый storage barrier и отдельный лицензированный игровой процесс остаются обязательными для будущего боевого стенда.

## Тестовые часы изолированного захвата {#guild-setup-clock}

Только dev host `Rimlink.GuildAcceptanceHost` предоставляет операторские `GET /api/admin/acceptance/clock/` и `POST /api/admin/acceptance/clock/advance` со scope `admin`. Шаг разрешён лишь в HOME, после первых сохранений обеих разрешённых тестовых личностей, при точном текущем cut/revision и отсутствии любого Active battle, включая ожидание cleanup. Purpose: EligibilitySetup либо ScheduledWindowNotice. Один шаг не более 7 суток, общий bootstrap budget 30 суток/32 шага. Нельзя перескочить ближайшее объявленное окно. После первого сдвига новые регистрации закрыты.

Шаг хранится как защищённая GuildCaptureOperation в общей цепочке, а domain clock публикуется после commit. Exact replay не добавляет время повторно; проверенный prefix восстанавливается до допуска запросов. Это не отдельный финансовый журнал. Auth/TLS, leases, challenges, сеть, AI и 20-минутный предел боя используют реальные часы. Шаг сам не производит и не выдаёт ресурс. Виртуальные сутки не являются многодневным runtime-тестом.

В изолированном host фоновый планировщик продолжает ожидать разрешённый HOME-допуск при GuildCapture.Enabled=false. Подготовка назначенной кампании требует проверенной общей V3 authority и текущего grant; сервер с выключенной настройкой `GuildCapture:Enabled` и без такого допуска кампании не запускает. Начало симуляции и выдача ресурсов в HOME по-прежнему запрещены.

Фоновый гильдейский планировщик ждёт SaveFiles storage barrier S, если другой writer временно скрыл опубликованный cut. Полный допуск проверяется уже под S→B; предварительная проверка transient cut не должна пропускать проход подготовки или отмены. Unit-регрессия подтверждает ожидание writer, а повторная native-проверка задержек после исправления ещё не выполнена.
