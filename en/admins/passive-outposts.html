Outposts: readiness, administration and isolated acceptance ​

Product remains Pending ​

The 10.0.14 executor uses the separate qualification rimlink-outposts-schema-20261107-runtime14 and its provider-v1 profile; the historical 10.0.13 qualification is unchanged. Qualification, provider profile and recorded Framework must match as one exact tuple. Unknown patches and mixed tuples refuse. Fresh/pre-DDL execution preserves exact artifact hash/MVID/provider/recipe equality; after proven post-schema state, legacy witness validation retains the no-DDL path. The server/CLI runtimeconfigs require 10.0.14 explicitly; do not bypass this policy with a runtime override.

The project version is 0.9.2; changing the version does not enable Product.

Version 0.9.2 ships a Pending embedded build artifact. Outposts:Enabled=true, an admin account, schema migration, a confirmed manifest or a successful private build cannot qualify Product. The release keeps the capability disabled. Update the server and client mod together.

The one readiness evaluator reports configuration, the fixed ten safety integrations and contract revisions, build qualification, actual startup state, chain-proved domain format, current schema, advertised capability, custody recovery and retained-history protection. Unknown fails closed. Enabled=false closes new gameplay, but never removes custody fences. Migrated domain v1 is FormatActivationRequired, not corrupt history: inspection and explicit v2 activation remain available while ordinary domain writers are closed. NoActiveWorld remains admin-only. Only the existing proved Completed Recreate path may bind a successor world through its separate evaluator gate; it does not enable ordinary recovery before real Ready.

Inspect, preview, retain and confirm ​

Use the Outposts screen in the existing admin panel or rimlink-tools admin outposts with the normal authenticated REST endpoint. GET inspection requires Read; upload, preview and commit require Admin, with service role checks as a second boundary. The panel retains its session/CSRF channel. Game-admin manifest confirmation uses the same canonical command service through additive protobuf fields; an old bare ID/digest confirmation is refused.

The CLI supports inspect [--player ID] [--operation ID] [--limit N] [--cursor VALUE], preview --request FILE, initialize --request FILE, activate-domain-format --request FILE, resolve --request FILE, and manifest inspect ID|upload FILE|confirm --request FILE. It calls REST only; it does not open a running database or calculate a replacement intent digest.

Preview drafts contain action, a fresh D-format requestId, a reason of 1..1024 UTF-8 bytes and exactly the selected typed action fields. The server binds the authenticated actor, observation, evidence, allocations and intent. Hashes are 64 lowercase hexadecimal characters; the canonical command is base64 and at most 64 KiB. Inspection returns at most 100 rows/1 MiB. The JSON transport is bounded at 2 MiB to allow an optional base64 OriginalOrdinaryInput sidecar, itself bounded at 1 MiB. That exact binary input is decoded and verified in memory, never accepted as an assertion of missing source, logged, staged on disk or stored in the command/audit. A hash cannot reconstruct a missing original RPC.

Save the whole returned command before submitting it with confirmed:true. The CLI accepts a retained preview envelope and removes diagnostic intent/blockers fields when posting its exact command/digest. The panel requires saving the command and a separate confirmation. Changing an input invalidates its preview. A changed head/state/evidence refuses the original selection: request a new preview and confirm it explicitly. No adapter silently refreshes or resubmits a replacement request. On an uncertain response preserve the saved command; a failure is not proof of a durable rejection or permission for another grant.

Initialization requires positively empty protected history, an already physically provisioned qualified NULL anchor, the actual world binding and exact schema/backend/location observation. It never initializes over missing/corrupt authority with history. An interrupted initialization needs the same original complete command/allocation; its digest alone is insufficient. Physical provisioning and restore/resume/backout remain separate stopped-server procedures, not online repair buttons.

Manifest and recovery choices ​

Before the first export, populate the server's def catalog from the active modpack. The full catalog must include the main world's biome names plus Steel and WoodLog. rimlink-tools modpack defs scans ThingDef and PawnKindDef only. Use the authenticated PUT /api/admin/modpack/defs with {"defNames":[...]} to submit the complete list, including biome names. This replaces the whole catalog, so retain the allowed item and pawn names when adding biomes. An empty catalog rejects a world manifest.

Export the administrator's actual game world on the main thread. The manifest uses the server's canonical world parameters after checking the actual planet. The local colony scenario, storyteller and difficulty may differ. The planet, game build, DLC and gameplay definitions must still match. Upload its exact binary document in chunks of at most 256 KiB, up to 24 MiB in total. Staging is a protected mutation and does not confirm the document. Inspect world/parameter/defs/DLC/catalog fingerprints, tile coverage, revision/digest and affected owner/preparation/outpost counts. Request a separate confirmation preview with an audit reason. Changing geography affecting custody requires the complete qualified recovery graph. Confirmation follows the existing settle/hold rules, preserves provenance and never enables Product or guesses elapsed production under SafetyHold.

After a bulk restore, a colony without protected outpost history can continue uploading ordinary saves, even if the backup already had a save for that colony. The server checks the restored generation and write epoch against the new save and verifies its file and recovery metadata. When that colony first takes a protected snapshot in the restored world, the server checks the retained cut for prior protected history. A colony with protected history still needs the canonical snapshot proof and the restore bridge. A verified pending handoff from another player can be staged after a new ordinary save in the restored colony. Custody stays with the sender until an accepted protected save contains the recipient's delivery receipt. A pending parcel selected by a bulk restore continues to read its original confirmed manifest. The server verifies the stored restore authorization against the parcel, recipient and current scope before serving that document. A later recall creates a new return envelope in the current scope and retains the original assignment capture.

Archiving or restoring a colony covered by the current bulk restore uses the protected lifecycle journal, including for ordinary saves. Archives that already existed in the selected backup are verified against that backup's owner, generation, manifest and file hashes. An archive created after the bulk restore without a lifecycle record requires recovery. Keep the original archive and its evidence when a check fails.

The server validates retained backup files and nested provenance before committing protected changes. It opens SQLite on a disposable verification copy and checks the retained inventory again afterwards. Restore files used by resume or backout remain durably written.

The client waits 30 seconds after the current automatic refresh finishes before starting the next one. When protected data checks take longer, this leaves time for owner commands between refreshes.

Resolve is limited to ExistingTerminal, AbortNoRemoval, AbortWithReturn, OrdinaryReturn and CanonicalDownload. Each rechecks the actual immutable source, original scope, current canonical proof and exact operation state. Property-moving choices additionally require qualified recovery readiness. Existing accepted/applied outcomes produce no second transfer; unknown removal cannot be converted to a negative source. CanonicalDownload selects the existing authorized snapshot/provenance and requires owner download/reconciliation, not a spawn, new epoch or rewritten historical payload. All historical outcomes carry NoReplayAuthorization.

Archive/reset/backup diagnostics are advisory. A readiness-only observation does not execute their full locked lifecycle validation: such a result is Unknown, with the required check named, rather than Allowed. A proved readiness blocker is Denied. Preserve artifacts and use the existing explicit operation/preflight; no automatic settle runs during inspection. See backup and recovery for offline procedures.

Isolated host and build-only qualification ​

tools/Rimlink.OutpostAcceptanceHost is a dev-only executable, excluded from ordinary published server/CLI/mod artifacts and the final Docker image. It uses the same application builder, routes, backend, authorization and storage checks. Its internal nonserialized provider identifies IsolatedAcceptance/Pending and waives only the circular requirement for the future Product acceptance seal. It does not waive integrations, automated prerequisites, client versions, authority, exact proofs or locks. There is no ordinary runtime flag or config key for this mode.

The dev executable carries the real panel files in its build output and uses that explicit web root. Comparing panel bytes against the embedded source inventory does not replace checking the rendered page in a browser. An admin-only host defers constructing domain writers and admits them when the same evaluator later observes real Ready after the proved successor bind. Each started writer continues rechecking the gate.

Before a separately authorized Task16 start, an explicit stand descriptor must bind a canonical private root containing separate data, external anchor, backups/archive, game copy and two save roots; unique stand-owned host/guest game IDs; exact compiled mod/companion/core/protocol binaries; loopback port; configuration and prerequisite files. Preparation owns only empty private state and never provisions authority. Reparse/alias paths, hard links in owned state, foreign files, changed configuration, wrong binary identities/evidence or a second ownership lock refuse. Restart rechecks them. The host clears inherited configuration sources and loads only the owned stand file; it does not copy production auth, launch shared games, edit MCP configuration or terminate processes.

Build-only scripts/Seal-OutpostQualification.ps1 rebuilds the dev tool before evaluating an explicit evidence record. Candidate output remains Pending. Seal refuses unless every required automated case, actual G1–G7, real Astra whole-branch review and verified fixes has PASS evidence for the exact embedded safety-source identity, with matching evidence-file SHA-256. Tests using synthetic records prove refusal/evaluation logic only; they are not acceptance evidence. No real seal has been generated. The artifact is embedded in a later build and excluded from its own source hash; runtime configuration, admin APIs, data/anchor or a copied backup cannot change it. A relevant source change invalidates the old qualification.

For a positively empty stopped new stand, the separate provision <stand.json> command calls the existing OutpostAnchorStore.Provision(), verifies the physical Record=NULL singleton and creates no logical authority. Neither prepare nor run performs provisioning. Repeat provisioning, history, a partial store or a busy lock refuses while retaining files.

The private controller uses a current-user-only channel with exact stand/run/source identities and a random nonce. run <stand.json> records the launch attempt, then publishes its clock journal after startup checks and verification of the real OutpostClock sample. Early refusals are recorded separately. A subsequent restart <stand.json> <previous-run-id> <downtime-ticks> requires the same source's closed journal and records its SHA-256 and explicitly declared nonnegative downtime. Published journals are retained, including incomplete runs. Actual persisted checkpoint validation forbids starting in the past. The private TimeProvider feeds only OutpostClock. A positive idempotent step moves consistent UTC and monotonic readings, while other services and transport timers keep ordinary time. The journal records the initial binding, actual Sample, planned/applied steps, real process clocks and closure. A journal write failure fences further steps and stand qualification.

The dev companion binds pause controls to attestation from the live private host, exact loaded binaries, its own game/save-data paths and the current login/session. Waits distinguish durable local saves, accepted saves, removal and cleanup; there is no wait inside atomic batch removal. A different game, menu/visit, disconnect/relogin or cancellation invalidates the wait. For lost replies, a server interceptor holds the real response after service completion and before handing it to gRPC; it never fabricates a successful response. These tools reproduce boundaries and do not themselves prove G1–G7.

For G2, separate entry pauses cover real Prepare/Commit calls after the ordinary authentication/capability gate and before the business service. They bind the current session, scope, original operation and intent digest. Reached-entry does not prove that another replay has no result. After-durable pauses and lost transport replies are recorded separately.

For G3, rimlink/outpost_acceptance_fault controls one dev-only fault for a selected real protected parcel. delivery-placement-fail-after-prefix checks the exact game DLL against the inspected RimWorld 1.7.4998 and 1.7.5000 builds and records the loaded DLL hash in the evidence. Within the ordinary drop call it records actual object references, quantities, worker UUIDs and containers, then interrupts only when 0 < placed < total. It neither waits nor makes network calls on the main thread. delivery-definition-unavailable denies one existing lookup for an actually declared thing:<defName> or kind:<defName> exactly once; this is explicitly labelled fault injection, not a DefDatabase edit or a real cross-mod login test. Arming rechecks the private host, current session and authentic parcel. A separate private record observes the real write fence and absence of a local materialization receipt before ordinary abort; the hook does not set these flags. When the active home game rejects a protected batch as incompatible before placement, it pauses and fences saves while the server retains the parcel. Full placement without a receipt and held without WritesBlocked do not prove partial placement and write blocking. These scenarios still require real game execution; building the tools is not a G3 PASS.

The dev-only delivery-before-materialize pause holds a real delivery after the server reply and before objects are placed on the map. Returning to the main menu cancels the wait. The companion can read the cancelled pause in the menu by exact parcel and operation ID. Verify separately that the server kept the pending parcel and that no placement or receipt occurred.

The game defers automatic outpost refresh and starting another background recovery pass while the same client is admitting workers, applying an owner command or processing a protected parcel. Typed outpost requests have a two-minute deadline for validating retained restore history. When the login or game changes, the original cancellation still applies. If a manifest page times out, the client retries that page once in the same login and keeps the pages already read. The full manifest digest and local compatibility checks still run before custody or delivery can change.

After a bulk restore, login checks the authenticated world, owner, generation, write epoch and restore boundary before replay. Proven outbox entries from another scope are kept with the original outbox document. A verified pending save from the same colony's previous restore boundary is kept as a .restore-boundary-….rws file with its original pending journal and flag. The client then downloads the server's canonical save. Ambiguous or damaged recovery evidence still requires recovery.

The offline dev adapter provides offline-inspect <stand.json> <archive>, offline-backout-inspect <stand.json> <restore-id> and offline <stand.json> <invocation.json>. Invocation version=1 explicitly selects execute, resume or backout: Execute/Backout require an owned requestFile and a separate confirmationDigest; Resume requires the original restoreId. Paths, the original request/journal and descriptor are bound to the owned stand. The codec shared with the normal CLI preserves its strict JSON format: requests of 1..32 MiB, depth 32, no duplicate/unknown properties; Anchor ByteString is an array of byte values 0..255, at most 4096 elements. No new confirmation or repair grant is created.

The existing restore Checkpoint holds only a separate worker. The private controller observes a published record without opening the mutable DB. Arm selects a literal hook, an exact relative inventory path where applicable and an occurrence after that arm. Before publication, a Reached event is durably written and read back with the actual journal identity/phase/revision and real process clocks. Release requires exact armId/sequence/event SHA-256 and unchanged inputs/journal; retries are idempotent. A run allows at most 64 arms and 256 mutating control commands, waits up to 120 seconds, and cancels the worker through its ordinary cancellation/error path after 30 seconds without a heartbeat. Cancellation and Refused/Maintenance do not establish NoEffect. Hard interruption of the owned CLI followed by inspect→explicit Resume/Backout checks actual files, the native journal, main/external completion and publication. GUI games are controlled separately through the authorized CUA Driver. The adapter itself proves neither G6 completion nor power-loss safety.

Independent G6 cases may use sequential preparation of one stopped stand: normally restore an authentic newer cutB, then start a separate cutA restore with new IDs/boundaries. The next case begins only after the previous case has a proved terminal state; a new Execute or raw DB/anchor copy cannot reset an unfinished journal. Actual inventory and hooks prove replace/delete coverage. A missing-path fault retains the coherent complete anchor artifact set and checks refusal/Maintenance at the unavailable original path, including another startup. The retained store is not irretrievably lost and cannot establish successful LostAnchorRecovery. Remove this fixture fault only after stopping, checking unchanged original bytes and proving no intervening domain/fence changes. A separate same-boundary older-DB negative and a real successful fresh-boundary restore remain required.

Limits and verification status ​

When RimWorld updates, rebuild the mod and the development companion against the installed build and repeat the isolated game checks on that build. A change in game version or gameplay content also requires a compatible confirmed manifest. The acceptance build used RimWorld 1.7.5000.

Immutable trigger SQL in the outpost migrations uses explicit CRLF bytes, so an LF source checkout produces the same qualified catalog. The six existing profile IDs and digests are unchanged; unknown LF-only trigger catalogs still refuse without repair. Updating the assembly does not replace the executor of an already frozen restore plan.

Real G1–G7 acceptance has completed on isolated two-client stands, followed by one final branch review and verification of all seven required fixes. Evidence preserves each source/build boundary: the affected game routes were checked in four real scenarios, and the final server-only valuation edge was checked separately. These results have not been resealed as a Product qualification for the release build. Product remains Pending/off. Builds and targeted unit/RPC checks do not replace two real clients. Never delete server.lock, save-storage.lock, an anchor, return fence or restore journal to force readiness.
